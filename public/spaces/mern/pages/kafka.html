Kafka Fundamentals

Q1. What is Apache Kafka?

Apache Kafka is a distributed, fault-tolerant event-streaming platform built for high-throughput, real-time data pipelines and streaming applications. Producers append events to durable topic partitions, and consumers read them independently at their own pace.

What does each part mean?

TermMeaning in KafkaExample
Distributed Kafka runs as a cluster of multiple brokers instead of relying on one server. Topic partitions are spread across those brokers, allowing storage and traffic to be shared. An orders topic has six partitions distributed across three brokers. Each broker handles part of the order traffic, and more brokers can be added as traffic grows.
Fault-tolerant Kafka replicates partition data across brokers. If the broker hosting a leader replica fails, an in-sync follower can become the new leader so clients can continue operating. With replication factor 3, an order event is stored on three brokers. If one broker crashes, another replica serves the partition without losing the acknowledged event.
Event An event is an immutable record describing something that happened. It normally contains a key, value, timestamp, and optional headers. { "orderId": "O-101", "status": "CREATED" } records the fact that order O-101 was created. The orderId can be used as the key to preserve ordering for that order.
Streaming Events are produced and consumed continuously rather than waiting for a complete batch. Kafka retains them for a configured period, so consumers can process new events or replay older ones. Every checkout immediately produces an order event. Inventory, payment, analytics, and notification consumers process the stream independently.
Platform Kafka is more than a message queue. It provides durable storage, producers and consumers, replication, consumer groups, Kafka Connect for integrations, and Kafka Streams for processing. An application publishes transactions, Kafka Connect moves them to a data warehouse, and Kafka Streams calculates totals in real time.
High throughput Kafka can handle large numbers of events efficiently by using append-only sequential writes, batching, compression, partition-level parallelism, and efficient network transfer. An e-commerce system can publish hundreds of thousands of click or order events per second by distributing them across partitions and batching producer requests.
Real time Consumers can receive and process events with very low latency soon after they are published. “Real time” here generally means near-real-time processing, not a hard real-time deadline. A fraud-detection consumer evaluates a payment seconds or milliseconds after the payment event arrives instead of processing it in an overnight job.
Data pipeline A pipeline moves and transforms data between systems reliably. Kafka acts as the durable middle layer that decouples the source from one or more destinations. Application database changes are captured into Kafka and then delivered to Elasticsearch for search, S3 for archival, and a warehouse for reporting.
Streaming application A streaming application continuously consumes events, applies operations such as filtering, grouping, joining, or aggregation, and produces results or new events. A Kafka Streams application groups purchases by customer over a five-minute window and emits an alert when the total crosses a fraud threshold.

Simple flow: An Order Service produces an OrderCreated event to Kafka. Kafka stores it durably in a replicated partition. Inventory and Payment services consume it through separate consumer groups, while Analytics can replay the same event later without affecting those services.

Interview answer: “Kafka is distributed because its partitions run across multiple brokers, fault-tolerant because those partitions are replicated, and high-throughput because it uses partitioning, batching, and sequential log writes. It streams durable events in near real time, allowing independent applications to process or replay the same data for pipelines, analytics, and event-driven microservices.”

Q2. Why do we use Kafka?

Kafka handles large traffic spikes, durable event storage, real-time processing, and asynchronous communication. It decouples producers from consumers, lets services scale independently, and supports replay because consuming an event does not immediately delete it.

Q3. What are Kafka's main components?

A producer publishes records; a broker stores and serves them; a topic names an event stream; partitions divide that stream; a consumer reads records; a consumer group shares partitions; and an offset identifies a record's position within a partition.

Q4. What is a Kafka topic?

A topic is a named, append-only stream of related events, such as orders.created or payments.completed. Producers write to it and one or more independent consumer groups read from it.

Q5. What is a partition?

A partition is an ordered, immutable log that forms part of a topic. Partitions are distributed among brokers and let Kafka process reads and writes in parallel.

Q6. Why are partitions important?

Partitions provide horizontal scalability, parallel consumption, and load distribution. Within one consumer group, a partition is assigned to only one consumer at a time, so useful consumer parallelism cannot exceed the number of partitions.

Q7. What is a Kafka broker?

A broker is a Kafka server. It stores partition log files, handles producer and consumer requests, replicates partitions, and participates in cluster coordination. A production cluster normally uses multiple brokers for capacity and fault tolerance.

Q8. What is a producer?

A producer is a client that serializes records and publishes them to topics. It chooses a partition through a key, default partitioner, or custom partitioner and controls batching, compression, acknowledgements, and retries.

Q9. What is a consumer?

A consumer pulls records from brokers, deserializes and processes them, and tracks its position through offsets. Different consumer groups can independently read the same records.

Q10. What is a consumer group?

A consumer group is a set of consumers cooperating on a workload. Kafka assigns each subscribed partition to exactly one consumer in that group, while a different group receives its own independent view of the topic.

Q11. What is an offset?

An offset is a monotonically increasing position assigned to a record within one partition. Consumers commit offsets, commonly in Kafka's __consumer_offsets topic, so they can resume or deliberately replay data.

Q12. Is Kafka push-based or pull-based?

Kafka uses a pull model: consumers request batches when ready. This provides natural back pressure, allows efficient batching, and prevents the broker from overwhelming a slow consumer.

Q13. What does append-only log mean?

Records are appended sequentially to the end of a partition log rather than updated in place. Sequential I/O, batching, and the operating-system page cache are major reasons Kafka achieves high throughput.

Q14. Does Kafka delete messages after consumption?

No. Consumption only advances a consumer's offset. Kafka deletes or compacts records according to the topic's time, size, or compaction policy, which makes replay possible.

Q15. Kafka vs RabbitMQ: when would you choose each?

Choose Kafka for durable event streams, replay, very high throughput, analytics, and event-driven architectures. Choose RabbitMQ for traditional work queues, flexible per-message routing, and low-latency task distribution. The correct choice depends on delivery, retention, ordering, and replay requirements.

Internals, Reliability, and Delivery

Q16. How does Kafka achieve high throughput?

Kafka combines sequential disk writes, page-cache use, zero-copy transfer, record batching, compression, and partition-level parallelism. It avoids expensive per-record random I/O.

Q17. What is replication factor?

The replication factor is the number of copies of each partition across brokers. A factor of three normally means one leader and two followers, allowing the cluster to survive broker failures when replicas remain in sync.

Q18. What are leader and follower replicas?

The leader handles reads and writes for a partition. Followers copy the leader's log and can be elected leader if the current leader fails. Replica placement should span brokers and, where supported, failure domains.

Q19. What happens if a broker goes down?

The controller detects the failure and elects new leaders from eligible in-sync replicas. Clients refresh metadata and reconnect. With adequate replication and min.insync.replicas, service continues without acknowledged data loss.

Q20. What is ISR?

ISR means in-sync replicas: replicas sufficiently caught up with the partition leader. ISR membership matters because acks=all waits for the required in-sync replicas and leader election normally selects from this set.

Q21. How does Kafka guarantee message ordering?

Kafka guarantees order only within a partition. Use a stable entity key such as orderId so related records reach the same partition. Global ordering requires one partition and therefore sacrifices parallelism.

Q22. What delivery semantics does Kafka support?

At-most-once can lose messages but avoids duplicates; at-least-once avoids loss but may redeliver; exactly-once uses idempotence and transactions for atomic Kafka read-process-write flows. External side effects still require idempotent application design.

Q23. How does a consumer know where to resume?

It resumes from the committed offset for its group and partition. Commit after successful processing for at-least-once delivery; commit before processing only when occasional loss is acceptable.

Q24. What is consumer rebalancing?

Rebalancing redistributes partitions among members of a consumer group. Consumption may pause while ownership changes, so frequent rebalances can create latency and lag spikes.

Q25. When does a rebalance occur?

Common triggers are a consumer joining or leaving, missed heartbeats, a subscription change, or a partition-count change. Static membership and cooperative assignment can reduce unnecessary partition movement.

Q26. What is auto offset commit?

With auto commit, the client periodically commits the latest polled positions. It is convenient but can commit records before business processing finishes, so critical consumers commonly disable it and acknowledge only after success.

Q27. What is the difference between enable.auto.commit=true and false?

true lets the consumer library commit periodically; false gives the application explicit commit control. Manual control improves processing guarantees but requires careful handling of failures, batches, and retries.

Q28. What happens if a consumer crashes?

After its session expires, the group coordinator triggers a rebalance and assigns its partitions to surviving consumers. Processing resumes from the last committed offsets, so uncommitted records may be delivered again.

Q29. What is a retention policy?

Retention determines how long or how much data Kafka keeps, independently of whether records were consumed. Typical controls are time-based retention, size-based retention, and log compaction.

Q30. What is the difference between time- and size-based retention?

Time retention removes old log segments after a configured age; size retention removes old segments when a partition exceeds its byte limit. If both apply, Kafka removes eligible segments when either limit is reached.

Q31. What is log compaction?

Compaction eventually retains the latest value for each key, while tombstone records represent deletion. It is useful for changelogs and rebuilding current state; it is different from keeping every event for a fixed time.

Q32. What is an idempotent producer?

An idempotent producer prevents duplicate writes caused by producer retries. With enable.idempotence=true, Kafka uses producer IDs and per-partition sequence numbers to reject duplicate batches.

Q33. Explain acks=0, acks=1, and acks=all.
SettingBehaviourTrade-off
0No broker acknowledgementLowest latency, highest loss risk
1Leader acknowledgesLeader failure before replication may lose data
allAll required ISR replicas acknowledgeStrongest durability, somewhat higher latency

For important events, pair acks=all with an appropriate min.insync.replicas.

Q34. What are serializers and deserializers?

A serializer converts a key or value object into bytes before publishing; a deserializer reconstructs an object when consuming. Producer and consumer formats must agree, ideally through a versioned schema.

Q35. What is a dead-letter topic?

A dead-letter topic stores records that still fail after bounded retries. Include the original topic, partition, offset, exception, timestamp, and correlation ID so teams can diagnose, fix, and safely replay failures.

Q36. What is exactly-once semantics?

Kafka exactly-once semantics combine idempotent production with transactions so output records and consumed offsets commit atomically in a Kafka-to-Kafka pipeline. It does not automatically make database calls or emails exactly once.

Q37. How does Kafka achieve fault tolerance?

Kafka uses replicated partition logs, leader election, ISR tracking, persistent storage, producer retries, and committed consumer offsets. Correct replication and acknowledgement settings are essential; replication alone is not a complete guarantee.

Q38. What role did ZooKeeper play in Kafka?

Older Kafka deployments used ZooKeeper for controller election, broker membership, and cluster metadata coordination. Modern Kafka uses KRaft and no longer requires ZooKeeper.

Q39. What is KRaft mode?

KRaft is Kafka's built-in metadata consensus system based on a Raft-style quorum. It removes the ZooKeeper dependency, simplifies operations, and improves metadata scalability and controller failover.

Ecosystem, Performance, and Security

Q40. Kafka Streams vs Consumer API: what is the difference?

The Consumer API gives low-level polling, offset, and processing control. Kafka Streams is a higher-level Java library for transformations, joins, windows, aggregations, local state stores, and fault-tolerant stream-processing topologies.

Q41. What is Kafka Connect?

Kafka Connect is a framework for moving data between Kafka and external systems using reusable connectors. It handles scaling, offsets, configuration, and fault recovery without requiring a custom integration service.

Q42. What is the difference between a source and a sink connector?

A source connector imports records from an external system into Kafka. A sink connector exports Kafka records to an external system such as a database, search index, or object store.

Q43. What is Schema Registry?

A Schema Registry centrally stores schemas and compatibility rules for formats such as Avro, Protobuf, and JSON Schema. It enables safe schema evolution and prevents incompatible producers from breaking consumers.

Q44. Compare Avro, JSON, and Protobuf.

JSON is readable and flexible but larger and often weakly governed. Avro is compact, schema-driven, and popular in Kafka ecosystems. Protobuf is compact, fast, strongly typed, and supports explicit field evolution. Choose based on interoperability, tooling, evolution rules, and readability needs.

Q45. What is zero-copy in Kafka?

Zero-copy lets the operating system transfer cached log data directly to the network socket without repeatedly copying it through application buffers. This lowers CPU use and memory-copy overhead.

Q46. How does Kafka handle back pressure?

Consumers pull only what they can handle and can tune fetch and poll sizes. Growing consumer lag signals insufficient processing capacity; respond by optimizing work, batching, or scaling consumers up to the partition count.

Q47. What is throttling in Kafka?

Kafka quotas can limit producer byte rate, consumer fetch rate, and request rate per client or user. Throttling protects broker resources and prevents one workload from degrading the whole cluster.

Q48. What happens if a producer is faster than the broker?

The producer buffers records and sends batches. If its buffer fills before delivery completes, send() can block up to max.block.ms and then fail. Tune batching and compression, apply upstream back pressure, and fix broker or network bottlenecks rather than retrying forever.

Q49. How do you secure Kafka?

Use TLS for encryption, SASL or mutual TLS for authentication, and ACLs for authorization. Also protect secrets, isolate networks, apply least privilege, encrypt disks where required, audit access, and secure Schema Registry and Connect endpoints.

Q50. What are common real-time Kafka use cases?

Examples include order and payment events, notifications, audit logs, clickstreams, fraud detection, CDC pipelines, metrics, log aggregation, event-driven microservices, and continuously updated analytics.

Spring Boot and Production Scenarios

Q51. Why is Kafka useful in a microservice architecture?

Kafka enables asynchronous, loosely coupled communication: producers do not require consumers to be available at the same moment. Events remain durable and replayable, while separate consumer groups let services scale and fail independently. Use REST when an immediate response is genuinely required.

Q52. What is KafkaTemplate in Spring Boot?

KafkaTemplate is Spring Kafka's producer abstraction. It handles serialization and asynchronous sends, exposes delivery results, and can participate in Kafka transactions. Production code should observe send failures rather than treating send() as guaranteed success.

kafkaTemplate.send("orders.created", order.id(), event)
    .whenComplete((result, error) -> {
        if (error != null) log.error("Kafka publish failed", error);
    });
Q53. What does @KafkaListener do?

@KafkaListener registers a Spring method as a Kafka message handler and configures topics, group ID, concurrency, and container factory. The container manages polling, heartbeats, deserialization, offset commits, and error handling.

@KafkaListener(topics = "orders.created", groupId = "inventory-service")
public void reserve(OrderCreated event) {
    inventoryService.reserve(event);
}
Q54. How do you handle consumer exceptions in Spring Boot?

Classify errors as retriable or permanent. Use a bounded backoff for transient failures, route exhausted or non-retriable records through DeadLetterPublishingRecoverer, preserve diagnostic headers, alert on the DLT, and make processing idempotent.

Q55. How should failed Kafka messages be retried?

Use immediate retry only for brief transient errors, then exponential backoff or retry topics for longer outages, followed by a DLT after a fixed maximum. Avoid blocking a partition indefinitely and never retry validation or deserialization errors without a remediation path.

Q56. What is consumer lag?

Consumer lag is the difference between a partition's log-end offset and a consumer group's committed or current offset. Persistent growth means production is outpacing processing; a momentary spike may simply reflect batching or a rebalance.

Q57. How do you debug continuously increasing consumer lag?
  1. Measure lag per partition and identify whether it is uniform or caused by a hot key.
  2. Compare producer rate with consumer throughput and inspect rebalances, errors, GC pauses, CPU, disk, and network.
  3. Profile slow database or HTTP calls and check max.poll.records and max.poll.interval.ms.
  4. Optimize or batch processing, then add consumers up to the partition count or repartition through a controlled migration.
Q58. How do you improve Kafka consumer performance?

Batch reads and writes, remove blocking or N+1 work, tune fetch and poll sizes, use appropriate listener concurrency, compress efficiently, and add partitions and consumers when justified. Preserve per-key ordering and do not let asynchronous work cause offsets to commit before processing completes.

Q59. How do you monitor Kafka in production?

Monitor consumer lag and consumption rate; producer error, retry, and request latency; broker request latency, disk use, network traffic, offline partitions, under-replicated partitions, ISR changes, and controller health. Correlate metrics with logs and traces, and alert on sustained symptoms rather than isolated spikes.

Q60. What happens when partition count is increased?

Consumers rebalance and new records spread across more partitions, increasing potential parallelism. Existing records are not redistributed. Key-to-partition mapping can change, so per-key ordering across the change may be affected. Partition count cannot simply be reduced; for strict requirements, migrate to a new topic.

Q61. How do you choose a partition strategy?

Estimate target throughput, per-partition capacity, and maximum useful consumer concurrency. Choose a high-cardinality key that preserves required entity ordering and distributes load evenly. Avoid low-cardinality or skewed keys, leave measured growth headroom, and account for broker file-handle and metadata overhead.

Q62. What happens internally when a producer sends and a consumer reads a record?
  1. The producer serializes the record, selects a partition, batches it, and sends it to the leader.
  2. The leader appends it to a log segment; followers replicate it.
  3. The broker acknowledges according to the producer's acks setting.
  4. The consumer fetches a batch from a chosen offset, processes records, and commits its next position.
Q63. What is auto.offset.reset?

It applies only when a consumer group has no valid committed offset. earliest starts at the oldest retained record, latest starts with new records, and none fails instead of choosing automatically.

Q64. What happens when a new consumer joins a group?

The member joins through the group coordinator, the group negotiates an assignment, partitions move according to the configured assignor, and consumption resumes. Cooperative sticky assignment reduces stop-the-world movement compared with eager rebalancing.

Q66. Kafka Streams vs Spark Structured Streaming: when would you use each?

Kafka Streams is an embedded Java library suited to low-latency, Kafka-native per-service processing with local state stores. Spark Structured Streaming is a separate distributed analytics engine suited to large ETL, data-lake, SQL, and machine-learning workloads across many data sources.

Q67. How do Kafka consumer groups, offsets, and rebalancing work together?

Kafka combines consumer groups, partition offsets, and rebalancing to provide parallel processing, failure recovery, and independent consumption of the same topic.

1. Consumer groups

  • Consumers that use the same group.id cooperate to process a topic.
  • Within one group, each partition is assigned to exactly one consumer at a time. A consumer may own several partitions.
  • If a topic has four partitions and the group has two consumers, each consumer will typically process two partitions.
  • If the group has six consumers but only four partitions, at most four consumers can receive assignments; the remaining consumers stay idle.
  • Different groups consume independently. For example, inventory-service and analytics-service can each read every event from orders.created because they use different group IDs.

2. Offsets

An offset is a record's sequential position inside one partition. Offsets are not global across a topic. Each consumer group maintains a committed offset for every partition it consumes, normally in Kafka's internal __consumer_offsets topic.

  • Current position: the next record the consumer will fetch during its active session.
  • Committed offset: the durable recovery position stored for the group. Kafka commits the offset of the next record to read.
  • If records at offsets 0–9 were processed successfully, committing offset 10 means processing should resume from record 10.
  • Commit after successful processing for at-least-once delivery. A crash before the commit may cause records to be delivered again, so consumers must be idempotent.
  • Committing before processing can provide at-most-once behavior, but a crash after the commit can lose unprocessed work.

3. Rebalancing

A rebalance redistributes partitions among the active members of a group. The group coordinator tracks membership using join requests, heartbeats, and polling activity.

Common rebalance triggers include:

  • a new consumer joining the group;
  • a consumer shutting down, crashing, or missing heartbeats;
  • a consumer exceeding max.poll.interval.ms because processing takes too long;
  • subscribed topics or their partition counts changing.

During assignment, a partition assignor decides which member owns each partition. With an eager strategy, members revoke all partitions before receiving a new assignment, temporarily pausing the group. A cooperative sticky strategy moves only the partitions that need to change, reducing disruption and retaining assignments where possible.

End-to-end failure example

  1. The orders.created topic has partitions P0, P1, P2, and P3. Consumer A owns P0/P1, while Consumer B owns P2/P3.
  2. Consumer A processes and commits its offsets independently for P0 and P1.
  3. Consumer A crashes and stops sending heartbeats.
  4. After the session timeout, the coordinator removes A and starts a rebalance.
  5. Consumer B, or a newly started Consumer C, receives P0 and P1 and resumes from that group's last committed offsets.
  6. Any successfully processed but uncommitted records may be delivered again. Idempotent processing prevents duplicate database updates or notifications.

How to reduce harmful rebalances

  • Keep polling regularly and ensure record processing does not exceed max.poll.interval.ms.
  • Tune session.timeout.ms and heartbeat settings carefully instead of masking slow processing with very large values.
  • Use cooperative sticky assignment to reduce partition movement.
  • Use static membership with a stable group.instance.id for consumers that restart predictably.
  • Shut consumers down gracefully so they can leave the group cleanly and commit completed work.
  • Monitor rebalance count/duration, consumer lag, processing time, poll interval, and commit failures.

Interview answer: “Consumers with the same group ID divide topic partitions so only one member in that group owns a partition at a time. The group stores a committed offset per partition, which is the next position to read after recovery. When membership or partition metadata changes, Kafka rebalances those assignments. If a consumer fails, another member takes its partitions and resumes from the last committed offsets, which can redeliver uncommitted records; therefore, I commit only after successful processing and make the consumer idempotent.”
