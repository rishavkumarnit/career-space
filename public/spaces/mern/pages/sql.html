1. SQL Theory Fundamentals

Q1. What is SQL, and what are its four sub-languages? ***

SQL (Structured Query Language) is the standard language for querying and managing data in a relational database. It's conventionally split into four sub-languages by what they operate on:

Sub-languagePurposeCommands
DDL — Data DefinitionDefines/modifies schema structureCREATE, ALTER, DROP, TRUNCATE
DML — Data ManipulationReads/writes the data itselfSELECT, INSERT, UPDATE, DELETE
DCL — Data ControlManages permissionsGRANT, REVOKE
TCL — Transaction ControlManages transactionsCOMMIT, ROLLBACK, SAVEPOINT

Common follow-up: "is SELECT really DML if it doesn't modify anything?" — strictly it's sometimes bucketed separately as DQL (Data Query Language), but most interview answers fold it into DML since it's still about handling data rather than schema.

Q2. Primary key vs foreign key vs unique key ***
Primary keyForeign keyUnique key
PurposeUniquely identifies each row in its own tableReferences a primary/unique key in another tableEnforces uniqueness on a non-primary column
Count per tableExactly oneMany allowedMany allowed
NULLsNever allowedAllowed (means "no parent")Usually one NULL allowed
Default indexOften becomes the clustered indexNot automatically indexed in every engineAlways backed by an index

A foreign key's whole job is enforcing referential integrity — the database physically refuses an INSERT/UPDATE that would leave a foreign key pointing at a parent row that doesn't exist, and by default blocks deleting a parent row that's still referenced.

Q3. What is normalization? Briefly explain 1NF, 2NF, 3NF ***

Normalization is the process of structuring tables to reduce data redundancy and prevent update/insert/delete anomalies, typically by splitting one wide table into several related ones.

FormRule
1NFEvery column holds a single, atomic value — no comma-separated lists or repeating groups crammed into one field
2NF1NF, plus every non-key column depends on the entire primary key — only matters when the key is composite (eliminates partial dependency)
3NF2NF, plus no non-key column depends on another non-key column — every non-key column depends on the key, the whole key, and nothing but the key (eliminates transitive dependency)

Common follow-up: "is more normalization always better?" — no. Highly normalized schemas minimize redundancy but require more joins to reassemble data, which can hurt read-heavy analytics workloads. Deliberately reintroducing redundancy (denormalization) is a common, valid tradeoff for reporting tables and read replicas.

Q4. WHERE vs HAVING ***

WHERE filters individual rows before grouping/aggregation happens, and can't reference an aggregate function. HAVING filters groups after GROUP BY has run, and is the only place you can filter on an aggregate like COUNT()/SUM().

SELECT dept_id, COUNT(*) AS headcount
FROM employees
WHERE is_active = true        -- filters rows first
GROUP BY dept_id
HAVING COUNT(*) > 5;          -- then filters the resulting groups

Common pitfall: trying to filter on an aggregate inside WHERE — WHERE COUNT(*) > 5 is a syntax error, because at the point WHERE runs, grouping hasn't happened yet and no aggregate value exists.

Q5. UNION vs UNION ALL **

UNION combines the result sets of two queries and removes duplicate rows — it implicitly runs a DISTINCT pass, which costs a sort/hash step. UNION ALL combines them and keeps every row, duplicates included, with no dedup pass.

Common pitfall: reaching for UNION out of habit when duplicates are actually impossible (e.g., the two queries pull from mutually exclusive ID ranges) or simply don't matter — that's paying for a dedup pass that changes nothing except performance. Default to UNION ALL unless you specifically need deduplication.

Q6. DELETE vs TRUNCATE vs DROP ***
DELETETRUNCATEDROP
TypeDMLDDLDDL
RemovesRows matching WHERE (or all, if omitted)All rows, at onceThe entire table structure and its data
LoggingRow-by-row, fully loggedMinimally logged (deallocates pages)Schema change, logged as metadata
RollbackYes, within a transactionOften not, or engine-dependentNot once committed
TriggersFire normallyRow-level triggers don't fireN/A

TRUNCATE is dramatically faster than an unqualified DELETE for clearing a whole table precisely because it skips row-by-row logging — it just deallocates the data pages, rather than recording each individual row deletion the way DELETE does.

Q7. What is an index? Clustered vs non-clustered ***

An index is an auxiliary data structure — almost always a B-tree — that lets the engine locate matching rows without scanning the whole table, at the cost of extra storage and slower writes (every INSERT/UPDATE/DELETE must also update the index).

Clustered indexNon-clustered index
StorageDetermines the physical on-disk order of the table's rowsA separate structure holding the indexed column(s) plus a pointer back to the row
Count per tableExactly one (the table data is the index)Many allowed
DefaultOften the primary key, by defaultAnything explicitly created with CREATE INDEX

Common follow-up: "why is a lookup via a non-clustered index sometimes still slow?" — unless the index covers the query (contains every column the query needs), matching it still triggers a second lookup back to the actual table row to fetch the remaining columns — this "key lookup" step is exactly what a covering index is designed to eliminate.

Q8. ACID properties ***
PropertyGuarantee
AtomicityA transaction is all-or-nothing — if any part fails, the whole thing rolls back
ConsistencyA transaction moves the database from one valid state to another, never violating constraints
IsolationConcurrent transactions don't observe each other's uncommitted, in-progress changes (degree governed by isolation level)
DurabilityOnce committed, changes survive even a crash immediately afterward

Common follow-up: "what actually enforces Isolation?" — isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable), which trade off strictness against concurrency. Lower levels allow anomalies like dirty reads or non-repeatable reads in exchange for less locking overhead and higher throughput.

Q9. View vs table vs materialized view **

A table stores actual data on disk. A view stores no data of its own — it's a saved, named SELECT that re-runs live against the underlying tables every time it's queried, useful for simplifying/reusing a complex query or restricting which columns a user can see. A materialized view behaves like a view but its result set is physically stored, so reads are much faster — the tradeoff is that it goes stale and needs an explicit REFRESH, since it doesn't automatically re-run on access.

Q10. Stored procedure vs function **

A stored procedure is a precompiled, named block of SQL/procedural logic invoked with CALL/EXEC. It can perform side effects (INSERT/UPDATE/DELETE, transaction control), doesn't have to return anything, and generally can't be used inline inside a SELECT.

A function must return a value, is typically restricted from having side effects, and can be called inline as part of a larger expression — SELECT id, calculate_tax(amount) FROM orders — which is exactly what a procedure can't do.

Q11. Types of JOINs — quick overview ***

RIGHT (OUTER) JOINMirror of LEFT — all rows from the right table
FULL (OUTER) JOINAll rows from both sides; NULLs wherever there's no match
CROSS JOINEvery row from the left paired with every row from the right — no ON condition (Cartesian product)
SELF JOINNot a distinct join type — any of the above, applied to a table joined against itself

Q12. Window functions vs GROUP BY ***

GROUP BY collapses multiple rows into one row per group — the individual row detail is gone, only the aggregated value remains. A window function computes an aggregate, ranking, or offset-based value per row while keeping every row in the output, computed "over a window" of related rows (defined by PARTITION BY) rather than collapsing them.

-- GROUP BY: one row per department, detail lost
SELECT dept_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY dept_id;

-- Window function: every employee row kept, each annotated with their dept's average
SELECT emp_id, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg_salary
FROM employees;

This is the primer — the Window Functions section below works through five full scenarios.

2. Window Functions

Q13. Calculate the moving average of sales for the past 3 months ***

Schema: sales(sale_date, amount).

WITH monthly_sales AS (
  SELECT
    DATE_TRUNC('month', sale_date) AS month,
    SUM(amount) AS total_sales
  FROM sales
  GROUP BY DATE_TRUNC('month', sale_date)
)
SELECT
  month,
  total_sales,
  AVG(total_sales) OVER (
    ORDER BY month
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
  ) AS moving_avg_3mo
FROM monthly_sales
ORDER BY month;

The CTE first collapses raw sales into one row per calendar month. The window frame ROWS BETWEEN 2 PRECEDING AND CURRENT ROW then includes the current row plus the two before it — a trailing 3-month window that slides forward and recalculates at every row as ORDER BY month advances.

Dialect note: DATE_TRUNC is Postgres; MySQL's equivalent is DATE_FORMAT(sale_date, '%Y-%m-01').

Q14. Assign a dense rank to employees based on their salary ***

Schema: employees(emp_id, name, department, salary).

SELECT
  emp_id,
  name,
  department,
  salary,
  DENSE_RANK() OVER (ORDER BY salary DESC) AS salary_rank
FROM employees;

DENSE_RANK() is the one to reach for whenever ties should share a rank without leaving a gap afterward — two employees tied for the top salary both get rank 1, and the next distinct salary gets rank 2 (not 3). RANK() would instead skip to 3, and ROW_NUMBER() would arbitrarily split the tie into 1 and 2.

Q15. Retrieve the first and last order date for each customer **

Schema: orders(order_id, customer_id, order_date).

SELECT DISTINCT
  customer_id,
  MIN(order_date) OVER (PARTITION BY customer_id) AS first_order_date,
  MAX(order_date) OVER (PARTITION BY customer_id) AS last_order_date
FROM orders;

For just this result, a plain GROUP BY customer_id with MIN/MAX would be simpler and is the more natural tool. The window-function version earns its keep when you need the first/last date sitting alongside other per-order detail columns in the same row (e.g., every individual order annotated with that customer's overall first/last date) — something a collapsing GROUP BY can't give you without a self-join back to the raw rows.

Q16. Find the Nth highest salary for each department using window functions ***

Schema: employees(emp_id, dept_id, salary).

WITH ranked_salaries AS (
  SELECT
    dept_id,
    emp_id,
    salary,
    DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employees
)
SELECT dept_id, emp_id, salary
FROM ranked_salaries
WHERE rnk = 3;  -- swap 3 for any N

PARTITION BY dept_id restarts the ranking from scratch inside each department, so "rank 3" always means the third-highest salary within that specific department, not company-wide. DENSE_RANK is deliberately used over ROW_NUMBER here — if two employees in the same department are tied for 2nd place, both should count as rank 2, and neither should be silently excluded or double-counted by an arbitrary tie-break.

Q17. Determine the percentage of total sales contributed by each employee **

Schema: sales(emp_id, amount).

SELECT
  emp_id,
  SUM(amount) AS employee_sales,
  SUM(amount) * 100.0 / SUM(SUM(amount)) OVER () AS pct_of_total
FROM sales
GROUP BY emp_id;

This mixes a regular aggregate with a window function on top of it: the inner SUM(amount) rolls sales up per employee (the normal GROUP BY aggregate); the outer SUM(SUM(amount)) OVER () is a window function with an empty OVER () — no PARTITION BY — so it sums across every group to get the grand total, letting each row divide its own total against the whole in a single pass, with no self-join or extra subquery needed.

3. Common Table Expressions (CTEs)

Q18. Use a CTE to split a full name into first and last names **

Schema: customers(customer_id, full_name).

WITH split_names AS (
  SELECT
    customer_id,
    full_name,
    SPLIT_PART(full_name, ' ', 1) AS first_name,
    SPLIT_PART(full_name, ' ', 2) AS last_name
  FROM customers
)
SELECT * FROM split_names;

Dialect note: SPLIT_PART is Postgres. MySQL has no direct equivalent for the "Nth part" case, but a two-part first/last split works with SUBSTRING_INDEX: SUBSTRING_INDEX(full_name, ' ', 1) for the first name, SUBSTRING_INDEX(full_name, ' ', -1) for the last.

Q19. Write a CTE to find the longest consecutive streak of sales for an employee **

Schema: sales(emp_id, sale_date). This is the classic "islands and gaps" problem.

WITH sales_days AS (
  SELECT DISTINCT emp_id, sale_date
  FROM sales
),
numbered AS (
  SELECT
    emp_id,
    sale_date,
    ROW_NUMBER() OVER (PARTITION BY emp_id ORDER BY sale_date) AS rn
  FROM sales_days
),
grouped AS (
  SELECT
    emp_id,
    sale_date,
    sale_date - (rn * INTERVAL '1 day') AS streak_group
  FROM numbered
)
SELECT
  emp_id,
  COUNT(*) AS streak_length,
  MIN(sale_date) AS streak_start,
  MAX(sale_date) AS streak_end
FROM grouped
GROUP BY emp_id, streak_group
ORDER BY emp_id, streak_length DESC;

The trick: for a run of consecutive calendar dates, sale_date minus row_number is a constant — every date in the run shifts down by exactly one more day than the row number increases, so they all land on the same computed value. Any gap in sales breaks that pattern and starts a new constant, which means grouping by that computed value naturally clusters each unbroken streak together, ready to COUNT().

Common follow-up: "how do I get only the single longest streak per employee, not every streak?" — wrap this whole query in one more CTE and add ROW_NUMBER() OVER (PARTITION BY emp_id ORDER BY streak_length DESC) = 1 in an outer WHERE, the same top-1-per-group pattern used in Q16.

Q20. Generate Fibonacci numbers up to a given limit using a recursive CTE ** 
WITH RECURSIVE fibonacci (n, current_val, next_val) AS (
  SELECT 1, 0, 1                        -- anchor: seeds the sequence
  UNION ALL
  SELECT n + 1, next_val, current_val + next_val
  FROM fibonacci
  WHERE current_val < 100              -- the "given limit"
)
SELECT n, current_val AS fibonacci_number
FROM fibonacci
ORDER BY n;

Every recursive CTE has the same two-part shape: an anchor member (the base case, run once) UNION ALL a recursive member that references the CTE's own name — each pass runs against the previous pass's output, not the original table, and the engine keeps iterating until a run produces zero rows (here, once current_val reaches the limit and the WHERE stops matching). Each iteration shifts the (current, next) pair forward by exactly one Fibonacci step.

Dialect note: Postgres and MySQL 8+ both use WITH RECURSIVE; SQL Server just uses WITH without the keyword, but the anchor/recursive-member structure is identical everywhere.

Q21. Use a CTE to identify duplicate records in a table ***

Schema: customers(customer_id, email).

WITH duplicates AS (
  SELECT
    customer_id,
    email,
    ROW_NUMBER() OVER (PARTITION BY email ORDER BY customer_id) AS rn,
    COUNT(*) OVER (PARTITION BY email) AS occurrences
  FROM customers
)
SELECT customer_id, email, occurrences
FROM duplicates
WHERE occurrences > 1
ORDER BY email, customer_id;

COUNT(*) OVER (PARTITION BY email) tags every row with how many rows share its email, without collapsing anything — so rows belonging to a duplicate group can still be filtered individually with a plain WHERE, which a GROUP BY + HAVING version couldn't do without losing the individual customer_ids.

Common follow-up: "now delete the duplicates, keeping one copy" — swap the filter to WHERE rn > 1 instead: that isolates every row except the first (by whatever ORDER BY you chose) in each duplicate group, which is exactly the set you'd feed into a DELETE.

Q22. Find the total sales for each category and filter categories with sales greater than a threshold using a CTE **

Schema: sales(category_id, amount).

WITH category_sales AS (
  SELECT
    category_id,
    SUM(amount) AS total_sales
  FROM sales
  GROUP BY category_id
)
SELECT category_id, total_sales
FROM category_sales
WHERE total_sales > 100000;

Common follow-up: "why not just use HAVING SUM(amount) > 100000 directly and skip the CTE?" — for exactly this query, HAVING is more concise and does the same job in one step. A CTE starts earning its keep once the aggregated result needs to be joined against other tables, referenced more than once, or filtered by a second, unrelated condition afterward — situations where naming the intermediate result makes the query easier to read and reuse.

4. Joins (Inner, Outer, Cross, Self)

Q23. Retrieve customers who have placed orders and those who have not (Full Outer Join) ***

Schema: customers(customer_id, name), orders(order_id, customer_id, order_date).

SELECT
  c.customer_id,
  c.name,
  o.order_id,
  o.order_date
FROM customers c
FULL OUTER JOIN orders o
  ON c.customer_id = o.customer_id;

A FULL OUTER JOIN keeps every row from both sides — customers with orders get matched normally, customers with zero orders appear with NULL order columns, and (if it can happen in this schema) any orphaned order with no matching customer would also still appear, with NULL customer columns.

Dialect note: MySQL has no native FULL OUTER JOIN. It's emulated as LEFT JOIN ... UNION ... RIGHT JOIN ... (or a LEFT JOIN unioned with a RIGHT JOIN ... WHERE left.key IS NULL to avoid duplicating the matched rows).

Q24. Find employees working on multiple projects using a self join **

Schema: employee_projects(emp_id, project_id).

SELECT DISTINCT
  a1.emp_id
FROM employee_projects a1
JOIN employee_projects a2
  ON a1.emp_id = a2.emp_id
 AND a1.project_id <> a2.project_id;

Joining the assignment table to itself on the same employee but a different project produces a row only when that employee has at least two distinct project assignments — matching (project A, project B) and (project B, project A) as two separate pairings, which is why DISTINCT is needed to collapse them back down to one row per employee.

Worth noting: a plain aggregate is actually the more natural tool for this specific question — SELECT emp_id FROM employee_projects GROUP BY emp_id HAVING COUNT(DISTINCT project_id) > 1 gets the same answer without a join at all. The self join is shown here because the question specifically asks for one; self joins earn their keep more clearly in Q27, where you need to pull back a manager's *name*, not just detect a relationship.

Q25. Match orders with customers, and display unmatched orders too (Left Join) *** 
-- all orders, matched customer info where it exists
SELECT
  o.order_id,
  o.order_date,
  c.customer_id,
  c.name
FROM orders o
LEFT JOIN customers c
  ON o.customer_id = c.customer_id;

-- isolate just the unmatched ("orphaned") orders
SELECT o.*
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;

LEFT JOIN keeps every row from orders (the "left" table) regardless of whether a match exists in customers; when it doesn't, every selected customer column comes back NULL. That's what makes WHERE c.customer_id IS NULL a reliable way to isolate exactly the unmatched rows — it's only NULL when the join found nothing to attach.

Q26. Generate a product pair list, excluding pairs of identical products (Cross Join with condition) ** 
SELECT
  p1.product_id AS product_1,
  p2.product_id AS product_2
FROM products p1
CROSS JOIN products p2
WHERE p1.product_id <> p2.product_id;

A bare CROSS JOIN produces every possible combination — N × N rows, including a product paired with itself — since it has no ON condition at all. The WHERE clause filters those self-pairs out afterward.

Common follow-up: "this still returns both (A, B) and (B, A) — how do I get only unique unordered pairs?" — swap the condition to p1.product_id < p2.product_id. That one change does two things at once: it still excludes self-pairs (a value is never less than itself), and it also keeps only one direction of each pair instead of both mirrored copies.

Q27. Retrieve employees and their managers using a self join ***

Schema: employees(emp_id, name, manager_id) — manager_id points back to another row's emp_id.

SELECT
  e.emp_id,
  e.name AS employee_name,
  m.name AS manager_name
FROM employees e
LEFT JOIN employees m
  ON e.manager_id = m.emp_id;

The classic self join for adjacency-list hierarchies: the same table plays two roles at once — e is "the employee row," m is "that employee's manager," found by matching e.manager_id back to m.emp_id in a second copy of the same table. LEFT JOIN (not INNER) matters here specifically so that whoever has no manager — the CEO, manager_id IS NULL — still shows up in the results instead of being silently dropped.

5. Subqueries

Q28. Find customers whose total order amount is greater than the average order amount *** 
SELECT
  customer_id,
  SUM(amount) AS total_order_amount
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > (
  SELECT AVG(amount) FROM orders
);

This reads "the average order amount" as the average of every individual order (a single number computed once by the subquery), compared against each customer's summed total. That's a genuinely ambiguous phrase in real interviews, though — the other common reading is "the average of customers' totals," which changes the subquery to SELECT AVG(customer_total) FROM (SELECT SUM(amount) AS customer_total FROM orders GROUP BY customer_id) t. Worth stating out loud which interpretation you're using before writing the query.

The subquery here is uncorrelated — it doesn't reference anything from the outer query, so the engine only needs to evaluate it once and reuse the result for every group's comparison.

Q29. Retrieve employees who earn the lowest salary in their department *** 
SELECT
  e.emp_id,
  e.name,
  e.dept_id,
  e.salary
FROM employees e
WHERE e.salary = (
  SELECT MIN(e2.salary)
  FROM employees e2
  WHERE e2.dept_id = e.dept_id
);

This one is correlated — the inner subquery references e.dept_id from the outer row, so conceptually it re-runs once per outer row, recomputing "the minimum salary in this employee's specific department" each time. Comparing with = against that per-row minimum naturally handles ties correctly: if two employees in the same department are both at the department floor, both are returned, unlike an ORDER BY salary LIMIT 1 approach which would arbitrarily cut one of them.

Q30. Identify products that have been ordered more than 10 times using a subquery ** 
-- direct, using HAVING — the natural way to write this alone
SELECT product_id
FROM order_items
GROUP BY product_id
HAVING COUNT(*) > 10;

-- as an explicit subquery/derived table
SELECT product_id
FROM (
  SELECT product_id, COUNT(*) AS times_ordered
  FROM order_items
  GROUP BY product_id
) counts
WHERE times_ordered > 10;

Both return identical results. The plain HAVING form is simpler whenever nothing else needs to happen — the derived-table form becomes necessary the moment that count needs to be joined back to a products table for names, or combined with another filter that itself needs the alias times_ordered to already exist.

Q31. Find regions where the maximum sales are below a given threshold ** 
SELECT region_id, max_sale
FROM (
  SELECT region_id, MAX(amount) AS max_sale
  FROM sales
  GROUP BY region_id
) region_max
WHERE max_sale < 5000;

Same shape as Q30: the inner query computes the per-region ceiling, the outer query filters on the now-materialized alias. The equivalent one-step version, GROUP BY region_id HAVING MAX(amount) < 5000, is just as correct and more common in practice — this derived-table form is worth knowing because it's what you fall back to once the filtered aggregate needs to be joined against something else.

6. Aggregate Functions

Q32. Calculate the median salary for each department ** 
SELECT
  dept_id,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median_salary
FROM employees
GROUP BY dept_id;

PERCENTILE_CONT(0.5) asks for the value at the 50th percentile — the median, by definition — interpolating between the two middle values when a group has an even count. It's supported by Postgres, Oracle, and SQL Server.

Common pitfall: assuming MySQL has the same function — it doesn't (no native MEDIAN/PERCENTILE_CONT before very recent versions). The manual fallback uses ROW_NUMBER()/COUNT() per department to find the middle row (or average the two middle rows for an even count) — a good one to know exists even if you don't memorize the full syntax, since interviewers often ask specifically because it's a well-known MySQL gap.

Q33. Find the total sales for each month and rank them in descending order ** 
SELECT
  DATE_TRUNC('month', sale_date) AS month,
  SUM(amount) AS total_sales,
  RANK() OVER (ORDER BY SUM(amount) DESC) AS sales_rank
FROM sales
GROUP BY DATE_TRUNC('month', sale_date)
ORDER BY sales_rank;

This is the common combo point between the two topics: GROUP BY collapses rows down to one per month first, and only then does the window function RANK() OVER (...) run on top of that already-aggregated result — window functions are logically evaluated after grouping, so they can freely reference the grouped/aggregated values like SUM(amount) directly.

Q34. Count the number of distinct customers for each product ** 
SELECT
  oi.product_id,
  COUNT(DISTINCT o.customer_id) AS distinct_customers
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
GROUP BY oi.product_id;

COUNT(DISTINCT ...) matters here specifically because a single customer can buy the same product across multiple separate orders — without DISTINCT, that customer would be counted once per order instead of once per product, inflating the number.

Q35. Retrieve the top 5 regions by total sales *** 
SELECT
  region_id,
  SUM(amount) AS total_sales
FROM sales
GROUP BY region_id
ORDER BY total_sales DESC
LIMIT 5;

Dialect note: LIMIT 5 is MySQL/Postgres syntax. SQL Server uses SELECT TOP 5 ... (goes in the SELECT clause instead, before the columns); the ANSI-standard form, supported by Oracle and others, is FETCH FIRST 5 ROWS ONLY after the ORDER BY.

Q36. Calculate the average order value for each customer ** 
SELECT
  customer_id,
  AVG(amount) AS avg_order_value
FROM orders
GROUP BY customer_id;

Straightforward GROUP BY + AVG. Worth distinguishing in an interview from a lifetime-value style metric: this is the average size of a single order, not a customer's total spend (SUM) or their order frequency (COUNT) — three different, commonly conflated numbers that are all one aggregate function apart from each other on the exact same table.

7. Indexing & Performance

Q37. Write a query to find duplicate values in an indexed column ** 
SELECT
  email,
  COUNT(*) AS occurrences
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;

The query itself is the same shape as Q21 — the "indexed column" part is about why it's fast: a B-tree index on email already stores values in sorted order, so the engine can walk it sequentially to group matching values instead of sorting the entire table from scratch in memory to perform the GROUP BY.

Q38. Analyze the impact of adding a composite index on query performance *** 
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 42 AND order_date > '2025-01-01';

CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);

EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 42 AND order_date > '2025-01-01';

Methodology: run EXPLAIN ANALYZE (Postgres/MySQL) before and after adding the index, and compare the plan and the actual timing — specifically, whether the step changes from a Seq Scan/full table scan to an Index Scan or Index Only Scan, and whether the reported execution time and rows-examined count both drop.

A composite (multi-column) index is only useful when a query's filter/sort columns match its leftmost prefix, in order — an index on (customer_id, order_date) speeds up a filter on customer_id alone or on both columns together, but does nothing for a query that filters on order_date alone.

Common follow-up: "so is adding an index always a win?" — no. Every index speeds up matching reads but adds overhead to every write (the index itself must be kept up to date) and consumes extra disk space — it's a read/write tradeoff, not a free upgrade, which is exactly why this question asks you to measure the impact rather than assume it.

Q39. Identify columns with high cardinality that could benefit from indexing ** 
SELECT
  COUNT(DISTINCT customer_id) AS distinct_customers,
  COUNT(*) AS total_rows,
  COUNT(DISTINCT customer_id) * 1.0 / COUNT(*) AS cardinality_ratio
FROM orders;

Cardinality = how many distinct values a column has relative to its total row count. A ratio close to 1.0 (e.g., an email, an order ID, a UUID) is high cardinality — an index lookup can narrow the result down to very few rows, which is exactly what makes an index worth having. A ratio close to 0 (e.g., a boolean flag, or a status column with 3–4 possible values) is low cardinality — a B-tree index there often isn't selective enough for the optimizer to prefer over a full scan, since matching any one value still means fetching a large fraction of the table.

Q40. Compare query execution times before and after adding a clustered index ** 
-- before: baseline timing
EXPLAIN ANALYZE
SELECT * FROM orders WHERE order_id BETWEEN 1000 AND 2000;

-- add a clustered index (SQL Server syntax — a table's PK is clustered by default in many engines)
CREATE CLUSTERED INDEX idx_orders_id ON orders (order_id);

-- after: re-run the identical query and compare
EXPLAIN ANALYZE
SELECT * FROM orders WHERE order_id BETWEEN 1000 AND 2000;

See Q7 for what a clustered index is; the relevant point for this question is why range scans specifically benefit so much: a clustered index physically reorders the table's rows on disk to match the index key, so a BETWEEN/range condition reads one contiguous block of storage instead of jumping around the table to fetch each matching row individually — which is what a non-clustered index lookup still has to do afterward, unless it happens to be a covering index.

Q41. Write a query that avoids the use of an index to test performance differences * 
-- wrapping an indexed column in a function defeats a standard B-tree index,
-- forcing a full scan instead:
SELECT * FROM orders WHERE UPPER(customer_email) = 'JANE@EXAMPLE.COM';

-- a leading wildcard also defeats a standard B-tree index:
SELECT * FROM orders WHERE customer_email LIKE '%@example.com';

-- or, explicitly (MySQL):
SELECT * FROM orders IGNORE INDEX (idx_customer_email)
WHERE customer_email = 'jane@example.com';

These are exactly the patterns to avoid in production for the same reason they're useful here: transforming the column (UPPER(...)) or anchoring a LIKE pattern with a leading wildcard both prevent the optimizer from using a standard index range scan, giving a reliable, deliberate full-scan baseline to compare against. Postgres also supports a blunter, connection-level override for testing — SET enable_seqscan = off/on — without touching the query text at all.

8. Advanced SQL

Q42. Stored procedures in detail ***

A stored procedure is a named program stored and executed inside the database. It can accept input/output parameters, run multiple SQL statements, use variables and control flow, modify data, and centralize a transaction-sensitive operation close to the data.

For example, transferring money requires the debit and credit to succeed as one unit. The procedure below validates the amount, locks both account rows against concurrent updates, checks the balance, and performs both updates.

CREATE OR REPLACE PROCEDURE transfer_funds(
  p_from_account bigint,
  p_to_account   bigint,
  p_amount       numeric(12, 2)
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_balance numeric(12, 2);
BEGIN
  IF p_amount <= 0 THEN
    RAISE EXCEPTION 'Transfer amount must be positive';
  END IF;

  -- Lock in a stable order to reduce deadlock risk.
  PERFORM 1
  FROM accounts
  WHERE account_id IN (p_from_account, p_to_account)
  ORDER BY account_id
  FOR UPDATE;

  SELECT balance INTO v_balance
  FROM accounts
  WHERE account_id = p_from_account;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Source account % does not exist', p_from_account;
  END IF;

  IF v_balance < p_amount THEN
    RAISE EXCEPTION 'Insufficient balance';
  END IF;

  UPDATE accounts
  SET balance = balance - p_amount
  WHERE account_id = p_from_account;

  UPDATE accounts
  SET balance = balance + p_amount
  WHERE account_id = p_to_account;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Destination account % does not exist', p_to_account;
  END IF;
END;
$$;

BEGIN;
CALL transfer_funds(101, 202, 500.00);
COMMIT;

Procedure vs function

ProcedureFunction
Called with CALLUsed in expressions such as SELECT calculate_tax(100)
Designed for an operation or workflowDesigned to compute and return a value or result set
Can support transaction control when called outside an explicit transaction, depending on the databaseNormally runs inside the caller's transaction and cannot commit independently
May expose values through INOUT/OUT parametersHas a declared return type

When to use: use a procedure for multi-step data operations that need one consistent implementation, bulk data maintenance, administrative jobs, or logic shared by several clients. Keep presentation rules and rapidly changing business workflows in the application layer. Procedures add deployment, versioning, testing, and database portability costs.

Security: grant applications permission to call the procedure instead of broad direct table-write access when appropriate. Parameterized procedure calls still matter; constructing a CALL string from user input can still create SQL injection.

Dialect note: syntax and transaction behavior differ significantly. SQL Server uses CREATE PROCEDURE ... AS and EXEC; MySQL uses DELIMITER while defining multi-statement procedures; the example above is PostgreSQL.

Q43. Triggers in detail ***

A trigger is database code that runs automatically when a specified event occurs. A trigger can run BEFORE, AFTER, or—in supported cases—INSTEAD OF an INSERT, UPDATE, DELETE, or other database event.

ChoiceMeaningTypical use
BEFORERuns before the row is written and can validate or modify NEWNormalize data, reject invalid values
AFTERRuns after the change succeedsAudit history, downstream bookkeeping
INSTEAD OFReplaces the original operation, commonly on a viewMake a complex view writable
FOR EACH ROWRuns once for every affected rowPer-record validation or audit data
FOR EACH STATEMENTRuns once for the entire statementStatement-level logging or coordination

This PostgreSQL example records every salary change. OLD contains the row before the update and NEW contains the row after it.

CREATE TABLE employee_salary_audit (
  audit_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  employee_id bigint NOT NULL,
  old_salary  numeric(12, 2) NOT NULL,
  new_salary  numeric(12, 2) NOT NULL,
  changed_by  text NOT NULL,
  changed_at  timestamptz NOT NULL DEFAULT now()
);

CREATE OR REPLACE FUNCTION audit_salary_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  INSERT INTO employee_salary_audit (
    employee_id, old_salary, new_salary, changed_by
  )
  VALUES (
    OLD.employee_id, OLD.salary, NEW.salary, current_user
  );

  RETURN NEW;
END;
$$;

CREATE TRIGGER employee_salary_audit_trigger
AFTER UPDATE OF salary ON employees
FOR EACH ROW
WHEN (OLD.salary IS DISTINCT FROM NEW.salary)
EXECUTE FUNCTION audit_salary_change();

UPDATE employees
SET salary = salary * 1.05
WHERE department_id = 10;

The final update fires the trigger once per changed employee. The WHEN condition prevents audit rows when an update mentions salary but does not actually change its value. IS DISTINCT FROM is NULL-safe, unlike an ordinary <> comparison.

Good uses: audit trails, enforcing a rule across every client, maintaining derived data that must stay transactionally consistent, and making views writable. Prefer declarative constraints such as NOT NULL, CHECK, UNIQUE, and foreign keys when they can express the rule more clearly.

Pitfalls: triggers are implicit side effects. They can surprise developers, slow bulk operations, recursively activate other triggers, and create deadlocks if they touch tables in an inconsistent order. Document them, keep them small, monitor their cost, and test multi-row statements—not only single-row updates.

Dialect note: PostgreSQL creates a trigger function separately. MySQL places the trigger body directly in CREATE TRIGGER. SQL Server triggers normally operate once per statement and use the inserted and deleted pseudo-tables, which may contain many rows.

Q44. How to read EXPLAIN ANALYZE ***

EXPLAIN shows the optimizer's estimated plan without running the query. EXPLAIN ANALYZE executes the query and adds actual time, rows, and loop counts, letting you compare the optimizer's prediction with reality.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT c.customer_id, c.name, SUM(o.total_amount) AS revenue
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE o.created_at >= DATE '2026-01-01'
GROUP BY c.customer_id, c.name
ORDER BY revenue DESC
LIMIT 10;

Read a PostgreSQL plan from the bottom upward: child nodes produce rows for their parent. A simplified plan might be:

Limit  (actual time=48.1..48.2 rows=10 loops=1)
  -> Sort  (actual time=48.1..48.1 rows=10 loops=1)
       Sort Key: (sum(o.total_amount)) DESC
       Sort Method: top-N heapsort  Memory: 27kB
       -> HashAggregate (actual time=42.0..46.7 rows=8100 loops=1)
            -> Hash Join (actual time=3.2..31.4 rows=125000 loops=1)
                 -> Seq Scan on orders o
                      Filter: created_at >= '2026-01-01'
                      Rows Removed by Filter: 875000
                 -> Hash
                      -> Seq Scan on customers c
Plan fieldHow to interpret it
cost=start..totalOptimizer units used to compare plans; they are not milliseconds
rows before executionEstimated rows produced by the node
actual time=a..bTime to first row and time to finish one loop, in milliseconds
actual rowsRows produced per loop; compare with estimated rows
loopsHow many times the node ran; approximate total work with time or rows multiplied by loops
Buffers: shared hitPages served from database cache
Buffers: shared readPages that required reads from storage
Rows Removed by FilterRows scanned and discarded; a large number can reveal an unselective scan

What to investigate

  1. Estimate errors: if estimated rows are 10 but actual rows are 100,000, update statistics and inspect skew or correlated columns. Bad estimates often cause the wrong join type or join order.
  2. Expensive scans: a sequential scan is not automatically bad. It is efficient when much of a table is needed. For a selective predicate over a large table, consider an appropriate index such as CREATE INDEX ON orders (created_at, customer_id) INCLUDE (total_amount).
  3. Repeated work: a fast node with a very high loops count can dominate the query, especially inside a nested-loop join.
  4. Disk spills: external merge sorts or multi-batch hashes indicate insufficient memory for that operation or an unnecessarily large intermediate result.
  5. Wide or unnecessary rows: returning fewer columns and filtering earlier can reduce I/O, memory, sorting, and network cost.

Safe workflow: capture the exact slow query and representative parameters, run it against production-like data, use EXPLAIN (ANALYZE, BUFFERS), change one thing, rerun the same plan, and compare execution time, row estimates, buffers, and result correctness. Warm-cache and cold-cache timings can differ.

Warning: ANALYZE really executes the statement. For UPDATE/DELETE/INSERT, use a safe environment or wrap the analysis in BEGIN; ... ROLLBACK; while accounting for trigger and locking side effects. On a busy production database, even analyzing a SELECT can be expensive.

Q45. LATERAL JOIN in detail ***

A LATERAL subquery in the FROM clause can reference columns from tables that appear before it. Conceptually, the database evaluates the right-side subquery for each left-side row. This is useful for a correlated query that must return columns or multiple rows.

Example: latest three orders for every customer

SELECT
  c.customer_id,
  c.name,
  recent.order_id,
  recent.created_at,
  recent.total_amount
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.order_id, o.created_at, o.total_amount
  FROM orders o
  WHERE o.customer_id = c.customer_id
  ORDER BY o.created_at DESC
  LIMIT 3
) AS recent ON true
ORDER BY c.customer_id, recent.created_at DESC;

The subquery can see c.customer_id because it is lateral. LEFT JOIN LATERAL keeps customers with no orders and fills the recent columns with NULL. Using JOIN LATERAL or CROSS JOIN LATERAL would omit a customer when the subquery returns no row.

An index matching the correlation and ordering makes the top-N lookup efficient:

CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at DESC)
INCLUDE (order_id, total_amount);

Example: compute and reuse a value for each row

SELECT p.product_id, p.name, price.final_price
FROM products p
CROSS JOIN LATERAL (
  SELECT ROUND(p.list_price * (1 - p.discount_percent / 100.0), 2)
         AS final_price
) AS price
WHERE price.final_price < 1000;

Compared with a correlated scalar subquery: a scalar subquery must return at most one row and usually one column. A lateral subquery can return several columns and several rows, can contain ORDER BY ... LIMIT, and acts like a table in the rest of the query.

Compared with a window function: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) is another top-N-per-group solution. The window approach often processes all matching orders before filtering. With a good index and a small N, the lateral approach can perform a short index lookup per customer. Measure both on realistic data.

Dialect note: PostgreSQL uses LATERAL. SQL Server's close equivalents are CROSS APPLY and OUTER APPLY. Modern MySQL supports lateral derived tables, but version and syntax support should be checked.

Q46. CROSS JOIN in detail ***

A CROSS JOIN returns the Cartesian product: every row from the first input paired with every row from the second. If the left table has m rows and the right table has n rows, the result has m × n rows.

Example: generate every product-size combination

SELECT p.product_id, p.name, s.size_code
FROM products p
CROSS JOIN sizes s
ORDER BY p.product_id, s.size_code;

With 100 products and 5 sizes, this intentionally generates 500 combinations. This is useful for building variant matrices, test data, schedules, grids, and every possible combination of small dimension tables.

Example: create a complete date-by-store reporting grid

WITH calendar AS (
  SELECT day::date
  FROM generate_series(
    DATE '2026-10-01',
    DATE '2026-10-07',
    INTERVAL '1 day'
  ) AS day
)
SELECT
  s.store_id,
  c.day,
  COALESCE(SUM(sa.amount), 0) AS daily_sales
FROM stores s
CROSS JOIN calendar c
LEFT JOIN sales sa
  ON sa.store_id = s.store_id
 AND sa.sale_date >= c.day
 AND sa.sale_date < c.day + INTERVAL '1 day'
GROUP BY s.store_id, c.day
ORDER BY s.store_id, c.day;

The cross join first creates a row for every store and every date. The left join then attaches matching sales, so dates with no sale remain present with a total of zero. A normal aggregation over sales alone could not produce missing dates because no source row exists for them.

CROSS JOIN vs other joins

JoinConditionPurpose
CROSS JOINNo ON conditionProduce every combination intentionally
INNER JOINRequires a match conditionReturn related pairs only
CROSS JOIN LATERALRight input can reference the current left rowRun a correlated table expression per left row

Common accident: forgetting a join condition can create an unintended Cartesian product. Joining 1 million orders to 100,000 customers without the intended relationship attempts to produce 100 billion rows before later operations. Use explicit JOIN ... ON ... for relationships and reserve CROSS JOIN for deliberate combinations.

Filter behavior: FROM a CROSS JOIN b WHERE a.key = b.key is logically equivalent to FROM a INNER JOIN b ON a.key = b.key, and optimizers usually produce the same plan. The explicit inner join communicates intent more clearly.
