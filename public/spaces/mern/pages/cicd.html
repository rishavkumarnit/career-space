CI/CD Interview Questions

Pipelines, deployment strategies, testing, security, and production delivery for MERN applications.

Q1. What is the difference between continuous integration, continuous delivery, and continuous deployment?

Continuous integration (CI) means frequently merging small changes into a shared branch and automatically building and testing them. Continuous delivery keeps every successful change ready for production, but a human may approve the release. Continuous deployment goes one step further and automatically releases every change that passes the pipeline.

Q2. What stages would you include in a CI/CD pipeline for a MERN application?

A mature pipeline takes one reviewed commit through verification, packaging, release, deployment, and production validation. The exact tools vary, but the responsibilities below should be explicit.

Fail-fast ordering: put cheap checks before expensive tests and deployments. Independent lint, unit-test, and security jobs can run in parallel after dependency setup, while packaging must wait for required gates. A failed required stage stops promotion.

Build once, promote many: build one immutable artifact and promote its exact digest through staging and production. Rebuilding per environment can silently introduce different dependencies or content. Environment-specific URLs, credentials, and feature settings should be supplied at deployment/runtime rather than compiled into separate artifacts.

Database path: validate migrations in CI, run them with a dedicated controlled job, and use expand-and-contract changes: add compatible schema, deploy code that supports old and new versions, backfill, switch usage, then remove the old schema in a later release.

pull request
  -> install
  -> lint + typecheck + unit tests + security scans (parallel)
  -> integration/contract tests
  -> build image once
  -> publish image by commit SHA/digest
  -> deploy staging
  -> migrate + smoke/E2E tests
  -> production approval
  -> canary 5% -> 25% -> 100%
  -> observe SLOs
  -> finalize or automatically roll back
Q3. Why should a pipeline use npm ci instead of npm install?

npm ci installs the exact dependency tree recorded in package-lock.json, removes any existing node_modules, and fails when the manifest and lockfile disagree. This makes CI builds faster and reproducible. npm install may update the lockfile and is better suited to local dependency changes.

Q4. How should secrets and environment-specific configuration be handled?

Keep configuration outside the build artifact and store secrets in the CI platform's encrypted secret store or a dedicated secrets manager. Inject them only into the jobs and environments that need them, mask them in logs, restrict access with least privilege, rotate them regularly, and never commit .env files or credentials to Git.

Q5. What is the difference between blue-green and canary deployment?

Blue-green deployment maintains two complete environments. The new version is deployed to the idle environment and traffic switches to it at once, enabling a quick rollback. Canary deployment gradually sends a small percentage of live traffic to the new version and increases it while monitoring errors and performance, reducing the blast radius of a bad release.

Q6. How do you design a safe database migration for a zero-downtime release?

Use backward-compatible, incremental changes: add new fields or tables first, deploy code that can work with both schemas, backfill data separately, switch reads and writes, and remove the old schema only after every application instance has moved forward. Avoid coupling a destructive migration to application startup, and test both migration and recovery procedures before production.

Q7. What is the difference between an artifact and a deployment?

An artifact is the immutable output of a build, such as a versioned Docker image or compiled bundle. A deployment places a specific artifact into an environment with its runtime configuration. Building once and promoting the same artifact through staging and production avoids environment-specific rebuild differences.

Q8. How would you make a CI pipeline faster without reducing confidence?

Cache the package manager's download cache, run independent lint and test jobs in parallel, use affected-file detection in a monorepo, split long test suites, reuse immutable build artifacts, and run quick checks before expensive end-to-end tests. Cache keys should include the lockfile, and cached output must never replace required validation.

Q9. What checks should run after a production deployment?

Run smoke tests against critical endpoints and user journeys, verify health and readiness checks, and monitor error rate, latency, saturation, logs, and business metrics. Define thresholds and an observation window so the release can automatically stop or roll back when service-level indicators regress.

Q10. What makes a rollback strategy reliable?

A reliable rollback uses versioned immutable artifacts, automated deployment commands, backward-compatible database changes, and a clearly defined trigger. Teams should test rollback regularly. When data has already changed incompatibly, rolling the application back may be unsafe, so a forward fix or feature flag may be the better recovery path.

Docker Basics

Q11. What is Docker, and why is it used?

Docker packages an application and its dependencies into a portable container. The container runs consistently across a developer's machine, CI, staging, and production, which reduces environment-specific problems and makes applications easier to build, ship, and scale.

Q12. What is the difference between a Docker image and a container?

An image is an immutable template containing the application, runtime, libraries, and filesystem. A container is a running or stopped instance of that image. Many isolated containers can be created from the same image.

Q13. What is a Dockerfile?

A Dockerfile is a text file containing instructions used to build an image. Common instructions include FROM for the base image, WORKDIR for the working directory, COPY for files, RUN for build commands, EXPOSE for documenting a port, and CMD for the default startup command.

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
Q14. What is the difference between RUN, CMD, and ENTRYPOINT?

RUN executes while the image is being built and creates a new image layer. CMD provides the default command or arguments when a container starts and is easily overridden. ENTRYPOINT defines the container's main executable; command-line arguments are normally appended to it.

Q15. How does Docker port mapping work?

A container has its own network namespace, so an application port is not automatically accessible from the host. The command docker run -p 8080:3000 my-api maps host port 8080 to port 3000 inside the container. EXPOSE 3000 documents the intended container port but does not publish it.

Q16. What are Docker volumes, and when should you use them?

Volumes store data outside a container's writable layer, allowing it to survive container removal and be shared or backed up. They are useful for databases and other persistent data. Containers themselves should remain disposable; source code is often bind-mounted during local development but copied into the image for production.

Q17. What is Docker Compose?

Docker Compose defines and runs a multi-container application from a YAML file. A MERN development setup might declare an API, React client, and MongoDB service along with their ports, environment variables, volumes, and shared network. docker compose up starts the complete stack.

Q18. How is Docker commonly used in a CI/CD pipeline?

The pipeline builds an image from a reviewed Dockerfile, runs tests and security scans, tags the image with a unique version such as the commit SHA, and pushes it to a container registry. Deployment then pulls that exact image into each environment. Avoid relying only on the mutable latest tag because it does not identify a specific build.

Redis Basics

Q19. What is Redis, and where is it commonly used?

Redis is an in-memory data store that provides very fast reads and writes. It is commonly used for caching, session storage, rate limiting, counters, leaderboards, queues, and publish/subscribe messaging. Redis is often placed alongside a primary database rather than used as a replacement for it.

Q20. Why is Redis faster than a traditional database?

Redis primarily serves data from memory instead of reading it from disk for every request. Its commands operate on optimized data structures and most command execution is serialized, avoiding much of the locking overhead found in multithreaded systems. Network latency and inefficient command usage can still become bottlenecks.

Q21. Which data types does Redis support?

Common Redis types include strings for cached values and counters, hashes for object-like fields, lists for ordered queues, sets for unique values, and sorted sets for ranked data such as leaderboards. Redis also supports streams, bitmaps, geospatial indexes, and probabilistic structures.

Q22. How would you cache an API response using Redis?

Use the cache-aside pattern: first check Redis using a predictable key; on a hit, return the cached value. On a miss, query the database, store the serialized result in Redis with an expiration, and return it. When the underlying data changes, invalidate or update the related cache entry.

const key = `user:${userId}`;
const cached = await redis.get(key);

if (cached) return JSON.parse(cached);

const user = await User.findById(userId);
await redis.set(key, JSON.stringify(user), { EX: 300 });
return user;
Q23. What is TTL in Redis?

TTL means time to live: the remaining time before a key expires automatically. Expiration prevents stale cache entries from living forever and limits memory usage. A TTL should reflect how long the application can safely tolerate stale data; adding small random variation can prevent many popular keys from expiring simultaneously.

Q24. Does Redis persist data?

Redis can persist data using RDB snapshots, which save point-in-time copies, and AOF, which records write operations. RDB is compact and useful for backups, while AOF can provide lower data-loss windows. They can be used together, but persistence does not remove the need for replication and backups.

Q25. What happens when Redis runs out of memory?

Redis follows its configured maxmemory-policy. It may reject new writes or evict keys using policies based on recency, frequency, randomness, or expiration. For a cache, an eviction policy such as least-recently-used may be appropriate; for critical persistent data, unexpected eviction can cause data loss and should be avoided through sizing and monitoring.

Q26. How can Redis be used for rate limiting?

Create a key based on the client and time window, increment it for every request, and set an expiration. If the counter exceeds the allowed limit, reject the request. The increment and expiration must be applied atomically—using a transaction or Lua script—to avoid race conditions under concurrent traffic.

Q27. How does Redis work internally?

Redis is a networked data-structure server. Clients send commands through the Redis serialization protocol (RESP), Redis finds the key in its in-memory dictionary, runs an operation implemented for that data type, and returns a RESP response. Most commands complete without reading application data from disk.

Command lifecycle

  1. Connection: a client opens or reuses a TCP connection and may authenticate and select a logical database.
  2. Protocol parsing: Redis parses a RESP command such as SET user:42 "..." EX 300.
  3. Event loop: readiness-based I/O lets Redis manage many connections without assigning one application thread per client. Modern Redis can use I/O threads for network read/write work.
  4. Command execution: the main command path executes commands in a serialized order. A single command such as INCR is atomic relative to other commands, avoiding per-key application locks for that operation.
  5. Data-structure operation: Redis selects an internal encoding suited to the value's type and size, updates memory, expiry metadata, persistence buffers, and replication stream as configured.
  6. Response: the result is encoded as RESP and written back to the client.

“Single-threaded” is shorthand for the primary command execution model, not the entire server. Background threads/processes can handle tasks such as asynchronous memory freeing, persistence, and network I/O. A slow O(n) command, large Lua script, or huge key can still delay unrelated clients because it occupies the command execution path.

Keys, values, and internal encodings

The keyspace is essentially a hash table mapping binary-safe keys to Redis objects. The public types—string, hash, list, set, sorted set, stream—have optimized internal encodings. A small hash may use a compact list-like encoding and later convert to a hash table as it grows. A sorted set typically combines a dictionary for direct member lookup with a skip list for ordered range operations.

SET user:42:name "Rishav" EX 300
HSET user:42 name "Rishav" role "developer"
INCR api:requests:2026-10-15
ZADD leaderboard 980 "player-7"

# Common complexity expectations
GET key                 # O(1)
HGET hash field         # O(1) average
LPUSH queue value       # O(1)
ZRANGE board 0 9        # O(log N + M), M returned members

Expiration and eviction

Redis stores TTL metadata separately. It removes expired keys in two ways: passive expiration deletes a key when a client accesses it and finds it expired; active expiration periodically samples expiring keys and deletes overdue ones so untouched expired keys do not occupy memory indefinitely.

Expiration and eviction are different. Expiration follows a key's TTL. Eviction occurs when memory exceeds maxmemory; the configured policy may reject writes or select keys using all-keys/volatile LRU, LFU, random, or TTL-based rules. Redis uses sampled approximations for policies such as LRU rather than maintaining a costly exact global order.

Persistence happens alongside in-memory serving; Redis does not become a disk-first database. Forking and copy-on-write can temporarily increase memory pressure during a snapshot or AOF rewrite, especially under a write-heavy workload.

Replication and high availability

A primary streams its replication data to replicas. Initial synchronization can send a snapshot, followed by buffered incremental commands. Replication is normally asynchronous, so a newly acknowledged primary write may be lost if the primary fails before a replica receives it. Sentinel monitors non-clustered deployments and coordinates failover. Redis Cluster shards keys across 16,384 hash slots, assigns slot ranges to primaries, and redirects clients to the node owning a key.

Replication improves availability and read capacity; it is not a backup. Cluster improves capacity and failover but constrains multi-key operations to keys in the same hash slot unless hash tags such as {account}:balance deliberately colocate them.

Atomicity, transactions, and Lua

One Redis command is atomic on the command execution path. MULTI/EXEC queues commands and executes them without another client command interleaving, but it does not provide relational rollback if one queued command fails. WATCH adds optimistic concurrency by aborting when watched keys change. Lua scripts/functions execute atomically, so they are useful for a read-check-write sequence, but long scripts block other command execution.

-- Atomic fixed-window limiter
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return count

Cache-aside request example

request
  -> GET product:42
     -> hit: deserialize and return
     -> miss: query database
              -> SET product:42 <json> EX 300
              -> return result

update
  -> commit database transaction
  -> DEL product:42

The database remains authoritative. Protect misses with request coalescing or a short lock to prevent a cache stampede, add TTL jitter so hot keys do not expire together, and define safe fallback behavior when Redis is slow or unavailable. Avoid very large values and unbounded collections because they increase memory, network transfer, persistence work, and command latency.
