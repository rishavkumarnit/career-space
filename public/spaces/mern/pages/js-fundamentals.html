JavaScript Interview Preparation Notes

49 core JS concepts, from hoisting to the critical rendering path.

1. What is hoisting?

Hoisting is JavaScript's behavior of moving declarations to the top of their scope before execution. In reality nothing physically "moves" — during the Memory Creation Phase (before any line runs), the JS engine scans the scope and pre-allocates memory for every var, let, const, function, and class declaration it finds. What differs between them is how that memory gets initialized, which is where most of the interview confusion lives — declarations are hoisted, but expressions are not, and that distinction trips people up constantly.

var declarations

Hoisted and initialized with undefined. Accessing a var before its declaration gives undefined, not an error.

console.log(a); // undefined
var a = 10;

// Internally:
var a;          // declaration hoisted, initialized to undefined
console.log(a); // undefined
a = 10;         // assignment stays here

Practical note: a common interview follow-up is "why does var hoisting cause bugs?" — because var is function-scoped, not block-scoped, a var declared inside an if/for block leaks into the whole function and silently overwrites outer values. This is one of the main reasons let/const are preferred today.

Example: a hoisted local variable shadows the outer variable

var status = "Active";

function checkStatus() {
  // The local `var status` declaration is hoisted to the top
  // of this function and shadows the outer variable.
  console.log("Status is: " + status);

  // ... complex logic ...

  var status = "Inactive";
}

checkStatus(); // "Status is: undefined"

The result is undefined, not "Active". Because var is function-scoped, the local declaration applies to the entire checkStatus function. Only the declaration is hoisted; the assignment remains in its original position.

// A useful mental model for how JavaScript executes checkStatus:
function checkStatus() {
  var status; // initialized to undefined and shadows the outer status

  console.log("Status is: " + status);
  status = "Inactive";
}

Function declarations

Hoisted with the function itself — not just the name, but the entire function body — so it's fully callable before its textual position in the file.

hello(); // works — logs "hello"
function hello() {
  console.log("hello");
}

Function expressions

This is where people often get confused. Assigning a function to a variable makes it a function expression, not a function declaration — and only declarations get hoisted with their value intact. Here, only the var hello binding is hoisted; the function itself is not.

hello(); // TypeError: hello is not a function
var hello = function () {
  console.log("hello");
};

// Internally:
var hello; // hello = undefined
hello();   // undefined() → TypeError
hello = function () {
  console.log("hello");
};

The same applies to an arrow function assigned with var — it's still just a value being assigned to a binding that was already hoisted as undefined:

hello(); // TypeError
var hello = () => {
  console.log("hello");
};

Class declarations

Classes are hoisted too, but — like let/const — they land in the Temporal Dead Zone rather than being initialized to anything usable. You can't instantiate a class before its declaration is evaluated.

const obj = new User(); // ReferenceError
class User {}

Mental model: hoisting applies to bindings/declarations, not to arbitrary assignments or expressions. For var x = 10, think of it as two separate steps: var x; (binding created and initialized during scope setup) then x = 10; (the assignment executes later, in place). A plain function foo(){} declaration is the special case — its binding is initialized with the actual function object during scope setup itself, which is why it's callable immediately. A function expression never gets that early treatment, no matter whether it's assigned with var, let, or const.

2. Are let and const also hoisted?

Yes. They are hoisted but remain in the Temporal Dead Zone (TDZ) until initialization.

console.log(a); // ReferenceError
let a = 10;

The engine still allocates memory for let/const during the Memory Creation Phase (that's the "hoisted" part), but unlike var it does not initialize them to undefined — the binding exists but is unreachable until the actual declaration line executes. This is a deliberate design choice: it turns a whole class of "used before assignment" bugs that var allowed silently into loud, immediate ReferenceErrors.

Practical note: const additionally requires an initializer at declaration time and cannot be reassigned after — but note that const only freezes the binding, not the value; a const object's properties can still be mutated.

3. Temporal Dead Zone (TDZ)

The time between variable (let/const) hoisting and initialization.

{
  // TDZ starts
  console.log(a);
  let a = 10;
  // TDZ ends
}

Accessing a variable inside the TDZ throws a ReferenceError.

The TDZ isn't tied to physical position in the file so much as execution order relative to the declaration statement — the binding is created when the scope is entered, but stays in an "uninitialized" state until the `let`/`const` line actually runs. It exists purely as a safety mechanism: it makes reading a variable before its declaration a hard error instead of silently returning undefined (as var would).

Practical note: `typeof` does not protect you from the TDZ — `typeof x` throws a ReferenceError if x is in the TDZ, unlike a truly undeclared variable where `typeof` safely returns "undefined". This trips people up in interviews.

4. == vs ===

== (Loose Equality): performs type conversion.

'5' == 5
// true

=== (Strict Equality): checks value and type.

'5' === 5
// false

Use === in production code.

Under the hood, == runs the Abstract Equality Comparison Algorithm: if the two operands are different types, JS coerces one side (usually the non-number to a number) before comparing. This is what causes surprising results like `null == undefined` being true (they're only equal to each other, and to nothing else) and `'' == 0` being true, while `NaN == NaN` is always false regardless of operator — you must use `Number.isNaN()` or `Object.is()` to test for NaN.

Practical note: a common interview trap is `[] == false` → true (empty array coerces to `""` then to `0`). This kind of implicit coercion is exactly why teams enforce === via linting.

5. Synchronous vs asynchronous code

Synchronous code executes sequentially — each operation must complete before the next starts. Asynchronous code allows long-running operations (timers, API calls, file operations) to run in the background, so JavaScript continues executing other code without blocking the main thread.

JavaScript remains single-threaded; async behavior is managed through the Event Loop and callback/microtask queues.

// Synchronous
console.log(1);
console.log(2);
// Output: 1  2

// Asynchronous
console.log(1);
setTimeout(() => {
  console.log(2);
}, 0);
console.log(3);
// Output: 1  3  2

The reason setTimeout(fn, 0) doesn't run immediately is that it's still handed off to the Web API/timer thread and queued as a macrotask — it only runs once the current synchronous call stack is completely empty, no matter how small the delay is. This is why "0ms" really means "as soon as possible after the current script finishes", not "instantly".

Practical note: a common follow-up is "what actually makes JS non-blocking if it's single-threaded?" — the JS engine itself (call stack + heap) is single-threaded, but the surrounding runtime (browser Web APIs or Node's libuv) is multi-threaded and handles timers, I/O, and network requests in the background, only handing the *callback* back to the single JS thread via the event loop.

6. Event loop (in browsers)

The event loop is a core mechanism that allows JS to perform non-blocking, asynchronous operations even though JS itself is single-threaded.

Event Loop coordinates:

  • Execute Synchronous Code: the main script runs first; every function call is pushed onto the Call Stack (LIFO) and executed immediately.
  • Offload Asynchronous Tasks: setTimeout, fetch, event listeners are handed to the browser's Web APIs (or Node APIs) to run in the background.
  • Queue the Callbacks: once the background task finishes, its callback is placed into a queue.
  • Monitor the Call Stack: the event loop checks if the Call Stack is empty.
  • Push to Stack: if empty, the event loop takes the first queued task and pushes it onto the stack.
console.log(1);
setTimeout(() => console.log(2));
Promise.resolve()
.then(() => console.log(3));
console.log(4);
// Output: 1  4  3  2
Run Sync Code
      ↓
Execute all Microtasks
      ↓
Render (if needed)
      ↓
Execute one Macrotask
      ↓
Repeat

The precise ordering matters a lot in interviews: the microtask queue (Promise .then/.catch/.finally, queueMicrotask, MutationObserver) is fully drained — including any new microtasks scheduled while draining — before the event loop even looks at the macrotask/callback queue (setTimeout, setInterval, I/O, UI events). That's why in the example above, `3` (a microtask) always logs before `2` (a macrotask) even though the Promise resolved instantly and the timer was scheduled first. The optional "Render" step only happens on the browser's own schedule, typically once per macrotask/animation frame, which is also why requestAnimationFrame callbacks run right before a repaint rather than as a normal macrotask.

Practical note: a classic bug this causes is UI feeling "frozen" — because the event loop can't repaint or process clicks until the call stack is empty, a synchronous long-running loop (or, more subtly, an infinite chain of microtasks, see next topic) blocks rendering entirely.

7. Starvation of the callback queue

Occurs when microtasks continuously execute and prevent callback queue execution.

function infinite() {
 Promise.resolve().then(infinite);
}
infinite();
setTimeout(() => console.log("Timer"));
// "Timer" never executes.

This happens because the event loop's rule is strict: drain the microtask queue completely before touching the macrotask queue. If a microtask keeps scheduling another microtask, the queue never empties, so the loop never advances to macrotasks — the timer callback, any click handlers, and even rendering all get starved indefinitely.

Practical note: this is a real production bug pattern — a recursive `.then()` chain (e.g., a retry loop implemented with promises instead of setTimeout) can freeze a page or hang a Node process. The fix is to break the recursion out via a macrotask (setTimeout/setImmediate) periodically, or restructure with async/await plus an explicit await of a timer.

8. Proxy object

Proxy is an object that wraps another object (the "target") and allows you to intercept and redefine fundamental operations for it.

const user = {
   name: "John"
};
const proxy = new Proxy(user, {
   get(target, prop) {
      console.log(`Accessing property: ${prop}`);
      return target[prop];
   }
});

console.log(proxy.name);

Output:

Accessing property: name
John

Reading proxy.name invokes the get trap first. The trap logs the property name and then returns user.name, which is why the two lines appear in that order.

Used for: validation, logging, reactive frameworks.

A Proxy works by defining "traps" — handler functions that intercept fundamental operations on the target object. Besides get/set, common traps include has (intercepts the `in` operator), deleteProperty (intercepts `delete`), and apply (intercepts function calls). The companion built-in `Reflect` object provides default implementations of these same operations, so a trap typically calls `Reflect.get(target, prop)` internally instead of `target[prop]` to correctly preserve default behavior (including edge cases like inherited getters).

Practical note: this is exactly the mechanism Vue 3's reactivity system uses under the hood — instead of Object.defineProperty per-property (Vue 2's approach), Vue 3 wraps a whole object in a Proxy so it can also react to new property additions and array index/length changes.

9. Callback hell

A callback is a function passed as an argument to another function, to be executed later. Callback hell ("Pyramid of Doom") arises from nesting multiple callbacks to manage sequential async operations, producing code that is hard to read, debug, and maintain.

function getData(dataId, getNextData) {
  setTimeout(() => {
    console.log("data", dataId);
    if (getNextData) {
      getNextData();
    }
  }, 2000);
}
getData(1, () => {
  getData(2, () => {
    getData(3, () => {
      getData(4);
    });
  });
});

Solution: Promises, Async/Await.

Beyond readability, nested callbacks create real structural problems: error handling has to be duplicated at every level (each callback needs its own error-first check), and it's easy to accidentally call a callback twice or never — this is sometimes called the "inversion of control" problem, because once you hand your callback to another function, you're trusting that function to call it correctly. Promises fix this by giving you a single object you control that is guaranteed to settle exactly once.

10. Promises

A Promise represents the eventual completion (or failure) of an asynchronous operation and its resulting value.

States: Pending, Fulfilled, Rejected.

const promise = new Promise((resolve,reject)=>{
   resolve("Success");
});

How Promises improve on callback hell

Promises provide a standardized abstraction for representing and composing the eventual results of asynchronous operations. Instead of deeply nesting callbacks, each operation can return a Promise and be connected into a readable, predictable chain.

  • Flatter control flow: sequential operations can be chained with .then() instead of creating a pyramid of nested callbacks.
  • Centralized error handling: one .catch() can handle errors from any earlier step in the chain.
  • Reliable settlement: a Promise can settle only once, preventing the multiple-callback problem.
  • Easy composition: methods such as Promise.all(), Promise.allSettled(), and Promise.race() coordinate multiple asynchronous tasks.
  • Better readability: Promises support async/await, allowing asynchronous code to resemble synchronous code.
// Nested callbacks
getUser(userId, (error, user) => {
  if (error) return handleError(error);
  getOrders(user.id, (error, orders) => {
    if (error) return handleError(error);
    displayOrders(orders);
  });
});

// Promise chain
getUser(userId)
  .then(user => getOrders(user.id))
  .then(displayOrders)
  .catch(handleError);

The executor function passed to `new Promise()` runs synchronously and immediately — before the constructor even returns — but any `.then`/`.catch` callbacks attached to the promise are always scheduled as microtasks, even if the promise is already resolved by the time you attach them. Once a promise settles (fulfilled or rejected), it is locked into that state and value forever — calling resolve()/reject() again afterward has no effect.

Practical note: an unhandled rejection (a rejected promise with no .catch) doesn't crash sync code but does trigger an "unhandledrejection" event/warning — always attach error handling, especially in async functions.

11. Promise chaining

A technique to execute a sequence of async operations one after another. It works because every call to .then() or .catch() returns a new promise, which can be used to call the next .then().

fetchUser()
.then(user => fetchOrders(user.id))
.then(orders => console.log(orders))
.catch(console.error);

Avoids callback hell.

The key mechanic: whatever a `.then()` callback returns becomes the resolved value of the new promise it returns. If that return value is itself a promise, the chain automatically "unwraps"/flattens it and waits for it to settle before continuing — this is what lets `fetchOrders(user.id)` inside a `.then` feed cleanly into the next `.then` instead of producing a nested promise-of-a-promise. A single `.catch()` at the end will catch a rejection from any step earlier in the chain, since a rejection skips all intermediate `.then()`s and jumps straight to the nearest `.catch`.

12. All Promise methods
  • Promise.all() — fails immediately if any promise rejects.
  • Promise.allSettled() — returns result of all promises.
  • Promise.race() — returns first settled promise.
  • Promise.any() — returns first successful promise; fails only if all fail.

process.nextTick() is a Node.js-specific API that schedules a callback to run immediately after the current operation finishes, before the event loop continues to the next phase.

These four combinators exist because "run several async operations concurrently" needs different failure semantics depending on the use case: use Promise.all when every result is required and any single failure should abort everything (e.g., loading required page data); use allSettled when you want the outcome of every operation regardless of failures (e.g., batch-uploading files where some may fail); use race for timeouts (race a real request against a timer promise); use any when you just need the first success from redundant sources (e.g., querying multiple mirrors/CDNs).

Practical note: `process.nextTick()` callbacks run even before the regular microtask (Promise) queue in Node, which occasionally causes ordering confusion when mixing the two.

13. Async / await

async and await provide a more synchronous-looking way to write and manage asynchronous code, particularly with Promises. Syntactic sugar over promises.

async function getData() {
   const result = await fetch(url);
   return result;
}

When await is encountered: the function pauses, control returns to the event loop, and the function resumes when the promise resolves.

Under the hood an async function always returns a Promise, and `await` is essentially sugar for chaining `.then()` — the rest of the function body after `await` runs as a microtask callback once the awaited promise settles. Error handling uses regular try/catch instead of `.catch()`, because a rejected awaited promise throws inside the async function.

async function load() {
  try {
    const res = await fetch(url);
    return await res.json();
  } catch (err) {
    console.error(err);
  }
}

Practical note: a very common performance bug is awaiting independent promises sequentially (`await a(); await b();`) when they don't depend on each other — this serializes work that could run in parallel. Prefer `const [x, y] = await Promise.all([a(), b()]);` when the calls are independent.

14. Debouncing & throttling

Execution frequency: debouncing postpones execution until after a period of inactivity — the function only runs once calls have stopped coming in for the set delay. Throttling instead caps execution to a fixed number of times per interval, running immediately and then ignoring further calls until the interval elapses.

Use cases: debouncing suits tasks that shouldn't fire repeatedly in quick succession, e.g. an API call triggered by a search input. Throttling suits controlling the rate of handlers on high-frequency events like scroll or resize, where you still want periodic updates rather than silence until the user stops.

Debounce

const input1 = document.querySelector("#input1");

input1.addEventListener("input", () => {
  console.log("input..."); // runs hundreds of times!
});

function debounce(func, delay) {
  let timeout;
  return function() {
    clearTimeout(timeout);   // clear previous timer
    timeout = setTimeout(() => {
      func();                // run after delay
    }, delay);
  };
}

// Example usage:
const searchHandler = debounce(() => {
  console.log("Searching...");
}, 3000);

input1.addEventListener("input", searchHandler);

Every keystroke resets the timer, so func only fires once the user has stopped typing for the full delay — ideal for search-as-you-type API calls where you don't want a request per keystroke.

Throttle

window.addEventListener("scroll", () => {
  console.log("scrolling");
});

function throttle(func, limit) {
  let inThrottle;
  return function() {
    if (!inThrottle) {
      func();                 // run immediately
      inThrottle = true;
      setTimeout(() => (inThrottle = false), limit);
    }
  };
}

// Example usage:
const scrollHandler = throttle(() => {
  console.log("fetching...");
}, 1000);

window.addEventListener("scroll", scrollHandler);

The first call runs immediately, then a cooldown flag blocks further calls until the limit expires — so func runs at most once per interval no matter how many scroll events fire in between.

Practical note: both implementations rely on a closure over timeout/inThrottle to persist state between calls, so the wrapped function "remembers" the timer or flag from one invocation to the next — see Q20 for why that's possible at all.

Source: GeeksforGeeks — Difference between Debouncing and Throttling

15. Polyfills

A polyfill is a custom implementation of a modern feature for older browsers/environments that don't natively support it.

Examples: Promise, Array.map, Array.filter.

Polyfills differ from a transpiler (like Babel): a transpiler rewrites new syntax (e.g., arrow functions, optional chaining) into older equivalent syntax at build time, whereas a polyfill adds a missing runtime API/method by attaching it to the relevant global or prototype so the rest of the code can call it as if it were native. In practice both are used together — Babel transpiles syntax and pulls in polyfills (via core-js) for missing built-ins.

Practical note: interviewers often ask you to implement one from scratch (see next topic) specifically to test whether you understand what the built-in method does internally, not just how to call it.

16. Polyfill implementations

Each polyfill below attaches its method onto the relevant prototype so it can be called on any instance exactly like the native version, and each accepts a callback plus reads `this` as the array/value it's invoked on.

// Array.map
Array.prototype.myMap = function(cb){
   const result = [];
   for(let i=0;i {
    const results = [];
    let completed = 0;
    if (promises.length === 0) {
      resolve([]);
      return;
    }
    promises.forEach((promise, index) => {
      Promise.resolve(promise)
        .then((value) => {
          results[index] = value;
          completed++;
          if (completed === promises.length) {
            resolve(results);
          }
        })
        .catch(reject);
    });
  });
};

myMap/myFilter loop the array once, calling the callback with (element, index, array) and either pushing every transformed value (map) or only values that pass the test (filter) into a new result array — neither mutates the original. myIncludes/myFind both do a linear scan and return early the moment they find a match, the only difference being includes returns a boolean while find returns the actual element (or undefined). Promise.myAll wraps every item in `Promise.resolve()` (so plain, non-promise values are handled too), tracks a `completed` counter, writes each result into `results` at its original index (not push order) so ordering is preserved even if promises settle out of order, and resolves only once `completed` reaches the total count — while any single rejection immediately rejects the whole thing via `.catch(reject)`.

17. Custom setInterval 
function mySetInterval(fn, delay){
   let cancelled = false;
   function run(){
      if(cancelled) return;
      fn();
      setTimeout(run, delay);
   }
   setTimeout(run, delay);
   return () => cancelled = true;
}

Native `setInterval` fires on a fixed cadence regardless of how long the callback takes, which can cause overlapping executions if `fn` is slow. This implementation instead chains recursive `setTimeout` calls — each call to `run()` only schedules the *next* call after `fn()` finishes — so it self-corrects and never overlaps. The returned function closes over the `cancelled` flag, letting the caller stop the loop (mimicking `clearInterval`) without needing to store or expose the underlying timer ID.

18. Variable scope

Global Scope, Function Scope, Block Scope.

var: function scoped.
let/const: block scoped.

Scope determines where a variable is visible and how long it lives. Every function call creates a new function scope; every `{}` block (if, for, while, or a bare block) creates a new block scope for let/const, but not for var — which is why a var declared inside a for-loop body is still accessible after the loop ends. Scopes nest: a lookup for a variable walks outward from the current scope through each enclosing scope up to global (the scope chain), stopping at the first match — this is the mechanism that both lexical scope and closures rely on.

Practical note: the classic `var` vs `let` loop bug — `for (var i = 0; i < 3; i++) setTimeout(() => console.log(i))` logs 3, 3, 3 because all callbacks share the one function-scoped `i`; swapping to `let` logs 0, 1, 2 because `let` creates a fresh binding per iteration.

19. Event delegation & propagation

Event Propagation is the process by which an event travels through the DOM tree when it occurs on an element.

Phases:

  • Capturing Phase (Top → Down): Document → Parent → Child. Runs only for listeners registered with capture: true.
  • Target Phase: event reaches the clicked element.
  • Bubbling Phase (Bottom → Up): Child → Parent → Document. Default behavior of addEventListener().
parent.addEventListener("click", () => {
  console.log("parent");
});
child.addEventListener("click", () => {
  console.log("child");
});
// Clicking child:
// child
// parent

Event Delegation: a technique where a parent handles events for its children using event bubbling. Fewer listeners, better performance, works for dynamically added elements.

document.getElementById("list")
  .addEventListener("click", (e) => {
    if (e.target.tagName === "LI") {
      console.log(e.target.textContent);
    }
  });

// Instead of:
// li1.addEventListener(...)
// li2.addEventListener(...)
// li3.addEventListener(...)

Event Propagation is how an event moves through the DOM (capturing, target, bubbling). Event Delegation is a pattern that leverages event bubbling by attaching a single listener to a parent element to handle events from its children.

Practical note: the most common interview follow-up is "why is delegation better for dynamic lists?" — because the listener lives on the stable parent, elements added later (e.g., after an API call re-renders a list) are automatically handled with zero extra wiring, whereas per-element listeners would need to be re-attached to every new node.

20. Closure

A closure is a function bundled together with references to its surrounding state (the lexical environment). A closure gives a function access to its outer scope. Closures are created every time a function is created, at function creation time.

Closure = function remembers variables from outer scope even after the outer function finishes.

function outer(){
   let count = 0;
   return function(){
      count++;
      return count;
   };
}
const increment = outer();

Practical example: a bank account with private balance

function createBankAccount(initialBalance) {
  let balance = initialBalance;

  return {
    deposit(amount) {
      balance += amount;
    },

    withdraw(amount) {
      if (amount <= balance) {
        balance -= amount;
      }
    },

    getBalance() {
      return balance;
    }
  };
}

const account = createBankAccount(1000);

account.deposit(500);
account.withdraw(200);

console.log(account.getBalance()); // 1300

The returned methods form closures over balance. Code outside createBankAccount cannot access or change that variable directly; it can only interact with it through deposit, withdraw, and getBalance.

The reason this works — and the "why" behind closures — is that a function in JS doesn't just carry its code, it carries a hidden reference to the lexical environment it was created in. When `outer()` finishes running, its execution context would normally be popped off the call stack and garbage collected, but because the returned inner function still holds a reference to `outer`'s variable environment (via the scope chain), that environment is kept alive in memory instead of being collected. Each call to `outer()` creates a brand new, independent environment, so `increment` and a second call `outer()` don't share state.

Practical note: closures are the mechanism behind private state (module pattern, memoization, debounce/throttle) but they're also a common source of memory leaks if a closure unintentionally keeps a large object or DOM node alive longer than needed — long-lived closures (e.g., attached to global event listeners) should be cleaned up when no longer needed.

21. Constructor function

A specialized function used to create and initialize multiple objects with the same structure — a blueprint for creating instances of an object type.

function Person(name){
   this.name = name;
}
const p1 = new Person("John");

Used before ES6 classes.

The `new` keyword is what makes this work, and it performs four implicit steps: (1) creates a brand-new empty object, (2) sets that object's internal `[[Prototype]]` to `Person.prototype` (so instances can find shared methods), (3) calls `Person` with `this` bound to the new object, and (4) returns that object automatically (unless the constructor explicitly returns a different object). Any function can technically be called with `new`, which is why constructor functions are conventionally PascalCased as a signal to callers.

Practical note: calling a constructor function without `new` silently sets `this` to the global object (or `undefined` in strict mode) instead of throwing, which is a classic source of bugs — ES6 classes fix this by throwing a TypeError if called without `new`.

22. Class

A blueprint/template used to create objects with shared properties and methods.

class Person{
   constructor(name){
      this.name = name;
   }
   greet(){
   console.log(this.name);
   }
}

An object is an instance of a class.

Under the hood, a class is not a new object model — it's syntactic sugar over the existing prototype-based system. Methods defined in a class body (like `greet`) are placed on `Person.prototype`, not copied onto each instance, so all instances share one copy in memory. Two behaviors set classes apart from constructor functions, though: class bodies always execute in strict mode, and classes are hoisted but left in the Temporal Dead Zone — you can't use a class before its declaration, unlike a hoisted function declaration.

Practical note: class methods are not automatically bound to the instance — passing `instance.greet` as a callback (e.g., to an event listener) loses its `this` unless you `.bind()` it or use an arrow-function class field.

Arrow-function class field preserves this

class Person {
  constructor(name) {
    this.name = name;
  }

  greet = () => {
    console.log(this.name);
  };
}

const person = new Person("rishav");
setTimeout(person.greet, 2000); // "rishav" after 2 seconds

The arrow function does not create its own this. When the instance field is initialized, it captures that instance as this, so passing person.greet as a detached callback still works.

A regular class method can lose this

class Person {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(this.name);
  }
}

const person = new Person("rishav");
setTimeout(person.greet, 2000); // does not reliably print "rishav"

// Fix: explicitly bind the method to the instance
setTimeout(person.greet.bind(person), 2000); // "rishav"

The regular method lives on Person.prototype and receives this from its call site. Passing it as a plain callback removes the person. receiver, so it is no longer called with the instance as this.

23. OOP concepts

JavaScript supports the four classic OOP pillars, but implements them on top of prototypes/closures rather than dedicated language keywords like `private`/`interface` in Java — that distinction ("JS fakes OOP via prototypes") is worth mentioning if asked to compare languages.

class Car {
  constructor(brand, color) {
    this.brand = brand;
    this.color = color;
  }
  drive() {
    console.log(`${this.brand} is driving`);
  }
}
const car1 = new Car("BMW", "Black");
const car2 = new Car("Audi", "White");
car1.drive();

Encapsulation: binding related properties/methods together, hiding internal data, allowing access only through controlled methods.

class BankAccount {
  #balance = 0;
  deposit(amount) {
    this.balance += amount;
  }
  getBalance() {
    return this.balance;
  }
}
const account = new BankAccount();
account.deposit(1000);
console.log(account.getBalance());

The `#balance` syntax is a true private class field (ES2022) — unlike the old convention of prefixing with `_balance`, it's actually enforced by the engine and inaccessible from outside the class, even via bracket notation.

Inheritance: one class reuses properties/methods of another.

class Vehicle {
  start() {
    console.log("Vehicle Started");
  }
}
class Car extends Vehicle {}
class Bike extends Vehicle {}
const car = new Car();
car.start();

`extends` sets up prototype-chain delegation: `Car.prototype.__proto__` becomes `Vehicle.prototype`, so an instance of Car that doesn't find `start` on its own prototype falls back to Vehicle's. `super()` inside a subclass constructor must be called before using `this`, because until it runs, the parent class hasn't finished initializing the object.

Abstraction: hiding implementation details, showing only what's necessary.

class PaymentService {
  pay(amount) {
    this.validatePayment(amount);
    console.log("Payment Successful");
  }
  #validatePayment(amount) {
    console.log("Validating...");
  }
}
const payment = new PaymentService();
payment.pay(500);

The caller only ever needs to know about `pay(amount)` — the validation details are marked private and inaccessible from outside, so the class's public surface stays small and the internals can change freely without breaking consumers.

Polymorphism: the same method call behaves differently depending on the object.

class Animal {
  sound() {
    console.log("Animal Sound");
  }
}
class Dog extends Animal {
  sound() {
    console.log("Bark");
  }
}
class Cat extends Animal {
  sound() {
    console.log("Meow");
  }
}
const dog = new Dog();
const cat = new Cat();
dog.sound();
cat.sound();

This works because method lookup happens dynamically at call time via the prototype chain: `dog.sound()` finds `sound` on `Dog.prototype` before ever checking `Animal.prototype`, so the overriding method "wins" — the calling code doesn't need to know or care which subclass it's dealing with. This is sometimes called dynamic dispatch or method overriding.

Practical note: a frequent interview question is "does JS support method overloading (same name, different params)?" — no, unlike Java/C++; a later function/method definition simply replaces an earlier one with the same name, so JS relies on default parameters, rest params, or manual argument checks instead.

24. Execution context & call stack

The execution context is the environment where code is evaluated and executed. The Call Stack is a data structure used by JS to manage execution contexts.

Types: Global Execution Context (GEC), Function Execution Context (FEC).

Two phases: Memory Creation Phase, Execution Phase.

Execution Context contains: Variable Environment, Scope Chain, this value.

function one() {
  two();
}
function two() {
  three();
}
function three() {
  console.log("Hello");
}
one();

┌─────────┐
│ three() │
├─────────┤
│ two()   │
├─────────┤
│ one()   │
├─────────┤
│ Global  │
└─────────┘

The Global Execution Context is created first when the script loads, and a new Function Execution Context is pushed onto the stack every time a function is invoked, then popped off when it returns. Within each context's Memory Creation Phase, the engine pre-scans the code and allocates memory for variables/functions (this is what produces hoisting); the Execution Phase then runs the code line by line, assigning actual values. Each context also holds a reference to its outer environment, forming the scope chain used for variable lookups.

Practical note: because the stack has a finite size, deep uncontrolled recursion (a function calling itself without a proper base case) throws a "Maximum call stack size exceeded" RangeError — a classic interview question is how to avoid it (iterative rewrite, trampolining, or tail-call patterns, though JS engines don't reliably optimize tail calls).

25. Lexical scope

A function can access variables based on where it is defined in the code, not where it is called. JS decides variable accessibility during the code-writing (lexical) phase.

function outer(){
   let a = 10;
   function inner(){
      console.log(a);
   }
}

JS searches: Current Scope → Parent Scope → Global Scope. The fundamental rule: inner scopes can look out, but outer scopes cannot look in.

A lexical environment is the runtime structure that stores variables/functions for an execution context and references its outer lexical environment. Lexical scope is the rule of variable accessibility; a lexical environment is the runtime object that implements those rules.

Practical note: lexical scope is what makes closures possible at all — a closure is just a function retaining a live reference to the lexical environment(s) it was defined within, even after the outer function has returned.

26. This keyword

this refers to the context where a piece of code is supposed to run. Most typically used in object methods, where this refers to the object the method is attached to. The value of this depends on how a function is invoked (runtime binding).

"Normal functions have dynamic this determined by how they're called, whereas arrow functions don't have their own this and instead lexically capture it from their surrounding scope."

  • Object Method: obj.show() → this = obj
  • Regular Function: this = window (non-strict)
  • Arrow Function: no own this, uses parent's this
class Counter {
  constructor() {
    this.count = 0;
  }
  start() {
    setTimeout(function () {
      console.log(this.count);
    }, 1000);
  }
}
// output: undefined

class Counter {
  constructor() {
    this.count = 0;
  }
  start() {
    setTimeout(() => {
      console.log(this.count);
    }, 1000);
  }
}
// output: 0

The reason: a regular function's `this` is determined entirely by its call-site — how it's invoked, not where it's defined. `setTimeout` invokes the callback as a plain function call, so inside it `this` defaults to the global object (undefined in strict mode), losing the connection to the class instance. An arrow function has no `this` binding of its own at all; it looks up `this` in its enclosing lexical scope at definition time, which here is `start()`, where `this` correctly refers to the Counter instance.

Practical note: `this` resolution follows a precedence order worth memorizing for interviews — new binding (constructor call) > explicit binding (call/apply/bind) > implicit binding (obj.method()) > default binding (plain function call, global/undefined). Arrow functions opt out of this entirely by using lexical `this` instead.

27. Prototype inheritance

JavaScript's mechanism for sharing properties/methods between objects. When a property isn't found on an object, JS looks in its prototype, then that prototype's prototype, and so on — the prototype chain.

prototype: exists on constructor functions/classes; used as the prototype of objects created by that constructor.
__proto__: exists on objects; points to the object's prototype.

const arr = [];
console.log(arr.__proto__ === Array.prototype); // true

Every object has __proto__. Functions have prototype.

Lookup:
obj
↓
obj.__proto__
↓
Object.prototype
↓
null

Classes internally use prototype — methods are stored on ClassName.prototype and shared by all instances. Classes are syntactic sugar over prototype-based inheritance.

The lookup itself is a linked-list style walk: when you access `obj.someProp`, the engine checks `obj`'s own properties first, and only if not found does it follow the internal `[[Prototype]]` link to check the next object up the chain, continuing until it either finds the property or reaches `null` (the end of the chain, typically after `Object.prototype`). This is also how you can create an object with no prototype at all — `Object.create(null)` — useful for a "pure" dictionary object with no inherited methods like `toString`.

Practical note: mutating a shared object on `Array.prototype` or `Object.prototype` directly (monkey-patching built-ins) affects every object in the program and is generally considered unsafe — this is why polyfills are careful to check `if (!Array.prototype.myMap)` style guards before adding new methods.

28. Shadowing & illegal shadowing

Shadowing occurs when an inner scope declares a variable with the same name as an outer scope, temporarily hiding the outer variable. Illegal Shadowing happens when a var declaration attempts to shadow a let/const variable in the same scope, causing a syntax error.

// Shadowing
let a = 10;
{
   let a = 20;
}

// Illegal Shadowing
let a = 10;
{
   var a = 20;
}
// SyntaxError

Shadowing is legal because `let`/`const` create a new binding scoped to the block, which simply takes precedence over the outer variable of the same name for lookups inside that block — the outer variable is untouched and reappears once the block ends. Illegal shadowing is a syntax error specifically because `var` is function-scoped: a `var a` inside the block isn't actually creating a new block-scoped binding, it's trying to redeclare the exact same `let a` binding that TDZ rules and let's "no redeclaration" rule forbid — the engine can detect this at parse time, which is why it's a SyntaxError rather than a runtime error.

Practical note: the reverse — shadowing a `var` with an inner `let` — is legal, since the inner `let` simply creates a separate block-scoped binding on top of the function-scoped var.

29. Currying

Converting a function with multiple arguments into nested functions.

function add(a){
   return function(b){
      return a+b;
   };
}
add(2)(3);

Currying is only possible because of closures: each nested function remembers the arguments already supplied by the outer calls (`a` remains accessible inside the returned function even after `add(2)` has returned), so the chain progressively builds up the full argument list before the final computation runs. It's closely related to but distinct from partial application, where you pre-fill some arguments of a normal multi-arg function and get back a function expecting the rest — currying specifically transforms an n-ary function into a chain of unary (single-argument) functions.

Practical note: a common real-world use is building reusable, pre-configured functions, e.g. `const withTax = curry(applyTax)(0.18)` — useful in functional-style pipelines and libraries like Lodash (`_.curry`) or Ramda.

30. Shallow copy vs deep copy

Shallow Copy: copies first level only — Object.assign(), spread operator.

Deep Copy: copies nested objects — structuredClone(obj).

The distinction matters because objects and arrays in JS are stored and assigned by reference. A shallow copy creates a new top-level object, but any property whose value is itself an object/array is copied as a reference, not a new object — so mutating a nested object through the copy still mutates the original. A deep copy recursively creates brand-new objects at every level, fully severing that shared reference.

// 1. JSON approach
const clone = JSON.parse(JSON.stringify(original));
// Cons: loses functions, undefined, and Symbol; converts Dates to ISO
// strings; fails on circular references

// 2. structuredClone() — current standard for deep cloning
// Pros: native, handles circular references, supports Date, Set, Map,
// RegExp, ArrayBuffer
// Cons: cannot clone functions, DOM nodes, getters/setters — throws

// 3. Manual
function deepClone(obj) {
  if (obj === null || typeof obj !== "object") {
    return obj;
  }
  if (Array.isArray(obj)) {
    return obj.map((item) => deepClone(item));
  }
  const clonedObj = {};
  for (let key in obj) {
    if (obj.hasOwnProperty(key)) {
      clonedObj[key] = deepClone(obj[key]);
    }
  }
  return clonedObj;
}

Practical note: a frequent real-world bug is `const copy = {...original}` followed by mutating `copy.nested.field`, unknowingly also mutating `original.nested.field` — this is exactly why state-management libraries (Redux, React state) insist on treating nested state as immutable and require deep/structural copies when updating.

31. Spread, rest, and destructuring

Spread — expanding a collection into individual elements

Takes an iterable (array, string) or, since ES2018, an object, and expands it into individual elements or key-value pairs wherever several are expected.

const arr1 = [1, 2, 3];
const arr2 = [...arr1, 4, 5];       // [1, 2, 3, 4, 5] — copy + append
console.log(Math.max(...arr1));      // 3 — spread into individual arguments

const base = { a: 1, b: 2 };
const merged = { ...base, c: 3 };    // { a: 1, b: 2, c: 3 }
const overridden = { ...base, b: 99 }; // { a: 1, b: 99 } — later keys win

This is exactly the "spread operator" already named back in Q30 as a shallow-copy tool — spreading an array/object only copies one level deep, so the same shallow-copy caveat applies: a nested object inside the spread result is still shared by reference with the original.

Rest — collecting individual elements into a collection

The identical ... syntax, doing the opposite job: gathering multiple remaining values into a single array or object instead of expanding one.

// rest parameters — collects remaining arguments into an array
function sum(first, ...rest) {
  return first + rest.reduce((a, b) => a + b, 0);
}
sum(1, 2, 3, 4); // first = 1, rest = [2, 3, 4]

// rest in array destructuring — collects remaining elements
const [head, ...tail] = [1, 2, 3, 4];
// head = 1, tail = [2, 3, 4]

// rest in object destructuring — collects remaining properties
const { id, ...otherFields } = { id: 1, name: 'A', active: true };
// id = 1, otherFields = { name: 'A', active: true }

How to tell them apart: same three dots, opposite meaning — position is the only signal. Rest always sits on the left side of an assignment or in a parameter list (collecting), and must always come last in that pattern, since it greedily claims everything remaining. Spread always sits on the right side, inside a call or a literal (expanding), and can appear anywhere, even multiple times.

Common pitfall: function f(...rest, last) {} is a SyntaxError — a rest parameter has to be the last parameter, since anything after it would have no elements left to receive.

Destructuring — unpacking into named variables

// array destructuring — positional
const [first, second] = [10, 20];

// object destructuring — matched by key, order doesn't matter
const { name, age } = { age: 30, name: 'Alice' };

// default values (only kick in when the value is strictly undefined)
const { role = 'guest' } = {};

// renaming while destructuring
const { name: userName } = { name: 'Alice' };

// nested destructuring
const { address: { city } } = { address: { city: 'Delhi', zip: '110001' } };

// function parameter destructuring — very common for React props
function Greeting({ name, age = 18 }) {
  return `${name} is ${age}`;
}

Common pitfall: assuming object destructuring is positional like array destructuring — it isn't. { age, name } and { name, age } pull from the exact same object identically, since matching is by property name, not declaration order; only array destructuring cares about position. Also, defaults follow the same "strictly undefined only" rule covered in the JS & React Quirks page's Destructuring defaults question — null does not trigger a default.

All three ultimately share one theme: syntax for moving between "several loose values" and "one collection," in both directions. Destructuring and rest both take a collection apart — into named variables, or into a smaller leftover collection — while spread does the reverse, rebuilding or merging collections back up from loose values.

32. Generator function

A special function declared with function* that can pause execution using yield and resume later using next(). Returns a generator object — useful for lazy iteration, producing sequences, and managing stateful execution without storing all values in memory at once.

function* counter() {
  yield 1;
  yield 2;
  yield 3;
}
const gen = counter();
console.log(gen.next()); // { value: 1, done: false }
console.log(gen.next()); // { value: 2, done: false }
console.log(gen.next()); // { value: 3, done: false }
console.log(gen.next()); // { value: undefined, done: true }

What makes generators special is that they can suspend execution mid-function and hand control back to the caller — each `yield` pauses the function exactly where it is (preserving all local variables and its position), and calling `.next()` again resumes from that exact point rather than restarting. Because the object returned by calling the generator conforms to the iterator protocol (it has a `.next()` method returning `{value, done}`), generators are also directly usable in a `for...of` loop and with the spread operator.

Practical note: generators are the classic way to model infinite or lazy sequences (e.g., an infinite ID generator) without pre-computing all values up front, and they were the mechanism async/await was historically built on top of (an async function is conceptually a generator auto-driven by a promise-aware runner).

33. Memoization

An optimization technique where we cache the result of expensive function calls and return the cached result when the same inputs occur again.

function memoize(fn){
   const cache = {};
   return function(...args){
      const key = JSON.stringify(args);
      if(cache[key]){
         return cache[key];
      }
      cache[key] = fn(...args);
      return cache[key];
   };
}
function square(n) {
  console.log("Computing...");
  return n * n;
}
const memoizedSquare = memoize(square);
console.log(memoizedSquare(5));
console.log(memoizedSquare(5));
console.log(memoizedSquare(5));

The technique relies on a closure over the `cache` object: the returned function persists across calls and keeps reading/writing the same `cache`, keyed by a serialized form of the arguments (`JSON.stringify(args)` here is a simple but imperfect key — it breaks down for arguments containing functions, undefined, or objects with different key ordering). It's a specific case of the broader time-space tradeoff — trading memory (storing every past result) for speed (skipping recomputation), and works best for pure functions where the same input always produces the same output.

Practical note: memoization is commonly demonstrated with recursive Fibonacci, where naive recursion is exponential (`O(2^n)`) but memoizing collapses it to linear time by caching overlapping subproblem results — a good example of dynamic programming in JS. Unbounded caches can also leak memory over a long-running process, so production memoizers often cap size (LRU) or use a `WeakMap` when keys are objects.

34. Set

A collection of unique values. Duplicates are automatically ignored. Maintains insertion order. Can store primitives and objects.

const set = new Set();
set.add(1);
set.add(1);
// Result: {1}

set.add([1]);
set.add([1]);
// Result: two entries (different array references)

Uniqueness is determined using SameValueZero equality — essentially like `===` but treating `NaN` as equal to itself (so a Set can only ever contain one `NaN`). Because objects/arrays are compared by reference rather than by value, two structurally identical arrays are still treated as distinct members, as shown above. Common methods: `.has(value)`, `.delete(value)`, `.size` (not `.length`), and Sets are iterable directly with `for...of` or spread (`[...set]`), which is the standard one-liner for deduplicating an array: `[...new Set(arr)]`.

Practical note: a related structure, `WeakSet`, only stores objects (not primitives) and holds them weakly — meaning entries don't prevent garbage collection if there are no other references, which is useful for tracking objects (e.g., "has this DOM node been processed?") without causing memory leaks.

35. Object.defineProperty()

Lets you define or customize an object's property with fine-grained control.

const user = {};
Object.defineProperty(user, "name", {
  value: "Rishav",
  writable: false,
  enumerable: true,
  configurable: true,
});
console.log(user.name);

This is the same low-level API that ordinary object literal properties use implicitly — writing `{ name: "Rishav" }` is roughly equivalent to defining that property with `writable: true, enumerable: true, configurable: true` by default. Using `Object.defineProperty` explicitly lets you flip those defaults: `writable: false` makes a property read-only (assignments silently fail, or throw in strict mode), `enumerable: false` hides it from `for...in`/`Object.keys()`, and `configurable: false` prevents it from being deleted or redefined again.

Using get and set, you can create computed properties, perform validation, control access, or execute logic whenever a property is read or written. Getters run on access, setters run on assignment.

const user = {
  firstName: "Rishav",
  lastName: "Sharma",
};
Object.defineProperty(user, "fullName", {
  get() {
    return `${this.firstName} ${this.lastName}`;
  },
  set(value) {
    const [first, last] = value.split(" ");
    this.firstName = first;
    this.lastName = last;
  },
});
console.log(user.fullName);

Practical note: `Object.freeze()` is a shortcut built partly on this idea — it makes every existing property non-writable and non-configurable in one call (shallow only — nested objects remain mutable), which is why "deep freeze" utilities recursively call `Object.freeze` on nested objects too.

36. Optional chaining & nullish coalescing

Optional chaining lets you safely access nested properties without an error if a value is null/undefined.

user?.address?.city

Nullish Coalescing: provides a default only when the left side is null or undefined.

value ?? "Default"

Only checks: null, undefined.

Optional chaining short-circuits: the moment any link in the chain (`user`, `user.address`) is null/undefined, evaluation stops immediately and the whole expression returns `undefined` — it never throws, and it never evaluates the remaining chain. This is different from `??`, which only cares about its immediate left-hand value being null/undefined, unlike `||` which also falls back on any falsy value (0, "", NaN, false) — a common bug when using `||` to set a default for a numeric quantity like `count || 10`, which incorrectly overrides a legitimate `0`. `??` fixes exactly that case.

Practical note: optional chaining also works with function calls (`obj.method?.()`) and bracket notation (`obj?.[key]`), and the two operators combine naturally: `user?.address?.city ?? "Unknown"`.

37. call, apply, bind

All three let you explicitly set what `this` refers to inside a function, overriding whatever the call-site would normally determine — this is "explicit binding" and it takes priority over implicit binding (obj.method()).

// call()
fn.call(obj,arg1,arg2);

// apply()
fn.apply(obj,[arg1,arg2]);

// bind()
const newFn = fn.bind(obj);
// Returns new function.

The difference between the three: `call` and `apply` both invoke the function immediately, differing only in how arguments are passed (comma-separated vs. an array — handy when arguments already exist as an array); `bind` doesn't invoke anything, it instead returns a brand-new function permanently bound to the given `this` (and optionally pre-set leading arguments), which you can call later — commonly used for detaching a method from its object (e.g., passing `obj.method.bind(obj)` as an event handler) without losing its `this`.

Practical note: arrow functions ignore call/apply/bind entirely for `this` purposes — since they have no own `this` binding, trying to rebind it has no effect on the lexically-captured value.

38. map vs filter vs reduce

Map: transforms array.
Filter: returns matching elements.
Reduce: produces a single value.

const cart = [10, 20, 30];
const total = cart.reduce((a, c) =>{
   return a + c
} , 0);

All three are higher-order functions that take a callback and iterate the array without mutating the original — this immutability is a big reason they're preferred in functional/React-style code over manual for-loops that mutate in place. `reduce`'s callback receives an accumulator and the current element on every iteration, folding the whole array down to a single value (a number, object, or even another array) — it's the most general of the three, and `map`/`filter` can technically both be implemented in terms of `reduce`.

Practical note: all three can be chained (`arr.filter(...).map(...).reduce(...)`), but each pass iterates the array separately — for very large arrays or hot code paths, a single manual loop or a single `reduce` doing everything can be more performant than chaining several separate passes.

39. Garbage collection

The automatic process of freeing memory occupied by objects no longer reachable in the program. JS uses the Mark-and-Sweep algorithm. An object is alive if it can be reached from a root.

Roots include: global variables, current function's local variables, function call stack, closures. Unreachable objects are removed automatically.

Mark-and-sweep works in two phases: starting from the roots, the collector "marks" every object it can reach by following references (objects, then their properties, then those objects' properties, and so on); anything left unmarked afterward is considered garbage and is "swept" (its memory reclaimed). This correctly handles reference cycles (two objects referencing each other) that a simpler reference-counting approach would leak, since neither object is reachable from a root even though they reference each other.

Practical note: despite automatic GC, JS apps can still leak memory when something unintentionally keeps a reference alive — common culprits are forgotten event listeners/timers holding closures over large objects, detached DOM nodes still referenced from JS variables, and growing global caches/arrays with no eviction. DevTools' heap snapshot comparison is the standard tool for tracking these down.

40. Normal function vs arrow function

Arrow functions were introduced primarily to solve the recurring `this`-loses-context problem in callbacks (see the `this` keyword topic), by deliberately omitting several features a normal function has — no own `this`, no own `arguments`, and no ability to act as a constructor. Because they don't create their own binding for these, they transparently defer to whatever scope they're written inside, which is exactly what makes them ideal for short callbacks but unsuitable for object methods that rely on dynamic `this`.

const user = {
  name: "Rishav",
  greet() {
    console.log(this.name);
  }
};

user.greet();                 // "Rishav" — called as user.greet(), so this = user

setTimeout(user.greet, 1000); // undefined — only the function value is passed;
                               // the timer calls it back with no receiver, so this = undefined

setTimeout only ever receives whatever user.greet evaluates to — a bare function reference. The `user.` in front of it is not part of that value, so when the timer fires, it's effectively just `greet()` with nothing supplying `this`. Swap in an arrow function at the call site and the problem disappears, because an arrow function has no `this` of its own to lose: `setTimeout(() => user.greet(), 1000)` still calls it back as `user.greet()`, so `this` resolves to `user` as normal.

Practical note: a common gotcha is defining an object method as an arrow function — `const obj = { value: 1, get: () => this.value }` — this fails because the arrow captures `this` from the surrounding (often global/module) scope, not from `obj`, so always use a normal function (or method shorthand) for object methods that need `this`.

41. Reflow vs repaint

Reflow (Layout) occurs when the browser recalculates size/position of elements due to layout-related changes (width, height, display, DOM modifications). Repaint occurs when only visual appearance changes (color, background) without affecting layout.

Reflow is more expensive — it may impact other elements and always triggers a repaint. A repaint does not necessarily trigger a reflow.

Layout thrashing is a performance anti-pattern that occurs when JS repeatedly reads and writes to the DOM in a loop.

Layout thrashing specifically happens when code alternates reads (like `el.offsetHeight`, which forces the browser to flush any pending layout changes to answer accurately) with writes (like `el.style.width = ...`) inside a loop — each read-after-write pair forces a synchronous, unbatched reflow, multiplying cost. The fix is to batch all reads first, then all writes, so the browser can compute layout once.

Practical note: the browser normally batches multiple style changes and reflows only once per frame — but reading certain "layout-triggering" properties (offsetTop/Left/Width/Height, getComputedStyle, getBoundingClientRect) forces it to do that work immediately, which is the root cause of thrashing.

42. Document fragment

A lightweight, tagless DOM object that exists entirely in memory — a temporary holding area for HTML elements. Because it's detached from the active document tree, you can manipulate its contents without triggering expensive repaints/layout recalculations.

const fragment = document.createDocumentFragment();

Inserting elements directly into the live DOM inside a loop forces the browser to recalculate styles/layout/paint on every insertion. Using a DocumentFragment batches all modifications in memory and triggers only one layout pass when appending to the active tree.

Another subtlety worth knowing: when you append a DocumentFragment to the real DOM, only the fragment's children are moved over — the fragment node itself is never inserted and becomes empty again afterward, ready to be reused or discarded.

Practical note: this is essentially what virtual-DOM libraries like React conceptually do at a higher level — batch many logical changes and apply them to the real DOM in as few operations as possible — DocumentFragment is the vanilla-JS equivalent for manual DOM building (e.g., rendering a large list from an array).

43. innerHTML vs textContent

The core difference is that `innerHTML` runs its input through the browser's HTML parser and builds real DOM nodes from it (tags become elements), while `textContent` never parses anything — it just sets/reads the raw text of all descendant text nodes, so any `<`/`>` characters stay literal text on screen instead of becoming markup.

// innerHTML — parses HTML
div.innerHTML = "<h1>Hello</h1>";

// textContent — treats as plain text
div.textContent = "<h1>Hello</h1>";
// Safer and faster.
FeatureinnerHTMLtextContent
Primary useGets/sets HTML markupGets/sets plain text
HTML parsingParses HTML tagsTreats everything as text
SecurityCan cause XSS with untrusted inputSafe from HTML injection
PerformanceSlower (HTML parsing)Faster (text only)

Practical note: a related property, `innerText`, differs from `textContent` in that it's aware of CSS rendering (it skips hidden elements and collapses whitespace like the visible page does) and triggers a reflow to compute that, making it slightly slower — `textContent` is generally preferred when you just need to read/write raw text.

44. DOM tree & nodes

The DOM (Document Object Model) Tree is a hierarchical representation of an HTML document created by the browser. The browser parses HTML and converts it into a tree of nodes.

Node Types: Document, Element, Text, Comment.

DOM is a programming interface provided by the browser representing an HTML document as a tree of objects. It allows JS to: read HTML content, modify elements, change styles, handle events, add/remove elements dynamically.

Every node in this tree implements a shared `Node` interface (giving properties like `parentNode`, `childNodes`, `nextSibling`) — Element nodes additionally implement the richer `Element`/`HTMLElement` interfaces (attributes, classList, style, etc.), which is why not every node type supports every DOM method. The DOM is intentionally kept separate from the HTML source text: once parsed, it's a live, mutable object tree, so JS changes to it are immediately reflected without needing to re-parse any HTML string.

Practical note: the DOM tree is distinct from the CSSOM (the parsed styles) — the two are combined into the "render tree" as part of the critical rendering path before layout can happen.

45. Stop propagation methods

event.stopPropagation() — stops the event from propagating (bubbling/capturing) to parent elements.

event.stopImmediatePropagation() — stops propagation to parents AND execution of any remaining listeners on the same element.

event.preventDefault() — prevents browser default behavior (e.g., form submission).

parent.addEventListener("click", () => console.log("parent"));
child.addEventListener("click", (e) => {
  e.stopPropagation();
  console.log("child");
});
// Clicking child logs only "child" — bubbling to parent is halted.

These three are independent and commonly confused: `stopPropagation` only affects whether the event continues traveling to other elements — it does not stop other listeners on the *same* element from running, nor does it stop the browser's default action (e.g., a link still navigates). `stopImmediatePropagation` is the stronger version, also skipping remaining listeners on the current element. `preventDefault` is unrelated to propagation entirely — it only cancels the browser's built-in behavior for that event (form submit, checkbox toggle, link navigation) and can be combined with either of the other two, or used alone.

Practical note: a frequent bug is calling `stopPropagation()` too aggressively inside a component, which can silently break outer event delegation (e.g., a modal-close-on-outside-click handler attached to `document` never fires because an inner click stopped propagation).

46. target vs currentTarget
PropertyMeaning
event.targetThe element that originally triggered the event
event.currentTargetThe element whose event listener is currently executing

During event bubbling, target remains the same, but currentTarget changes as the event moves through different elements. Commonly used in event delegation.

list.addEventListener("click", (e) => {
  console.log(e.target);        // the actual <li> (or nested element) clicked
  console.log(e.currentTarget); // always the <ul> the listener is attached to
});

This distinction is exactly what makes event delegation practical: `currentTarget` is fixed by where you attached the listener (the parent `list`), while `target` tells you which specific descendant actually triggered the event, letting the single parent handler figure out what was clicked and act accordingly (e.g., via `e.target.tagName` or `closest()`).

Practical note: `e.currentTarget` becomes `null` once the event has finished dispatching (e.g., if you log it later asynchronously) — capture the value you need synchronously inside the handler if you plan to use it after an await or a callback.

47. How the browser renders a web page

The Critical Rendering Path (CRP) is the sequence of steps the browser follows to convert HTML, CSS, and JS into pixels on the screen.

1. Download HTML
        ↓
2. Parse HTML → DOM Tree
        ↓
3. Download & Parse CSS → CSSOM
        ↓
4. DOM + CSSOM → Render Tree
        ↓
5. Layout (Reflow)
        ↓
6. Paint
        ↓
7. Composite
        ↓
Page appears on screen

Two steps are worth calling out for interviews: the Render Tree only includes visually rendered nodes (elements with `display: none` are excluded, though `visibility: hidden` elements are still included since they still take up space), and Layout computes the exact size/position of every render-tree node before Paint fills in actual pixels (colors, borders, text, shadows) onto layers, which are then Composited together by the GPU in the correct stacking order.

Practical note: both `<script>` and CSS `<link>` tags are render-blocking by default — the parser pauses building the DOM to fetch and execute a plain `<script>`, which is why scripts are traditionally placed before `</body>` or loaded with `defer`/`async` attributes to avoid delaying first render.

48. Why is innerHTML unsafe? (XSS)

innerHTML is unsafe because it parses a string as HTML and inserts it into the DOM. If that string comes from an untrusted source (user input, API response, URL params), malicious code can be injected and executed.

div.innerHTML =
"<img src=x onerror='alert(1)'>";

This is Cross-Site Scripting (XSS).

Prevention: textContent, input sanitization, CSP policies.

The onerror attribute above fires because the browser attempts to load src=x as an image, fails, and invokes the inline handler — demonstrating that the danger isn't limited to <script> tags; many attributes and elements (onerror, onload, <a href="javascript:...">, <svg onload>) can execute arbitrary JS once inserted via innerHTML. Once injected, that script runs with the same origin and privileges as the rest of the page — meaning it can read cookies (unless HttpOnly), make authenticated requests, or manipulate the DOM to phish the user.

Practical note: modern frameworks (React, Vue, Angular) auto-escape interpolated text by default specifically to prevent this class of bug, which is why they require an explicit, deliberately-named opt-out (`dangerouslySetInnerHTML` in React, `v-html` in Vue) to render raw HTML — a strong signal in code review that the surrounding input needs to be trusted or sanitized (e.g., with DOMPurify).

49. Give five important changes introduced in ES6

ES6, also called ECMAScript 2015, was a major JavaScript update. Five commonly discussed changes are:

  1. let and const: introduced block-scoped variables as safer alternatives to function-scoped var.
  2. Arrow functions: added shorter function syntax and lexical this binding.
  3. Template literals: added backtick strings with interpolation and multiline support.
  4. Destructuring: made it possible to extract values from arrays and objects into variables concisely.
  5. Modules: introduced standardized export and import syntax for sharing code between files.
// 1. Block-scoped declarations
let count = 1;
const appName = "Interview Notes";

// 2. Arrow function
const double = number => number * 2;

// 3. Template literal
const message = `${appName}: ${double(count)}`;

// 4. Destructuring
const user = { name: "John", role: "Developer" };
const { name, role } = user;

// 5. Modules
export { double };
// import { double } from "./utils.js";

Important: ES6 introduced the class keyword, but under the hood a JavaScript class is a special type of function built on the existing prototype-based inheritance system.

class Person {}

console.log(typeof Person); // "function"
console.log(Person.prototype); // object containing class methods

Class syntax is more than a simple visual rewrite: class bodies always run in strict mode, class constructors must be called with new, and class declarations remain in the Temporal Dead Zone until evaluated.

Other notable ES6 features include classes, Promises, default parameters, rest and spread syntax, enhanced object literals, iterators, generators, Map, Set, and Symbol.

50. What happens to this in a detached method passed to setTimeout? 
const user = {
  name: "hkdhk",
  printname() {
    console.log(this.name);
  }
};

setTimeout(user.printname, 1000);
// The method is called without user as its receiver.

A method's this value is determined by how the function is called. Passing user.printname gives setTimeout a detached function reference, so the later call no longer has user as its receiver. Depending on the runtime, strictness, and timer implementation, this will not be the original user object.

Preserve the receiver with an arrow wrapper or bind:

setTimeout(() => user.printname(), 1000);
setTimeout(user.printname.bind(user), 1000);
51. What does arr.filter(Boolean) do?

It removes every falsy value from an array. Passing Boolean is equivalent to arr.filter(value => Boolean(value)).

const arr = [1, 0, "hello", "", null, undefined, false, NaN, 42];
const result = arr.filter(Boolean);

console.log(result);
// [1, "hello", 42]

The removed falsy values are false, 0, -0, 0n, "", null, undefined, and NaN. Be careful when values such as 0 or an empty string are valid data and should be retained.

const className = [
  "button",
  isActive && "active",
  isDisabled && "disabled"
].filter(Boolean).join(" ");
52. What are the different types of functions in JavaScript?

JavaScript functions can be classified by their syntax or by how they are used. These categories can overlap—for example, an arrow function can also be a callback.

  1. Function declaration: declared with a name and fully hoisted, so it can be called before its definition.
  2. Function expression: a function stored in a variable; the variable's declaration rules determine when it can be accessed.
  3. Arrow function: concise ES6 syntax with lexical this; it has no own arguments and cannot be used as a constructor.
  4. Anonymous function: a function without an explicit name, commonly used as a callback.
  5. Immediately Invoked Function Expression (IIFE): a function expression that runs as soon as it is created.
  6. Method: a function stored as an object or class property and called through that object.
  7. Constructor function: a regular function called with new to create objects.
  8. Callback function: passed to another function to be invoked later or when an operation completes.
  9. Higher-order function: accepts a function, returns a function, or both.
  10. Generator function: declared with function*; it can pause with yield and resume later.
  11. Async function: declared with async; it always returns a Promise and can use await.
// Function declaration
function add(a, b) { return a + b; }

// Function expression
const subtract = function (a, b) { return a - b; };

// Arrow function
const multiply = (a, b) => a * b;

// IIFE
(function () { console.log("Runs immediately"); })();

// Method
const user = { greet() { console.log("Hello"); } };

// Constructor function
function Person(name) { this.name = name; }
const person = new Person("Rishav");

// Callback and higher-order function
[1, 2, 3].map(number => number * 2);

// Generator function
function* ids() { yield 1; yield 2; }

// Async function
async function loadUser() {
  const response = await fetch("/api/user");
  return response.json();
}

Interview point: declaration, expression, and arrow describe how a function is written, while callback and higher-order describe the role it plays.
