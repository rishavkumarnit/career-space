Behavioral Interview

Production incidents structured as clear, ownership-focused STAR answers with lessons and follow-up discussion.

1. Tell me about a production bug caused by an incorrect assumption between services.

Interview answer: “One production bug I worked on at ANNAM.AI involved our Question Service and Logging Service. Our logging flow assumed that every question was associated with a user. That assumption was valid during the normal question-creation flow, so the logging code directly accessed the user object.

Later, we introduced questions that could be uploaded manually through files. Those questions did not necessarily have an associated user. When the Question Service processed one of them, the Logging Service attempted to access the missing user information. The lookup returned null, causing a NullPointerException that propagated back and failed the core question-processing flow.

I traced the request from the Question Service through the logging call. This showed that the question data itself was valid; the actual problem was an incorrect downstream assumption that a user would always exist.

We fixed the issue by explicitly supporting a missing user and treating system- or file-created questions as a valid business scenario. We also made the logging path defensive so optional metadata could not break the primary workflow.

The main lesson was that, when debugging distributed services, I should not stop at the line throwing the exception. I need to understand every way an entity can enter the system and verify the assumptions made by each downstream service.”

STAR elementWhat to emphasize
SituationFile-uploaded questions could legitimately exist without a user.
TaskFind why valid question processing failed across two services.
ActionTraced the cross-service call, identified the invalid non-null assumption, handled the optional user, and isolated logging failure from the core workflow.
ResultSystem/file-created questions were processed correctly and missing optional log metadata no longer caused the business operation to fail.

Likely follow-up: I would add regression tests for user-created, system-created, file-created, and missing-user cases; use null-safe DTO mapping; attach correlation IDs across both services; and define whether logging is best-effort or mandatory so its failure policy is explicit.

2. Tell me about a production data bug involving aggregation or business identity.

Interview answer: “One of the more interesting production bugs I solved at ANNAM.AI was an incorrect course-completion count for users enrolled in multiple cohorts.

A batch process aggregated watch-time data from MongoDB and calculated completed items for each enrollment. The correct enrollment identity consisted of (userId, courseId, courseVersionId, cohortId), but the aggregation did not consistently group by cohortId. Completion data from different cohorts could therefore be merged, making one cohort show more completed items than the user had actually completed within it.

I traced the issue through the enrollment map, MongoDB $match and $group stages, and the final result mapping. I found that cohortId was missing from part of the aggregation key. I also found inconsistent handling of a missing cohort versus a MongoDB ObjectId cohort value.

I corrected the aggregation and result mapping so every stage consistently used (userId, courseId, courseVersionId, cohortId) as the identity. I also normalized the no-cohort case so matching and grouping used one representation.

The key lesson was that a database grouping key must exactly match the business entity's uniqueness definition. An aggregation can be syntactically and technically valid while still producing incorrect business results if one identity dimension is omitted.”

STAR elementWhat to emphasize
SituationUsers could have separate enrollments in the same course/version across multiple cohorts.
TaskExplain and correct completion counts that exceeded the valid total for one enrollment.
ActionFollowed data through application keys and MongoDB stages, restored cohortId to the full grouping identity, and normalized null/no-cohort values.
ResultCompletion totals were isolated per enrollment and cohort rather than leaking across cohort boundaries.

Likely follow-up: I would add fixtures covering the same user/course/version in several cohorts, assert totals per composite identity, validate BSON types before aggregation, compare a sample of batch results with source records, and monitor impossible counts such as completed items exceeding total items.
