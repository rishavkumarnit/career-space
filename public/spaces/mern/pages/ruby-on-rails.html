Ruby on Rails Interview Questions

Important Ruby and Rails concepts, practical examples, performance, security, testing, and production scenarios.

1. What are Ruby and Ruby on Rails?

Ruby is a dynamic, object-oriented programming language in which almost everything is an object. Ruby on Rails is an opinionated web application framework written in Ruby. It supplies routing, controllers, views, database access, migrations, testing support, security defaults, and command-line tooling.

Rails favors Convention over Configuration: follow its naming and folder conventions and the framework can infer much of the configuration. It also follows Don't Repeat Yourself (DRY), encouraging reusable logic instead of duplicated code.

2. Explain MVC in Rails and the request flow.

Model represents domain data and rules, usually through Active Record. View produces HTML or another representation. Controller accepts the request, coordinates application work, and selects the response.

Browser → Router → Controller action → Model/service → Controller → View/JSON → Browser

For GET /users/7, the router maps the request to UsersController#show. The action loads the user, then Rails renders a view or serialized JSON. Keep controllers thin: complex workflows belong in service objects or other focused domain objects, while persistence rules belong near the model.

3. What is Active Record?

Active Record is Rails' ORM. A model class usually maps to a database table, an object maps to a row, and attributes map to columns. It provides queries, associations, validations, callbacks, transactions, and persistence methods.

class User < ApplicationRecord
  has_many :orders, dependent: :destroy
  validates :email, presence: true, uniqueness: true
end

active_users = User.where(active: true).order(created_at: :desc).limit(20)

Use parameterized Active Record queries rather than interpolating untrusted strings into SQL. Use find_by when absence is normal and find_by!/find when absence should raise an exception.

4. How do Rails associations work?

Common associations are belongs_to, has_one, has_many, and has_many :through. The model declaration describes the object relationship, but the database should still enforce it with foreign keys, indexes, and appropriate null or uniqueness constraints.

class Order < ApplicationRecord
  belongs_to :user
  has_many :line_items, dependent: :destroy
  has_many :products, through: :line_items
end

class LineItem < ApplicationRecord
  belongs_to :order
  belongs_to :product
end

Use a join model such as LineItem when a many-to-many relationship has its own data, such as quantity or purchase price.

5. What is the difference between validations and callbacks?

Validations decide whether model data is acceptable before persistence. Callbacks run code at lifecycle points such as before_validation, before_save, after_create, or after_commit.

class User < ApplicationRecord
  before_validation :normalize_email
  validates :email, presence: true, uniqueness: true
  after_commit :enqueue_welcome_email, on: :create
end

Callbacks are useful for small, model-specific invariants, but hidden chains of callbacks make behavior difficult to understand and test. Put multi-step business workflows and external side effects in explicit service objects or jobs. Prefer after_commit for work that must occur only after the database transaction succeeds.

6. What are Rails migrations?

Migrations are versioned Ruby classes that change the database schema in a repeatable way. Rails records applied versions in schema_migrations, allowing a team and deployment pipeline to apply the same changes consistently.

class AddStatusToOrders < ActiveRecord::Migration[7.1]
  def change
    add_column :orders, :status, :string, null: false, default: "pending"
    add_index :orders, :status
  end
end

In production, avoid long table locks: add large indexes concurrently where supported, backfill in batches, and split destructive changes into backward-compatible deployments. Never edit an old migration that has already run in shared environments; create a new migration.

7. Explain Rails RESTful routing and resources.

resources :articles generates conventional routes for index, show, new, create, edit, update, and destroy. The HTTP verb and URL express the operation instead of placing verbs in route names.

# config/routes.rb
resources :articles, only: %i[index show create update destroy]

# GET    /articles      → articles#index
# GET    /articles/:id  → articles#show
# POST   /articles      → articles#create
# PATCH  /articles/:id  → articles#update
# DELETE /articles/:id  → articles#destroy

Use namespaces for API versions, shallow nesting to avoid deeply nested URLs, and rails routes to inspect the generated route table.

8. What are strong parameters, and why are they needed?

Strong parameters explicitly allow the request fields that may be used for mass assignment. They prevent a client from setting protected attributes such as admin, role, or account_id merely by adding them to a request.

def user_params
  params.require(:user).permit(:name, :email)
end

def create
  @user = User.new(user_params)
end

Strong parameters are only one layer. Authorization must still verify that the current user is permitted to perform the action on the target resource.

9. What is the N+1 query problem, and how do you fix it?

N+1 occurs when one query loads a collection and an additional query is issued for each record's association. Rendering 100 orders and calling order.user.name can therefore execute 101 queries.

# N+1
orders = Order.all

# Eager load associations in a small number of queries
orders = Order.includes(:user, :line_items)

# JOIN is useful when filtering on the associated table
orders = Order.joins(:user).where(users: { active: true })

Use logs, query tracing, or tools such as Bullet to detect N+1 behavior. Choose includes, preload, or eager_load deliberately, select only needed data, and paginate large collections.

10. What are scopes and concerns in Rails?

A scope names a reusable, chainable Active Record query. A concern packages behavior shared across multiple models or controllers.

class Order < ApplicationRecord
  scope :paid, -> { where(status: "paid") }
  scope :recent, -> { order(created_at: :desc) }
end

Order.paid.recent.limit(10)

Keep scopes query-focused. Concerns can reduce duplication, but a large concern with unrelated responsibilities merely hides complexity; prefer composition or a dedicated domain/service object when the behavior represents a separate concept.

11. How do database transactions and locking work in Rails?

A transaction makes a group of database changes succeed or roll back together. It protects atomicity inside one database, but it does not automatically roll back an email, HTTP call, or message already sent to another system.

Order.transaction do
  product = Product.lock.find(product_id) # SELECT ... FOR UPDATE
  raise ActiveRecord::Rollback if product.stock < quantity

  product.update!(stock: product.stock - quantity)
  Order.create!(user:, product:, quantity:)
end

Pessimistic locking serializes access to a row. Optimistic locking uses a lock_version column and raises when another transaction changed the row first. Keep transactions short, use database constraints as the final guard, and enqueue external work after commit.

12. How are background jobs handled in Rails?

Active Job provides a common API for asynchronous work such as emails, image processing, imports, and third-party API calls. A queue backend such as Sidekiq performs the work outside the web request.

class WelcomeEmailJob < ApplicationJob
  queue_as :mailers
  retry_on Net::ReadTimeout, wait: :polynomially_longer, attempts: 5

  def perform(user_id)
    UserMailer.welcome(User.find(user_id)).deliver_now
  end
end

WelcomeEmailJob.perform_later(user.id)

Pass record IDs rather than large objects, make jobs idempotent because queues may redeliver, configure retries and dead-letter handling, and monitor queue depth, failures, and execution time.

13. How does caching work in Rails?

Rails supports low-level caching with Rails.cache, fragment caching in views, Russian-doll caching for nested fragments, and HTTP caching using ETags and freshness headers. Production applications commonly use Redis or Memcached as a shared cache store.

products = Rails.cache.fetch("featured-products/v1", expires_in: 10.minutes) do
  Product.featured.limit(20).to_a
end

Choose cache keys that include a record version or schema version, set sensible expiry, and plan invalidation before adding a cache. Never use a cache as the only source of truth, and prevent cache stampedes for expensive values with locking or stale-while-revalidate strategies.

14. How do you secure a Rails application?
  • Use parameterized Active Record queries to prevent SQL injection and strong parameters to limit mass assignment.
  • Keep CSRF protection enabled for cookie-based browser sessions; use secure, HttpOnly, appropriately SameSite cookies.
  • Escape untrusted output to prevent XSS; avoid html_safe on user-controlled content and use a Content Security Policy.
  • Authenticate users with a reviewed solution and enforce resource-level authorization with policies such as Pundit or CanCanCan.
  • Store secrets in encrypted credentials or a secret manager, never in source control; rotate leaked credentials.
  • Use HTTPS, rate-limit sensitive endpoints, update gems, run security scanners, redact sensitive parameters from logs, and apply least privilege to database/cloud access.

Rails has helpful secure defaults, but they do not replace authorization, dependency maintenance, secret management, monitoring, and secure deployment configuration.

15. How do you test a Rails application?

Rails includes Minitest, while many teams use RSpec. Test models and focused domain objects for business rules, request tests for routing/authentication/API behavior, job tests for queued work, and system tests for a few critical browser flows.

RSpec.describe "POST /orders", type: :request do
  it "creates an order for an authenticated user" do
    post orders_path, params: { order: { product_id: product.id } }, headers: auth_headers

    expect(response).to have_http_status(:created)
    expect(Order.last.user).to eq(user)
  end
end

Keep tests deterministic, use factories/fixtures carefully, avoid excessive mocking of framework behavior, and test observable results rather than private implementation details.

16. A Rails endpoint is slow in production. How would you debug it?

Start with request traces and metrics to split time across the controller, database, views/serialization, cache, and external services. Check logs for repeated SQL, measure query counts and durations, run EXPLAIN (ANALYZE, BUFFERS) on slow queries, and look for missing indexes, N+1 queries, large result sets, lock waits, and connection-pool exhaustion.

Then inspect CPU profiles, memory allocation and garbage collection, worker/thread saturation, queue latency, cache hit rate, and upstream/downstream latency. Reproduce with production-like data, make one evidence-based change, load-test it, and compare p50/p95/p99 latency rather than relying on a single request.

17. Why would you choose Ruby on Rails?

Rails is a web application development framework written in the Ruby programming language. It makes web development easier by providing assumptions and defaults for the features developers commonly need. This lets developers write less code while accomplishing more and makes the development experience productive and enjoyable.

Rails is opinionated software: it assumes there is a preferred way to build web applications and encourages developers to follow “The Rails Way.” Following its established patterns can significantly improve productivity and consistency. Trying to force conventions and patterns from unrelated frameworks into Rails can work against its design and make development more difficult.

The Rails philosophy has two major guiding principles:

  • Don't Repeat Yourself (DRY): every piece of knowledge should have a single, unambiguous, authoritative representation within the system. Avoiding duplicated information makes code more maintainable, extensible, consistent, and less prone to bugs.
  • Convention Over Configuration: Rails provides sensible conventions for common web-development decisions instead of requiring developers to specify everything through configuration files. Developers only need to configure behavior that differs from those conventions.

Interview answer: “I would choose Ruby on Rails when the priority is to build and iterate on a database-backed web application quickly. Rails follows convention over configuration, so I spend less time configuring basic application plumbing. It provides generators, Active Record ORM, RESTful routing, database migrations, validations, testing support, and sensible security defaults out of the box. This allows the team to focus on business features, deliver an MVP faster, and maintain a consistent project structure.”

Main advantages:

  • Fast development: Rails provides an integrated, productive framework for prototypes, MVPs, CRUD applications, APIs, and SaaS products.
  • Maintainable conventions: A standard project structure makes unfamiliar Rails applications easier for experienced Rails developers to understand.
  • Rich ecosystem: Mature gems solve common needs such as authentication, authorization, background jobs, payments, testing, and administration.
  • Developer-friendly language: Ruby's expressive syntax helps teams write readable domain logic with relatively little boilerplate.
  • Production capability: Rails supports caching, background processing, database transactions, security protections, observability, and horizontal scaling.

Useful defaults out of the box: Rails follows convention over configuration by selecting and configuring sensible components when a new application is generated:

  • Puma web server: Rails includes Puma as its standard HTTP application server. Puma supports concurrent request handling with threads and can be used in both development and production.
  • SQLite database: A new Rails application uses SQLite by default unless another database is selected during project creation. SQLite is lightweight, serverless, and stores data in a local file, making it convenient for learning, prototypes, and local development.

These defaults provide a working application with very little setup. For production, the team should still choose components based on its workload—for example, PostgreSQL is commonly preferred when an application needs greater concurrency, operational tooling, or advanced database features.

Interview-ready answer: “I would choose Rails when delivery speed, maintainability, and standard web application features matter more than extremely low-level performance control. I would still evaluate the workload: a CPU-intensive system, a hard real-time service, or a team without Ruby expertise might be better served by another technology. Rails is not automatically the best option for every service, but it is highly effective for rapidly delivering business-focused web products.”

18. What is the Ruby on Rails alternative to Hibernate?

Active Record is the closest Rails equivalent to Hibernate. Both are ORM tools that map application objects to relational database tables and reduce the amount of SQL and persistence boilerplate developers must write.

  • Hibernate: commonly used in Java and Spring applications and implements the Jakarta Persistence (JPA) specification.
  • Active Record: built directly into Rails through the activerecord gem and follows Rails' convention-over-configuration approach.
  • Entity mapping: a Hibernate @Entity is broadly comparable to a Rails model inheriting from ApplicationRecord.
  • Relationships: Hibernate annotations such as @OneToMany and @ManyToOne correspond to Rails associations such as has_many and belongs_to.
  • Schema evolution: Rails migrations play a role similar to database migration tools commonly paired with Hibernate, such as Flyway or Liquibase.
# Rails / Active Record
class Customer < ApplicationRecord
  has_many :orders
end

class Order < ApplicationRecord
  belongs_to :customer
end

# Generates SQL lazily when the relation is evaluated
orders = Order.includes(:customer).where(status: "paid")

Important difference: Hibernate is based mainly on the Data Mapper style, where persistence infrastructure manages plain Java entities. Rails uses the Active Record pattern, where the model contains both domain data and persistence methods such as save, update, and destroy. Therefore, Active Record is the practical Rails counterpart, but it is not an exact architectural equivalent.

Interview answer: “The closest Ruby on Rails alternative to Hibernate is Active Record. Both provide ORM features such as object-table mapping, associations, querying, transactions, validations, and change tracking. The key distinction is that Active Record is tightly integrated with Rails and places persistence behavior on the model, whereas Hibernate usually acts as a separate persistence layer implementing JPA.”

19. What is the difference between Spring Boot and Ruby on Rails?

Spring Boot and Ruby on Rails can both build production web applications and REST APIs, but they belong to different ecosystems and optimize for different priorities. Spring Boot is a Java framework built on the broader Spring ecosystem, while Rails is an opinionated full-stack framework written in Ruby.

AreaSpring BootRuby on Rails
LanguageJava, with JVM libraries and strong static typingRuby, with concise and expressive dynamic typing
ApproachConvention plus extensive configuration and component choicesStrong convention over configuration and “The Rails Way”
Typical strengthLarge enterprise systems, complex integrations, high-throughput services, and mature microservice ecosystemsRapid delivery of database-backed products, CRUD applications, SaaS platforms, and MVPs
Data accessCommonly Spring Data JPA with HibernateBuilt-in Active Record ORM
Dependency injectionSpring IoC container provides first-class dependency injection and bean lifecycle managementRails commonly relies on conventions, modules, and plain Ruby objects; a DI container is not central to the framework
ConcurrencyStrong multithreading support on the JVM; also supports reactive applicationsPuma supports processes and threads, but MRI Ruby has a Global VM Lock that limits parallel execution of Ruby code within one process
Startup and memoryUsually higher startup time and memory use, though tuning, AOT, and native images can reduce themFast development workflow, but production memory and boot behavior still depend on application size and worker configuration
EcosystemSpring Security, Spring Data, Spring Cloud, Batch, Integration, and extensive enterprise toolingRails generators, Active Job, Action Mailer, Hotwire, and a productive gem ecosystem
Development speedMore explicit structure and types, often with additional code and configurationGenerators and conventions usually make standard web features quicker to implement

When would you choose each?

  • Choose Spring Boot when the team has strong Java expertise, the system needs complex enterprise integrations, strict compile-time contracts, sophisticated security, JVM performance, or an extensive microservices platform.
  • Choose Rails when fast product iteration, a small productive team, conventional database-backed workflows, and reduced setup code are the main priorities.

Interview answer: “Spring Boot gives me a flexible, strongly typed Java ecosystem suited to complex enterprise services and large-scale integrations. Rails is more opinionated and usually lets a team deliver conventional web features faster with less boilerplate. Neither is universally better: I would choose based on workload, team expertise, delivery speed, operational requirements, and the surrounding technology ecosystem.”

20. Explain object-oriented programming (OOP) in Ruby.

Ruby is an object-oriented language in which almost everything—including numbers, strings, arrays, classes, and even nil—is an object. Objects contain state and respond to methods, while classes define their structure and behavior.

The four OOP principles in Ruby

  • Encapsulation: Keep an object's internal state private and expose controlled behavior through methods. Instance variables such as @balance are not directly accessible outside the object. attr_reader, attr_writer, and attr_accessor create controlled accessors.
  • Abstraction: Expose what an object does while hiding implementation details. Ruby does not have a dedicated abstract keyword; teams commonly use base classes, modules, and methods that raise NotImplementedError to define a contract.
  • Inheritance: A class can inherit from one superclass using <. Ruby supports single class inheritance, while modules provide reusable behavior through mixins.
  • Polymorphism: Different objects can respond to the same method in their own way. Ruby commonly uses duck typing: if an object responds to the required messages, its exact class is less important.
module Taxable
  def price_with_tax
    price * 1.18
  end
end

class Product
  include Taxable

  attr_reader :name, :price

  def initialize(name, price)
    @name = name
    @price = price
  end

  def description
    "#{name}: #{price}"
  end
end

class DiscountedProduct < Product
  def initialize(name, price, discount)
    super(name, price)
    @discount = discount
  end

  # Method overriding provides polymorphic behavior.
  def description
    "#{name}: #{price - @discount} after discount"
  end
end

products = [
  Product.new("Book", 500),
  DiscountedProduct.new("Course", 1_000, 200)
]

# Both objects respond to description, but each produces its own result.
products.each { |product| puts product.description }

Ruby-specific points

  • A Ruby class is itself an object and is an instance of Class.
  • Ruby uses dynamic typing and duck typing rather than requiring an interface declaration.
  • Modules provide namespaces and mixins, helping share behavior without multiple class inheritance.
  • Method visibility can be controlled with public, protected, and private.
  • Ruby supports open classes, so classes can be reopened and extended; this is powerful but should be used carefully to avoid unexpected behavior.

Interview answer: “Ruby is a pure object-oriented language where almost every value is an object. It supports encapsulation through instance variables and method visibility, abstraction through public APIs and modules, single inheritance through the < operator, and polymorphism mainly through method overriding and duck typing. Ruby modules also provide reusable mixins, which are preferred over multiple class inheritance.”
