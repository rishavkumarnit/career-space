HTML & CSS — Interview Prep

The recurring greatest hits — semantics, the box model, specificity, positioning, and layout. Priority noted where marked (*** highest).

1. HTML

Q1. What is semantic HTML, and why does it matter? ***

Semantic HTML means using tags that describe the meaning or role of their content, not just how it looks — <header>, <nav>, <main>, <article>, <section>, <aside>, <footer> — instead of reaching for a generic <div> for every container.

<!-- div soup: no information beyond class names -->
<div class="nav">...</div>
<div class="content">
  <div class="post">...</div>
</div>

<!-- semantic: the tag itself carries meaning -->
<nav>...</nav>
<main>
  <article>...</article>
</main>

It matters for three concrete reasons: accessibility — screen readers expose semantic landmarks so users can jump straight to nav/main/footer instead of reading the whole page linearly; SEO — search engines weight content inside <article>/heading tags more meaningfully than content in unlabeled divs; and maintainability — <nav> tells the next developer what it's for at a glance, whereas <div class="nav"> only works as long as nobody edits the class name.

Common follow-up: "so is <div> ever the right choice?" — yes, whenever a wrapper has no inherent meaning of its own and exists purely as a styling/layout hook. Semantic tags are for regions that genuinely represent something; div/span are for everything else.

Q2. Block vs inline vs inline-block elements **
BlockInlineInline-block
Line breaksStarts on a new lineFlows within surrounding textFlows within surrounding text
Width/heightRespected; defaults to full available widthIgnored — sized to contentRespected
Vertical margin/paddingPushes surrounding elementsApplied visually but doesn't affect layoutPushes surrounding elements
Examplesdiv, p, h1, sectionspan, a, strong, emNone natively — set via display: inline-block

inline-block is the hybrid: it sits in the flow of text like an inline element, but respects width, height, and vertical margin/padding like a block — which is why it's a common choice for nav items, badges, and buttons that need to sit next to each other yet still be sized explicitly.

Common pitfall: setting margin-top/margin-bottom on an inline element (like a span) and being confused when nothing moves — inline elements ignore vertical margin entirely, they only respect horizontal margin.

Q3. defer vs async on <script> tags **

A plain <script src="..."> blocks HTML parsing entirely while it downloads and executes. Both defer and async let the script download in parallel with parsing instead — they differ in when it's allowed to execute.

asyncdefer
ExecutesImmediately once downloaded — pauses parsing right thenAfter parsing finishes, just before DOMContentLoaded
Execution order (multiple scripts)Not guaranteed — whichever finishes downloading first runs firstGuaranteed — runs in document order
Good forIndependent scripts with no dependencies (analytics, ads)Scripts that need the full DOM, or depend on each other

Common follow-up: "why not just put <script> at the end of <body> instead?" — that was the pre-defer workaround, and it still blocks parsing for that script's download+execution at the point it's encountered. defer achieves the non-blocking download without moving markup around, while additionally guaranteeing both document order and that it runs before DOMContentLoaded fires.

Q4. What are data-* attributes for? *

Custom attributes for embedding extra information directly on an element, for JS or CSS to read, without inventing a non-standard attribute name that could collide with a future HTML spec addition.

<button data-user-id="42" data-role="admin">Edit</button>

<script>
  const btn = document.querySelector("button");
  console.log(btn.dataset.userId); // "42"
  console.log(btn.dataset.role);   // "admin"
</script>

Each data-kebab-case attribute is exposed on the element's .dataset object in camelCase. They're also directly selectable in CSS via attribute selectors, e.g. [data-role="admin"] { ... }.

Common pitfall: dataset values are always strings, even if they look numeric — data-count="5" gives "5", not 5. Forgetting to convert (Number(el.dataset.count)) before doing arithmetic is a classic bug.

Q5. What is web accessibility (a11y), and what do ARIA attributes do? **

Accessibility (a11y) means building UI that works for people using assistive technology — screen readers, keyboard-only navigation, switch devices, and so on. Semantic HTML (Q1) is the first line of defense: native elements like <button> or <select> come with keyboard support and a screen-reader role built in, for free.

ARIA (role, aria-label, aria-expanded, aria-hidden, etc.) fills the gap when semantic HTML genuinely can't express something — e.g. a custom dropdown built from styled <div>s needs role="listbox" and aria-expanded to behave like a native <select> for a screen reader.

<button aria-expanded="false" aria-controls="menu" onclick="toggleMenu()">
  Menu
</button>
<ul id="menu" hidden>...</ul>

Interview soundbite: "no ARIA is better than bad ARIA." Reach for a native semantic element first; only bolt on ARIA when there's genuinely no built-in equivalent, since incorrect ARIA can actively make things worse than having none at all.

2. CSS

Q6. The CSS box model — content-box vs border-box ***

Every element's rendered box is made of four layers, from the inside out: content, padding, border, and margin (margin is spacing outside the box, between it and its neighbors — it's not part of the box's own size).

┌─────────────── margin ───────────────┐
│ ┌────────────── border ─────────────┐ │
│ │ ┌──────────── padding ──────────┐ │ │
│ │ │          content              │ │ │
│ │ └────────────────────────────────┘ │ │
│ └──────────────────────────────────┘ │
└────────────────────────────────────────┘

The box-sizing property decides what width/height actually measure:

.content-box { box-sizing: content-box; width: 200px; padding: 20px; border: 5px solid; }
/* rendered width = 200 + 20*2 + 5*2 = 250px — padding/border ADD to the width */

.border-box { box-sizing: border-box; width: 200px; padding: 20px; border: 5px solid; }
/* rendered width = 200px flat — padding/border eat INTO the 200px */

content-box is the CSS default, but it means adding padding or a border changes an element's actual rendered size — which is rarely what you want. That's why almost every reset/framework starts with * { box-sizing: border-box; }: it makes the width you declare the width you get, regardless of padding or border.

Q7. How does CSS specificity and the cascade work? ***

When multiple rules target the same element and property, the browser resolves the conflict in order: (1) importance — !important rules win outright, (2) specificity — a weighted score per selector, (3) source order — if specificity ties, whichever rule was declared last wins.

Selector typeWeightExample
Inline style1000style="color:red"
ID100#header
Class / attribute / pseudo-class10.btn, [type=text], :hover
Element / pseudo-element1div, ::before

Scores add up per selector — .card .title is two classes (10+10=20), which beats a single .title (10) regardless of source order, but loses to a single ID like #title (100).

Common pitfall: reaching for !important to win a specificity fight. It works locally, but the only way to override it later is another !important of equal-or-higher specificity — which spirals into a stylesheet nobody can reason about. Fixing the actual selector specificity or source order is almost always the better call.

Q8. The position property — static/relative/absolute/fixed/sticky ***
ValueIn normal flow?Positioned relative to
static (default)YesN/A — top/left/etc. have no effect
relativeYes — still occupies original spaceIts own original position
absoluteNo — removed from flowNearest positioned ancestor, or the viewport if none
fixedNo — removed from flowThe viewport; stays put while scrolling
stickyYes, until threshold crossedBehaves like relative, then sticks like fixed within its container's bounds

An element also becomes a "positioned ancestor" (a valid target for its absolutely-positioned children) the moment it gets any position other than static — this is why position: relative with no offsets is such a common pattern: it changes nothing visually but establishes a containing block for children.

Common pitfall: an absolute element jumping to the corner of the whole page instead of positioning inside its intended parent — it walks up the ancestor chain looking for the nearest non-static ancestor, and silently falls back to the viewport if it never finds one. A less obvious variant: a transform, filter, or will-change on an ancestor also creates a new containing block, which can unexpectedly trap a fixed child into behaving like absolute.

Q9. Flexbox vs Grid — when do you reach for which? ***
FlexboxGrid
DimensionsOne at a time — a row OR a columnTwo at once — rows AND columns together
Sizing driven byContent — items can grow/shrink to fill spaceContainer — you define the grid, items place into it
Best forNav bars, toolbars, centering, evenly distributing items along one axisPage/section layout, dashboards, image galleries

Flexbox thinks in terms of a single axis: give it a row of items and rules for how to distribute leftover space (justify-content, flex-grow). Grid thinks in terms of a two-dimensional template: you declare rows and columns up front (grid-template-columns) and place items into cells, which is what one-dimensional Flexbox can't do without nesting.

Common follow-up: "can you combine them?" — yes, and it's the normal pattern in real layouts: Grid for the overall page skeleton, Flexbox for aligning content within an individual grid cell or component (e.g. centering a button inside a card).

Q10. Pseudo-classes vs pseudo-elements **

A pseudo-class (single colon, :) selects a real element that already exists in the DOM, based on its state or position — :hover, :focus, :first-child, :nth-child(), :checked.

A pseudo-element (double colon, ::) targets a sub-part of an element that isn't a real DOM node at all — ::before, ::after, ::first-line, ::placeholder. (::before/::after still work with a single colon for legacy reasons, but :: is the modern, unambiguous syntax.)

.card:hover {              /* state on a real element */
  box-shadow: 0 4px 12px rgba(0,0,0,.15);
}

.card::before {            /* generated content, not a real element */
  content: "★";
  color: gold;
}

Common pitfall: setting other properties on ::before/::after but forgetting content: "" — without it, the pseudo-element is never generated at all, so nothing renders no matter what else is styled.

Q11. z-index and stacking contexts ***

z-index only has an effect on positioned elements (or flex/grid items), and it's only ever compared against other elements within the same stacking context — not globally across the whole page.

A stacking context is a self-contained layer. Several common properties create a new one: position paired with a z-index other than auto, opacity below 1, transform, filter, will-change, isolation: isolate. Once created, every descendant's z-index is only ranked against siblings inside that same context — the entire context then gets stacked as a single unit against its own siblings, using the parent context's rules.

Classic gotcha: a child with z-index: 9999 still renders behind another, seemingly lower element. Usually the culprit is a parent that unintentionally created its own stacking context (e.g. an opacity: 0.99 or a transform added for an unrelated animation) — the child's huge z-index is only winning inside that small context, while the parent itself is losing the outer stacking fight.

Q12. CSS units — px vs % vs em vs rem vs vw/vh **
UnitRelative toNotes
pxNothing — absoluteFixed size, doesn't scale with anything else
%The parent's corresponding dimensionHeight % resolves to nothing unless the parent has an explicit height
emThe element's own font-sizeCompounds across nesting — each level scales off its already-scaled parent
remThe root (<html>) font-size onlyNever compounds, regardless of nesting depth
vw / vh1% of viewport width/heightIndependent of any parent — useful for full-bleed sizing

Common pitfall: nesting em-sized elements and getting unexpectedly large text — a font-size: 1.2em three levels deep multiplies against each ancestor's already-scaled size (1.2 × 1.2 × 1.2 ≈ 1.7×), not against the page's base size. rem exists specifically to sidestep this by always measuring from the root, which is why it's the more predictable default for sizing.

Q13. What is a Block Formatting Context (BFC)? **

A BFC is a self-contained mini layout environment — floats, margins, and clears happening inside it don't leak out and affect elements outside it. It's triggered by properties like overflow other than visible, any float, position: absolute/fixed, or display: flow-root/flex/grid.

It solves two classic layout problems:

<!-- Problem: floated children collapse the parent's height to 0 -->
<div class="gallery">
  <img style="float:left" src="a.jpg">
  <img style="float:left" src="b.jpg">
</div>
<!-- .gallery has zero height — floats are out of normal flow -->

<!-- Fix: give the container its own BFC -->
.gallery { display: flow-root; }
<!-- now .gallery expands to contain its floated children -->

The other classic case is margin collapsing: a child's top margin can "escape" through its parent and collapse with the parent's own margin if nothing separates them. Giving the parent a new BFC contains the child's margin inside it instead.

Common follow-up: "isn't overflow: hidden the usual fix for this?" — it works and is common in older code, but it has the side effect of clipping any content that overflows the container. display: flow-root was added specifically to create a BFC with no side effects, and is the modern preferred fix.

Q14. Responsive design — media queries & mobile-first **

Media queries apply CSS conditionally based on viewport characteristics:

/* mobile-first: base styles target the smallest screen, no query needed */
.card { display: block; }

@media (min-width: 768px) {
  .card { display: flex; } /* progressively enhance for larger screens */
}

Mobile-first means writing unqualified base styles for the smallest screen, then layering on min-width queries to enhance for larger viewports — as opposed to desktop-first, which starts with the full desktop layout and uses max-width queries to scale things down. Mobile-first is generally preferred because it forces prioritizing core content, and phones never have to download or parse override rules meant to undo a desktop layout.

Common pitfall: forgetting the viewport meta tag — <meta name="viewport" content="width=device-width, initial-scale=1">. Without it, mobile browsers render the page at a fake desktop-width viewport and zoom out to fit, so min-width/max-width queries evaluate against that fake width instead of the real device width, and "responsive" styles never seem to trigger correctly.
