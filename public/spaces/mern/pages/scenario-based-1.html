Scenario-Based Interview Questions — Part 1

Production troubleshooting, microservices, concurrency, databases, API scalability, and project discussions.

Production Troubleshooting

1. Your API response time increased from 200 ms to 6 seconds after deployment. How will you debug it?

Compare the release, configuration, traffic, and dependency metrics with the last healthy version. Trace a slow request end to end and inspect application time, database queries, connection pools, external calls, CPU, memory, and GC. Mitigate with a rollback or feature flag if impact is high, then reproduce, fix, load-test, and monitor p95/p99 latency.

2. Production CPU usage suddenly became 100%. How will you identify the root cause?

Identify the affected instances and correlate the spike with traffic, deployments, scheduled work, and dependency failures. Capture CPU profiles and thread dumps; look for hot loops, excessive serialization, retry storms, GC, regex backtracking, or too many runnable threads. Stabilize by scaling, throttling, disabling the faulty job, or rolling back, then fix from profiler evidence.

3. Your application intermittently throws OutOfMemoryError in production. How will you investigate?

Determine which memory area failed, preserve the heap dump, and inspect GC logs and memory trends. Compare heap histograms and dominator trees to find retained objects, unbounded caches, large payloads, listener leaks, queues, or native/direct-memory pressure. Fix the retention or bound the workload; increasing heap alone only delays a leak.

4. Database connections are exhausted during peak traffic. What could be the reasons?

Possible causes include leaked connections, long transactions, slow or blocked queries, an oversized request queue, retry storms, pool misconfiguration, or a database at its connection limit. Inspect pool active/idle/wait metrics, acquisition stack traces, pg_stat_activity, locks, and query latency. Close resources reliably, shorten transactions, tune queries and timeouts, apply backpressure, and size the pool against database capacity.

5. An API fails only in production but works locally and in staging. How will you debug it?

Compare configuration, secrets, feature flags, runtime versions, network/DNS, certificates, permissions, database schema/data volume, and dependent service versions. Reproduce the exact request using a correlation ID and inspect production-safe logs and traces. Avoid debugging by changing production blindly; recreate the difference in a controlled environment and add a regression check.

6. Application logs suddenly stopped in production. What could cause this?

Check whether the process is alive and requests still arrive, then inspect disk space/inodes, file permissions, log rotation, logging level/configuration, collector agents, network delivery, stdout capture, and blocked asynchronous appenders. DEBUG volume may have filled the disk or queue. Use metrics and platform events when logs themselves are unavailable.

7. A deployment brought down the entire application. How will you recover quickly?

Stop or pause the rollout and restore the last known-good immutable artifact or shift traffic to the healthy blue/green environment. Validate health and key user journeys, communicate status, and preserve evidence. Later identify why canary checks, readiness probes, compatibility controls, or rollback automation failed and improve them.

8. The application becomes slow every night at a specific time. How will you investigate?

Correlate the exact window with cron jobs, backups, ETL, report generation, log rotation, autoscaling, certificate jobs, and database maintenance. Compare CPU, I/O, locks, query plans, GC, and pool saturation during and outside that window. Reschedule, stagger, throttle, or isolate the competing workload after proving the correlation.

9. Users report intermittent 500 errors. How will you approach debugging?

Measure which routes, instances, users, and dependencies fail, then follow representative correlation IDs through logs and traces. Group exceptions by signature and check deployment, timeout, pool, resource, and data-pattern correlations. Add a focused reproduction and regression test; return a safe error response rather than exposing stack traces.

10. A thread dump shows most threads in WAITING. What could this indicate?

WAITING can be normal for idle pool threads waiting on a queue, so inspect stack traces and repeated dumps rather than the state alone. It may also indicate threads waiting for locks, futures, latches, pool connections, or responses. Look for the owner or missing signal and correlate with pool utilization and request latency.

11. Application memory usage keeps increasing. How will you identify a memory leak?

First distinguish normal heap growth from memory that remains high after full GC. Capture heap dumps at different times and compare retained sizes, GC roots, class histograms, and allocation profiles. Common causes are unbounded caches, static collections, listeners, ThreadLocal values, queues, sessions, and resources that are never closed.

12. Restarting a service temporarily fixes the issue, but it returns. What does that indicate?

It suggests accumulating state or exhausted resources: a memory/resource leak, stale cache, growing queue, stuck threads, connection leak, disk growth, or a dependency that recovers when connections reset. Track the relevant metric from restart until failure and take dumps before restarting. Treat restart as mitigation, not the root-cause fix.

13. GC pauses are causing latency spikes. How will you optimize them?

Use GC logs and allocation profiling to confirm pause type, frequency, heap occupancy, and allocation rate. Reduce temporary allocations and oversized caches, bound batches, fix leaks, and choose an appropriate heap and collector for the latency target. Validate changes under realistic load; simply enlarging the heap can create longer pauses.

14. The health API returns UP, but users cannot use the application. Why?

A shallow health endpoint may only prove that the process is running. Real traffic can still fail due to broken routes, authentication, exhausted pools, partial dependency failure, bad data, or frontend/CDN problems. Separate liveness from readiness and add lightweight checks for critical capability plus synthetic user-journey monitoring.

15. The application crashes after enabling DEBUG logs. Why?

DEBUG can generate huge volume, fill disk, saturate log I/O or network collectors, exhaust an asynchronous logging queue, increase allocations, or accidentally serialize large objects. Reduce the scope and duration of debug logging, sample it, redact sensitive data, enforce rotation/retention, and monitor logging backpressure.

16. A production issue started immediately after a configuration change. How will you validate the cause?

Diff the effective runtime configuration—not only the source file—and correlate its activation time with the failure. Roll back that single change or disable its flag, then observe whether metrics recover. Reapply it in a safe environment with a test that reproduces the issue and add validation for invalid combinations.

17. Users experience random timeouts under high traffic. What could be wrong?

Likely causes include thread or connection-pool exhaustion, lock contention, queue buildup, GC pauses, slow database/external calls, network saturation, retry amplification, or load-balancer timeout mismatch. Use saturation metrics and traces to find where time is spent, then bound concurrency, apply backpressure, tune the bottleneck, and set consistent timeout budgets.

18. A service consumes excessive disk space. What will you check first?

Check filesystem usage by directory and file type: application/access logs, heap or core dumps, temporary uploads, container layers, database/WAL files, and failed rotation. Stop unbounded growth safely, archive or remove only verified disposable data, then enforce rotation, retention, quotas, alerts, and cleanup ownership.

19. A third-party API becomes slow and your APIs time out. How will you handle it?

Use strict connection/read timeouts, a circuit breaker, bounded retries with exponential backoff and jitter only for safe operations, and bulkhead isolation so the dependency cannot consume every thread. Cache or serve a fallback where business-safe, move non-immediate work to a queue, expose partial failure clearly, and monitor the provider's latency and error budget.

20. A background scheduler consumes excessive CPU. How will you debug it?

Correlate CPU with the job schedule and capture a profile and thread dump while it runs. Check tight loops, unexpectedly large input, inefficient queries, excessive parallelism, repeated failures, and overlapping executions. Make the job bounded, observable, resumable, and protected against concurrent runs.

Microservices and Resilience

21. One slow microservice affects the entire system. How will you find the bottleneck?

Trace representative requests across services and compare time spent in queues, code, database, cache, and downstream calls. Inspect p95/p99 latency, saturation, consumer lag, and recent changes for each hop. Optimize or isolate the proven bottleneck, then enforce per-hop timeout budgets so one slow service cannot hold the whole request indefinitely.

22. Service A depends on Service B, but B is down. How will you prevent cascading failures?

Give the call a short timeout, circuit breaker, and isolated connection/thread pool. Retry only safe transient failures with a small budget and jitter; otherwise fail fast, serve cached/degraded data, or queue asynchronous work. Surface dependency health and recover gradually when B returns.

23. Retries between services caused overload. How will you avoid retry storms?

Limit retries end to end rather than at every layer, retry only transient and idempotent operations, and use exponential backoff with jitter. Honor Retry-After, cap concurrency, add circuit breakers and retry budgets, and shed load. Prefer queues for recoverable asynchronous work.

24. Microservice communication fails intermittently. How will you debug it?

Use correlation IDs and distributed traces to distinguish DNS, service discovery, TLS, routing, connection resets, timeout, server errors, and pool exhaustion. Check failures by source/destination instance and availability zone, compare configuration and certificates, and use network telemetry. Avoid assuming the network is the cause without hop-level evidence.

25. One service deployment broke a dependent service. Why can this happen?

The new version may have removed or renamed fields, changed validation or semantics, altered event schemas, or tightened timeouts/authentication. Maintain backward-compatible contracts, use consumer-driven contract and schema-compatibility tests, version only when necessary, deploy additive changes before removals, and use canary rollout.

26. A distributed transaction failed between two services. How will you maintain consistency?

Avoid a cross-service ACID transaction. Model the workflow as a Saga: each service commits locally and emits an event through an outbox; failures trigger idempotent compensating actions. Track Saga state, retry safely, handle dead letters, and run reconciliation for stuck or ambiguous cases.

27. The API Gateway is a bottleneck. How will you improve scalability?

Keep it stateless, run multiple instances behind a load balancer, avoid business logic and blocking transformations, tune connection reuse and limits, and cache safe responses or authorization metadata. Profile routing, TLS, logging, and plugins; apply rate limits at the edge and scale on latency/concurrency rather than CPU alone.

28. One healthy service instance receives no traffic. What could be wrong?

It may be absent from service discovery, failing readiness, in the wrong target group/zone, blocked by security rules, using mismatched labels or ports, or affected by sticky sessions/load-balancer weighting. Inspect registration, endpoints, readiness events, load-balancer health reasons, and routing configuration from the same network.

29. Service discovery stops working. What happens and how will you recover?

New lookups and topology changes fail; clients may temporarily use cached addresses, but stale endpoints eventually cause errors. Restore the discovery control plane, verify quorum/network/certificates, and re-register instances. Use highly available discovery, bounded caching, health checks, and fallback behavior without hiding prolonged failure.

30. Inter-service latency increased significantly. How will you troubleshoot it?

Break latency down with distributed tracing into DNS, connection/TLS, queueing, server processing, database, and downstream time. Check cross-zone routing, payload size, retries, connection reuse, pool saturation, GC, and deployments. Compare affected and healthy instances before changing timeout values.

31. A microservice produces too many logs and fills storage. What will you do?

Reduce noisy logger levels or sample repetitive events, but preserve incident evidence. Enforce structured logging, rotation, retention, quotas, compression, and rate limits; alert on ingestion and disk growth. Remove secrets and avoid logging full request bodies or stack traces for expected errors.

32. Microservices are tightly coupled and deployments are difficult. How will you improve the architecture?

Map dependencies and redefine services around business capabilities and owned data. Remove shared databases and shared release libraries, expose stable contracts, make changes backward compatible, and replace chatty synchronous flows with events where eventual consistency fits. Extract incrementally and measure whether each boundary reduces coupling.

33. A service sends duplicate requests. How will you prevent duplicate processing?

Require an idempotency key tied to the business operation and store its result under a unique constraint. On retry, return the original result instead of repeating side effects. Message consumers similarly store event IDs transactionally; database business keys remain the final protection.

34. Which patterns provide fault tolerance between services?

Use timeouts, circuit breakers, bounded retries with jitter, bulkheads, rate limiting, load shedding, fallbacks, health checks, and queues. Combine them with idempotency, outbox/inbox, dead-letter handling, and Sagas. Select patterns by failure semantics—blindly stacking all of them can amplify load.

35. Several services overload the same downstream service. How will you solve it?

Measure demand by caller, apply quotas and global concurrency limits, cache reusable results, batch requests, and eliminate duplicate calls. Use bulkheads and fair queues so one caller cannot starve others. Scale or partition the downstream only after reducing avoidable work.

36. A service crashes during sales traffic spikes. What improvements would you suggest?

Load-test to find the limiting resource, keep instances stateless, autoscale early, cache hot reads, queue bursty work, and enforce admission control/backpressure. Bound pools and payloads, protect dependencies with bulkheads, and degrade optional features. Pre-warm capacity for predictable events and monitor saturation and business success.

37. How will you monitor failures across many microservices?

Centralize structured logs, metrics, and distributed traces with consistent service, version, environment, and correlation fields. Use RED signals—rate, errors, duration—plus saturation, queue lag, and business metrics. Define SLO-based alerts and dashboards, service ownership, dependency maps, and actionable runbooks.

38. One service version is incompatible with another. How will you handle API versioning?

Prefer additive, backward-compatible evolution: add optional fields, tolerate unknown fields, and deprecate before removal. Use contract tests and a compatibility matrix, then deploy consumers before breaking producers. Introduce a new endpoint/event version only for genuinely incompatible semantics and run both during migration.

39. How will you trace one request across multiple microservices?

Propagate a standard trace context through HTTP and messaging, create spans for each service and dependency, and include trace/correlation IDs in structured logs. A tracing backend then shows the full critical path, errors, and slow spans. Do not create unrelated new trace IDs at service boundaries.

40. When would you replace synchronous communication with asynchronous communication?

Use messaging when the caller does not need an immediate result, traffic must be buffered, multiple consumers react independently, or temporal decoupling improves resilience. Keep synchronous calls for immediate validation or query results. Async design adds eventual consistency, duplicate delivery, ordering, observability, and reconciliation concerns.

Concurrency and Multithreading

41. Multiple users can book the same seat simultaneously. How will you prevent it?

Make the inventory database the authority and reserve with one atomic conditional update or a unique constraint for seat and event. Only one transaction succeeds; others receive a conflict. Use short expiring holds for checkout, idempotency keys for retries, and compensation when payment fails.

42. The thread pool is exhausted and APIs time out. How will you debug it?

Inspect pool active/queued/rejected metrics and several thread dumps to see whether workers are blocked on database, HTTP, locks, or long CPU work. Find the slow dependency or unbounded submission source, then add timeouts, bulkheads, backpressure, and bounded queues. Increasing threads can worsen context switching and downstream overload.

43. A production deadlock made the application hang. How will you identify it?

Capture JVM thread dumps—jstack or jcmd Thread.print—and inspect the deadlock report, lock owners, and waiting stacks. For database deadlocks, inspect server deadlock logs and involved SQL. Fix consistent lock order, reduce lock scope, and add timeouts and tests for the competing paths.

44. A shared counter gives inconsistent values during concurrent requests. Why?

count++ is a read-modify-write sequence, not an atomic operation, so updates can be lost and visibility is not guaranteed. Use AtomicLong/LongAdder, synchronization, or an atomic database/cache increment depending on scope. A JVM atomic cannot coordinate counters across service instances.

45. Async processing is slower than synchronous execution. What could be wrong?

The tasks may be too small, CPU-bound on already saturated cores, serialized by a shared lock, queued in an undersized/oversized pool, or dominated by scheduling and context-switch overhead. Measure queue wait versus execution, pool utilization, cores, blocking calls, and contention. Async improves concurrency, not the speed of every operation.

46. Two scheduled jobs process the same data. How will you avoid duplicate execution?

Use a distributed scheduler or lock with an owner token and expiry, or claim rows atomically by status. Still make the job idempotent because locks can expire or nodes can crash. Store checkpoints and use unique business constraints to prevent repeated side effects.

47. The application creates too many threads under load. What problems can this cause?

Each thread consumes stack memory and scheduling overhead; too many cause context switching, cache misses, native-thread exhaustion, longer queues, and instability. Use bounded executors, explicit rejection/backpressure, separate pools for workloads, and concurrency sized to CPU or downstream capacity.

48. Threads are blocked by synchronized methods. How will you optimize?

Profile contention and identify the exact lock and critical section. Reduce protected work, move I/O outside locks, split one global lock into independent locks, prefer immutable state or concurrent collections, and use read/write or atomic techniques when semantics allow. Preserve correctness and benchmark under contention.

49. A background thread silently crashes without logs. How will you investigate?

Inspect executor task handling: exceptions from submit() may be held inside the returned Future. Always observe futures/completion stages, wrap task boundaries with structured error logging, and configure an uncaught-exception handler. Add success/failure/heartbeat metrics so missing work is detectable without logs.

50. High concurrency causes database locking. How will you reduce contention?

Identify blockers and locked statements, shorten transactions, access rows in a consistent order, index predicates so fewer rows are locked, reduce hot rows, and use atomic conditional updates or optimistic locking. Move slow external calls outside transactions and retry deadlock victims with a bounded policy.

51. Concurrent requests create duplicate orders or payments. How will you ensure idempotency?

Accept an idempotency key for one logical operation and atomically store it with the result under a unique constraint. Repeated requests return the stored result; concurrent inserts let only one win. Pass a stable key to the payment provider and reconcile ambiguous timeouts before charging again.

52. One thread holds a lock too long. How will you identify it?

Take repeated thread dumps or a Java Flight Recorder profile and locate BLOCKED threads, their lock identity, and the owning stack. Correlate the owner with request traces and duration. Move blocking I/O out of the critical section, reduce scope, or redesign shared state.

53. Producers create work faster than consumers process it. How will you handle backpressure?

Use bounded queues and slow, reject, or shed producer work when capacity is reached. Scale consumers up to the real downstream limit, batch efficiently, prioritize traffic, and expose queue-depth/age metrics. Durable brokers absorb temporary bursts but do not replace capacity planning.

54. Why are peak-traffic concurrency bugs difficult to reproduce locally?

They depend on rare timing, production data size, multi-instance behavior, resource pressure, network latency, and real dependency limits. Reproduce with deterministic stress/load tests, production-like topology and data, fault injection, and repeated runs. Thread dumps, traces, and event histories capture evidence when reproduction remains intermittent.

55. What should you consider before processing large data in parallel?

Classify CPU versus I/O work, measure task size and ordering requirements, confirm thread safety, and account for memory, partitioning, error recovery, rate limits, and downstream capacity. Use bounded parallelism and checkpoints; compare against batching or database-native processing before adding threads.

56. What is thread starvation?

Thread starvation means a task cannot obtain enough CPU, executor threads, locks, or another required resource because other work continually dominates it. Causes include unfair locks, priority misuse, long blocking tasks, and one workload monopolizing a shared pool. Use fair scheduling where needed, shorter tasks, separate bounded pools, and starvation metrics.

57. ConcurrentModificationException occurs randomly. What could cause it?

A collection is being structurally modified while a fail-fast iterator traverses it, possibly from the same loop or another thread. Do not mutate through the collection during iteration; use the iterator's supported removal, collect changes for later, synchronize correctly, or choose a suitable concurrent/copy-on-write collection.

58. Multiple APIs update the same record. How will you preserve consistency?

Define one owning service and use optimistic locking with a version column, or an atomic conditional update when the rule is simple. Return 409 or safely retry on conflict. Use pessimistic locks only for short, high-contention critical sections and preserve invariants with database constraints.

59. One asynchronous task depends on another. How will you coordinate them?

Express the dependency explicitly with CompletableFuture.thenCompose/thenCombine or a workflow/message state machine, rather than blocking a worker with get(). Propagate errors and timeouts, use bounded executors, make steps idempotent, and persist workflow state if it must survive restarts.

60. A scheduler runs once on one server but duplicates work on multiple servers. How will you solve it?

Every instance executes its local schedule. Use a cluster-aware scheduler, leader election, or a database/Redis distributed lock with expiry and ownership checks. Make the work idempotent and enforce a business unique constraint because no scheduling lock removes every crash race.

Database Performance and Reliability

61. A SQL query became slow as data volume grew. How will you optimize it?

Run EXPLAIN (ANALYZE, BUFFERS) with representative parameters, inspect scans, estimates, joins, sorts, and I/O, then add or adjust selective composite/partial indexes. Return less data, rewrite inefficient predicates, refresh statistics, and consider partitioning or precomputation only after measuring.

62. Database CPU suddenly became very high. What steps will you take?

Identify top queries by total and per-call CPU/time, active sessions, wait events, traffic changes, new plans, maintenance, and recent deployments. Stop or throttle runaway work, then fix scans, joins, missing indexes, excessive calls, or plan/statistics issues. Verify that application retries are not amplifying load.

63. One request makes too many database calls. What issue could this indicate?

It commonly indicates an ORM N+1 query problem, chatty repository logic, lazy loading during serialization, or queries inside a loop. Count queries per request and inspect traces/logs. Fix with a fetch join, entity graph, projection, batching, or one purpose-built query while avoiding a huge Cartesian result.

64. Pagination is slow on a large dataset. How will you optimize it?

Large OFFSET values force the database to scan and discard earlier rows. Use keyset/cursor pagination with a stable indexed ordering such as (created_at, id), request the next page after the last seen key, and avoid an expensive exact count when unnecessary.

65. Concurrent requests insert duplicate records. How will you prevent it?

Enforce uniqueness in the database on the true business key; an application “check then insert” has a race. Use an atomic upsert or insert and handle unique violations as an existing result. Add an idempotency key when duplicates represent repeated requests.

66. A database deadlock occurred during concurrent updates. How will you debug it?

Inspect the database deadlock report for transactions, statements, locks, and access order. Reproduce the competing sequence, update resources in a consistent order, shorten transactions, and ensure predicates are indexed. Retry the aborted transaction only with a small bounded backoff.

67. Writes slowed after adding indexes. Why?

Every insert, update, or delete must maintain relevant index structures, causing CPU, I/O, WAL, page splits, and locking overhead. Remove redundant/unused indexes, use narrower or partial indexes, batch writes, and measure read benefit against write cost. More indexes are not automatically better.

68. A query is fast locally but slow in production. What could differ?

Production may have far more data, different distributions/statistics, indexes, parameters/plans, concurrent locks, cache warmth, hardware, configuration, network latency, or database version. Compare actual plans and wait events with production-like parameters and anonymized data before modifying the query.

69. You found an N+1 query problem. How will you fix it?

Confirm it by counting repeated child queries, then fetch required relations in bulk using a join fetch, entity graph, projection, batch fetching, or a second IN query. Keep pagination semantics in mind and fetch only needed columns. Add a test or metric limiting query count for that use case.

70. The database connection pool is often exhausted. What could cause it?

Connections may leak, transactions may stay open, queries may be slow/blocked, traffic or retries may exceed capacity, or the pool may be incorrectly sized. Inspect acquisition time, active/idle/leak metrics, sessions, locks, and query traces. Fix the hold time and admission rate before simply enlarging the pool.

71. A Spring transaction does not roll back. What could be wrong?

Common causes are self-invocation bypassing the Spring proxy, a non-public method, catching and suppressing the exception, throwing a checked exception without rollbackFor, using the wrong transaction manager, or crossing an async thread. Verify proxy boundaries and exception flow; by default Spring rolls back on unchecked exceptions.

72. Large table scans slow APIs. How will you identify missing indexes?

Use slow-query statistics and EXPLAIN (ANALYZE, BUFFERS) to find high-row sequential scans and compare estimated versus actual rows. Design indexes around selective filters, joins, and ordering—not isolated columns. Confirm the plan improves under realistic data and monitor index usage/write overhead.

73. Joins become expensive as data grows. What optimizations can help?

Index join keys and filters, reduce rows and columns before joining, verify data types match, refresh statistics, and inspect join order/algorithm in the actual plan. Precompute or denormalize only proven read hotspots, partition when pruning applies, and avoid hiding a many-to-many explosion behind more hardware.

74. How will you optimize bulk inserts and updates?

Batch operations in bounded transaction sizes, use JDBC batching or database bulk-loading/upsert features, reuse prepared statements, and avoid per-row network round trips. Defer nonessential processing, measure index/constraint cost, and keep batches small enough to avoid huge locks, WAL bursts, and memory pressure.

75. One transaction locks rows too long. How will you identify it?

Inspect active sessions, transaction age, wait events, blockers, and the SQL owning each lock; correlate to an application trace. Find code that starts a transaction before network calls, user interaction, or heavy processing. Shorten the boundary, index the update predicate, and enforce transaction/statement timeouts.

76. Read-heavy traffic overloads the primary database. How will you scale it?

Cache safe hot data, eliminate inefficient/repeated queries, add read replicas, and route read-only traffic with awareness of replication lag. Use materialized views/search indexes for specialized reads and partition when appropriate. Keep consistency-sensitive reads on the primary or use a read-your-writes strategy.

77. You need fast reads and strong consistency. How will you balance them?

Classify operations by actual consistency need. Keep inventory, payment, and read-after-write paths on the authoritative store; cache immutable or less-sensitive data with explicit TTL/invalidation. Use versioned cache entries or update/invalidate after commit, and never claim strong consistency from an asynchronously updated cache.

78. Frequent database calls for static data add latency. What will you implement?

Cache the data in-process, in Redis, or at the HTTP/CDN layer depending on sharing and size. Choose TTL and event-driven invalidation based on update frequency, use cache-aside with protection against stampedes, and monitor hit rate and staleness. Configuration data can sometimes load once at startup.

79. A developer ran an UPDATE without WHERE in production. How can this be prevented?

Remove routine direct write access, require reviewed migration/change tooling, least-privilege roles, approvals, transaction wrappers, row-count safeguards, and safe SQL client settings. Maintain point-in-time recovery, audit logs, and tested backups. For emergency access, use time-limited credentials and peer review.

80. Database latency rose after deployment. How will you isolate application versus database?

Separate connection-pool wait, network time, and database execution using traces and DB statement statistics. Run the exact parameterized query directly and compare its actual plan; inspect request/query counts and transaction duration introduced by the release. If DB execution is stable but application spans grow, investigate pool, serialization, network, or ORM behavior.

API Scalability and Design

81. An API works for 1,000 users but crashes for 100,000. How will you scale it?

Load-test to locate the first saturated resource and define SLOs. Keep API nodes stateless and scale horizontally, cache hot reads, optimize queries, queue asynchronous work, partition heavy data, and protect dependencies with bounded pools, rate limits, and backpressure. Scale from measured bottlenecks, not user count alone.

82. One API receives excessive traffic and affects everything. How will you isolate it?

Apply per-route/client rate limits, quotas, and concurrency limits; isolate it with separate pools, cache, queues, or deployment capacity. Prioritize critical traffic and shed excess work with 429/503 plus retry guidance. Optimize or precompute its expensive result after profiling.

83. A very large API response increases latency. How will you optimize it?

Return only required fields, paginate collections, remove duplicated nesting, and use compression for compressible content. Stream large exports or provide asynchronous download links, cache stable results, and keep binary assets outside JSON. Measure serialization, transfer, and client parsing separately.

84. Mobile clients retry aggressively and overload the backend. How will you handle it?

Return clear retryable versus permanent errors and Retry-After, enforce gateway rate limits, and cap server-side concurrency. Clients should use exponential backoff with jitter and a retry limit. Make mutating operations idempotent so unavoidable retries cannot duplicate work.

85. Refreshing creates duplicate orders or payments. How will you solve it?

Generate one idempotency key for the checkout operation and reuse it across refreshes/retries. Atomically store the key and response under a unique constraint and pass a stable key to the payment provider. Disable repeat UI submission for usability, but do not rely on the frontend for correctness.

86. How will you design APIs for sudden sales-event spikes?

Pre-scale tested stateless capacity, put CDN/cache in front of reads, queue non-immediate work, reserve inventory atomically, and enforce fair admission/rate limits. Protect databases and payment services with bounded concurrency and degrade optional features. Run realistic spike tests and prepare dashboards and rollback controls.

87. Synchronous APIs are slow because they call many downstream services. What can improve them?

Remove unnecessary calls, fetch independent dependencies in parallel within a bounded budget, cache stable results, batch requests, and set per-hop deadlines. Use an aggregator/read model or asynchronous workflow when an immediate complete result is unnecessary. Avoid parallelizing into an already saturated dependency.

88. Consumers report breaking changes after deployment. How will you maintain compatibility?

Make changes additive, keep field meaning stable, tolerate unknown fields, and deprecate with a published migration window. Use OpenAPI/schema diffs and consumer-driven contract tests in CI. Version only incompatible contracts and operate old/new versions until consumers migrate.

89. The same expensive API is called repeatedly with identical data. What can help?

Use HTTP caching with Cache-Control and ETags, CDN caching for public data, or application cache-aside for shared computed results. Coalesce concurrent identical requests and precompute when useful. Choose cache keys, TTL, invalidation, and authorization boundaries carefully.

90. Third-party integrations cause API timeouts. How will you protect the system?

Enforce a timeout smaller than the caller's remaining budget, isolate the provider with a bulkhead and circuit breaker, and retry only safe transient failures with jitter. Queue noninteractive work, cache/fallback when valid, and return a clear partial or accepted status. Reconcile operations with ambiguous outcomes.

91. How will you design rate limiting for public APIs?

Define limits by authenticated principal/API key and route, with IP fallback for anonymous callers. Implement token-bucket or sliding-window counters at the gateway using an atomic distributed store, return 429 and retry metadata, and support burst plus sustained limits. Add quotas, exemptions, monitoring, and protection against unbounded key cardinality.

92. Authentication increased API latency. How will you optimize it?

Trace token parsing, cryptography, key retrieval, session lookup, and policy calls separately. Validate signed JWTs locally, cache issuer keys with rotation support, reuse connections, avoid remote introspection on every request, and cache safe authorization metadata briefly. Never skip signature, expiry, issuer, or audience validation for speed.

93. How will you reduce latency for read-heavy APIs?

Profile first, then combine CDN/HTTP/application caching, optimized projections and indexes, read replicas, pagination, compression, and precomputed/materialized views. Remove N+1 calls and unnecessary downstream hops. Track hit rate, staleness, and p95/p99 rather than only average latency.

94. Large file uploads cause memory spikes. How will you redesign the API?

Do not buffer the whole file in application memory. Stream with strict size/type/time limits, or issue a signed URL so the client uploads directly to object storage. Process asynchronously, scan content, store metadata in the database, and return upload/job status.

95. Multiple systems update the same entity and APIs return inconsistent data. What will you do?

Establish one system of record and explicit ownership for each field. Route commands through the owner, use versioning/optimistic concurrency, and publish ordered change events with idempotent consumers. For eventual consistency, expose state/version clearly and reconcile drift instead of allowing uncontrolled multi-writer updates.

96. You need millions of API requests daily. What architecture changes do you suggest?

Convert daily volume into peak requests per second and measure the current limit. Use load-balanced stateless services, CDN/cache, efficient indexes and pools, asynchronous queues, horizontal scaling, rate limiting, observability, and failure isolation. Partition or add replicas only when measured data/storage constraints require them.

97. API retries duplicate backend processing. How will you prevent it?

Make the operation idempotent with a client-supplied key, atomically persist the key and outcome, and return the existing outcome on repetition. Use unique business constraints and idempotent message consumers. Retry policies should know which methods/errors are safe to repeat.

98. An API depends on multiple services and sees frequent partial failures. How will you design it?

Classify required and optional dependencies, give each a deadline and isolated pool, and fail fast with a circuit breaker. Return partial data with explicit status only when the contract permits it; otherwise use an async workflow or prebuilt read model. Avoid retrying every failed branch inside one request.

99. The API Gateway slows during traffic spikes. How will you scale it?

Run stateless gateway instances behind a load balancer and autoscale on concurrency and latency. Minimize filters, payload transformations, synchronous logging, and remote auth calls; reuse upstream connections and cache safe metadata. Put CDN/WAF/rate limiting at the edge and load-test gateway limits separately.

100. How will you monitor API performance and find bottlenecks?

Track request rate, errors, and latency percentiles by endpoint/version/status, plus CPU, memory, pools, queues, database time, cache hit rate, and downstream latency. Propagate trace IDs and sample distributed traces. Alert on SLO burn and business failures, then drill from dashboards to traces and logs.
