MongoDB Interview Questions

16 questions on documents, schema design, queries, indexes, aggregation, transactions, and scaling.

Q1. What is MongoDB?

MongoDB is a document-oriented NoSQL database. It stores records as BSON documents inside collections rather than rows inside tables. Documents can contain nested objects and arrays, which often map naturally to JavaScript application data.

Q2. What is the difference between MongoDB and a relational database?
MongoDBRelational database
Stores documents in collectionsStores rows in tables
Supports flexible document shapesUsually enforces a predefined table schema
Often embeds related dataOften normalizes data across related tables
Uses document queries and aggregation pipelinesUses SQL, joins, and relational operations

Neither model is universally better. The choice depends on relationships, consistency requirements, query patterns, and operational needs.

Q3. What are BSON, documents, and collections?

BSON is MongoDB's binary representation of JSON-like data and supports additional types such as dates, binary values, decimals, and ObjectIds. A document is one record, and a collection groups related documents.

{
  _id: ObjectId("..."),
  name: "Rishav",
  skills: ["Node.js", "MongoDB"],
  active: true
}
Q4. What is an ObjectId?

An ObjectId is MongoDB's commonly used default value for the _id field. It is a 12-byte value designed to be unique and includes a timestamp component. Applications may use another unique value for _id, but every document in a collection must have one.

Q5. Does MongoDB have a schema?

MongoDB has a flexible schema: documents in one collection can have different shapes. This does not mean schema design is unnecessary. Applications should define expected fields and types, and important rules can be enforced with MongoDB schema validation or an ODM such as Mongoose.

Q6. What is the difference between embedding and referencing?

Embedding stores related data inside the same document, giving atomic reads and writes and avoiding extra queries. Referencing stores another document's ID, reducing duplication and supporting relationships that grow independently or are shared by many records.

Embed data that is bounded and normally read with its parent. Reference large, frequently changing, many-to-many, or independently accessed data.

Q7. How do basic CRUD operations work? 
db.users.insertOne({ name: "Rishav", active: true });

db.users.find({ active: true });

db.users.updateOne(
  { name: "Rishav" },
  { $set: { active: false } }
);

db.users.deleteOne({ name: "Rishav" });

Use precise filters and appropriate operators. For updates, $set changes selected fields without replacing the entire document.

Q8. What is an index, and why is it important?

An index is a data structure that helps MongoDB locate and sort matching documents without scanning the entire collection. Indexes improve reads but consume storage and add work to inserts and updates, so they should be based on real query patterns.

db.users.createIndex({ email: 1 }, { unique: true });
Q9. Why does field order matter in a compound index?

A compound index stores multiple fields in a defined order. MongoDB can efficiently use its prefixes, so an index on { status: 1, createdAt: -1 } supports queries beginning with status, but is generally less useful for a query only on createdAt. Equality fields commonly come before sort and range fields.

Q10. What is the aggregation pipeline?

The aggregation pipeline processes documents through ordered stages. Common stages include $match for filtering, $project for reshaping, $group for aggregation, $sort, $limit, and $lookup for combining collections.

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$customerId", total: { $sum: "$amount" } } },
  { $sort: { total: -1 } }
]);
Q11. What is the difference between find() and aggregate()?

find() is ideal for retrieving documents with filtering, projection, sorting, and pagination. aggregate() is used for multi-stage transformations, grouping, calculated fields, analytics, and collection joins. Use the simplest operation that expresses the query clearly.

Q12. Are MongoDB operations atomic?

A write operation is atomic at the single-document level, even when it changes several fields. MongoDB also supports multi-document transactions when an operation must update multiple documents atomically, but transactions add overhead and should not replace good document design.

Q13. What are replication and replica sets?

A replica set maintains copies of the same data across multiple MongoDB servers. One primary accepts writes, while secondary members replicate its operation log. If the primary becomes unavailable, eligible members elect a new primary, improving availability and supporting disaster recovery.

Q14. What is sharding?

Sharding horizontally partitions a collection across multiple servers so storage and workload can scale beyond one machine. The shard key determines how documents are distributed. A poor shard key can create uneven data distribution, hot shards, or inefficient scatter-gather queries.

Q15. How do you investigate a slow MongoDB query?

Use explain("executionStats") to inspect the query plan. Compare documents examined with documents returned, check whether a collection scan occurred, confirm that filtering and sorting use an appropriate index, and look for large skips or unbounded results. Then validate any new index against production-like data and write costs.

db.users
  .find({ status: "active" })
  .sort({ createdAt: -1 })
  .explain("executionStats");
Q16. How does MongoDB aggregation work? Explain with an example using important operations.

MongoDB aggregation passes documents through a sequence of pipeline stages. Each stage receives the previous stage's output, performs an operation, and passes its result to the next stage.

Suppose each order contains a customerId, status, createdAt, and an items array. The following pipeline finds the five highest-spending customers for paid orders placed in 2026:

db.orders.aggregate([
  // 1. Filter early so later stages process fewer documents
  {
    $match: {
      status: "paid",
      createdAt: { $gte: ISODate("2026-01-01") }
    }
  },

  // 2. Turn every item in the items array into a separate document
  { $unwind: "$items" },

  // 3. Calculate the value of each order item
  {
    $set: {
      itemTotal: { $multiply: ["$items.price", "$items.quantity"] }
    }
  },

  // 4. Group items by customer and calculate totals
  {
    $group: {
      _id: "$customerId",
      totalSpent: { $sum: "$itemTotal" },
      totalItems: { $sum: "$items.quantity" },
      orderIds: { $addToSet: "$_id" }
    }
  },

  // 5. Join the matching customer document
  {
    $lookup: {
      from: "customers",
      localField: "_id",
      foreignField: "_id",
      as: "customer"
    }
  },
  { $unwind: "$customer" },

  // 6. Select and rename the fields returned to the client
  {
    $project: {
      _id: 0,
      customerId: "$_id",
      customerName: "$customer.name",
      totalSpent: 1,
      totalItems: 1,
      orderCount: { $size: "$orderIds" }
    }
  },

  // 7. Return only the top five customers
  { $sort: { totalSpent: -1 } },
  { $limit: 5 }
]);

Important operations: $match filters documents, $unwind expands an array, $set creates a calculated field, $group aggregates values, $lookup joins another collection, $project shapes the result, $sort orders it, and $limit restricts its size.

Performance tip: place selective $match stages near the beginning and create indexes for commonly filtered, sorted, and joined fields. Use explain("executionStats") to inspect the pipeline's execution plan.
