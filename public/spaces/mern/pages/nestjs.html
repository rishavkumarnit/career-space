NestJS — Interview Prep

Architecture, dependency injection, and the request lifecycle — the core concepts interviewers probe for Nest-based backend roles.

Q1. What is NestJS, and how does it differ from Express? ***

NestJS is a progressive Node.js framework for building server-side applications. It's TypeScript-first (plain JS is supported too), and borrows heavily from Angular's playbook — modules, decorators, and a built-in dependency injection container.

Under the hood, Nest doesn't replace Express — by default it runs on top of Express (Fastify is a drop-in alternative), using it as the underlying HTTP adapter. You can still reach the raw request/response via @Req()/@Res(), and existing Express middleware keeps working.

ExpressNestJS
ArchitectureUnopinionated — you design the structureOpinionated — Modules/Controllers/Providers enforced
LanguageJS, TS optionalTypeScript-first
Dependency injectionNone built-inBuilt-in IoC container
Scaling structureManual discipline requiredCLI conventions + module boundaries
HTTP layerIs the HTTP layerSits on top of Express or Fastify

Common follow-up: "so does Nest replace Express?" — no, it wraps it. Nest adds architecture and DI on top; Express (or Fastify) still handles the actual HTTP server underneath.

Q2. What are the core building blocks of a Nest application? ***

Every Nest app is assembled from three primitives:

Modules

@Module() — organizes related code into a cohesive unit. Declares which controllers and providers belong to it, what it imports from other modules, and what it exports for others to use. Every app has at least one root module (AppModule).

Controllers

@Controller() — handles incoming requests and returns responses. Routes are defined with method decorators (@Get(), @Post(), etc.) and delegate the actual work to providers rather than containing business logic themselves.

Providers

@Injectable() — services, repositories, factories, or anything else that can be injected as a dependency. Registered in a module's providers array and handed to whichever controller or provider asks for them in its constructor.

// cats.service.ts
@Injectable()
export class CatsService {
  private cats = [];
  findAll() { return this.cats; }
}

// cats.controller.ts
@Controller('cats')
export class CatsController {
  constructor(private catsService: CatsService) {}

  @Get()
  findAll() {
    return this.catsService.findAll();
  }
}

// cats.module.ts
@Module({
  controllers: [CatsController],
  providers: [CatsService],
})
export class CatsModule {}

The controller never instantiates CatsService itself — Nest's DI container hands it a ready-made instance, which is the whole point of Q3.

Q3. What is Dependency Injection in NestJS, and how does it work under the hood? ***

Dependency Injection means a class receives its dependencies from an external source instead of constructing them itself. In Nest, that external source is the Nest IoC (Inversion of Control) container.

At startup, Nest reads each class's constructor parameter types — using TypeScript's design-time type metadata, emitted via emitDecoratorMetadata and read back with reflect-metadata — resolves a matching registered provider for each parameter, and injects the instance automatically. Providers are singletons by default: one shared instance per application, reused everywhere they're injected.

Not every dependency is a class you can type-hint, though — config values, constants, or third-party clients need a custom token:

@Module({
  providers: [
    { provide: 'CONFIG_OPTIONS', useValue: { apiKey: '123' } },
    CatsService,
  ],
})
export class CatsModule {}

@Injectable()
export class CatsService {
  constructor(@Inject('CONFIG_OPTIONS') private config: { apiKey: string }) {}
}

Providers can be registered as useClass (swap implementations), useValue (a plain object/constant), or useFactory (computed at runtime, can itself have injected dependencies) — useful for things like picking a different service implementation per environment.

Common pitfall: forgetting to add a provider to its module's exports array. Providers are private to the module that declares them by default — another module that imports yours still can't inject that provider unless you explicitly export it.

Q4. Explain the NestJS request lifecycle — Middleware vs Guards vs Interceptors vs Pipes vs Exception Filters ***

This is the question Nest interviews circle back to most. Five different layers can touch a request, and the order matters:

      │
      ▼
  Guards                ← canActivate(): allow or deny the request

  Interceptors (pre)    ← runs before the handler
      │
      ▼

      │
      ▼
  Route Handler          (your controller method)
      │
      ▼
  Interceptors (post)   ← can transform the outgoing response
      │
      ▼
  Exception Filters     ← only invoked if something threw
      │
      ▼
  Response
LayerPurposeExample
MiddlewareRuns before routing; sees raw req/res, no knowledge of the target handlerLogging, cookie parsing
GuardscanActivate() decides if the request is allowed to proceedAuthGuard, RolesGuard
InterceptorsWrap the handler call; can modify the call or its result on the way outLogging, caching, response mapping
PipesValidate or transform arguments before the handler runsValidationPipe, ParseIntPipe
Exception FiltersCatch thrown exceptions and format the error responseHttpExceptionFilter

Common follow-up: "why can't Middleware do authorization?" — Middleware executes before Nest has matched the request to a route handler, so it has no ExecutionContext and can't read route-level metadata (like a custom @Roles() decorator). Guards run after routing is resolved and do get the full context, which is exactly why authorization belongs in a Guard, not Middleware.

Q5. What are Pipes used for, and how does the built-in ValidationPipe work? **

Pipes operate on the arguments going into a route handler, for two purposes: transformation (e.g. a route param string coerced to a number via ParseIntPipe) and validation (reject the request with a 400 if the input doesn't pass).

The standard pattern combines a DTO class, class-validator decorators, and a global ValidationPipe:

// create-cat.dto.ts
export class CreateCatDto {
  @IsString()
  name: string;

  @IsInt()
  @Min(0)
  age: number;
}

// main.ts
app.useGlobalPipes(new ValidationPipe({ whitelist: true }));

// cats.controller.ts
@Post()
create(@Body() dto: CreateCatDto) {
  return this.catsService.create(dto);
}

whitelist: true strips any incoming properties that aren't declared on the DTO — a cheap guard against clients sneaking in fields your handler never asked for.

Common pitfall: adding class-validator decorators to a DTO and expecting validation "for free." The decorators are inert until a ValidationPipe is actually wired up (globally, or per-route via @UsePipes()) — without it, invalid payloads sail straight through to the handler.

Q6. What are Guards used for? **

Guards decide whether a given request should reach the route handler at all — implementing CanActivate, returning (or resolving to) a boolean. They're applied with @UseGuards() at the method, controller, or global level.

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    return !!request.headers['authorization'];
  }
}

@UseGuards(AuthGuard)
@Get('profile')
getProfile() { /* ... */ }

Role-based access typically pairs a Guard with a custom @Roles() decorator (built on SetMetadata) and Nest's Reflector to read that metadata back inside the guard — reflector.getAllAndOverride('roles', [...]) — so one generic RolesGuard can enforce different role requirements per route.

Why not just do this in Middleware? Same answer as Q4 — Guards run with full route context (including custom decorator metadata), Middleware doesn't.

Q7. What are Provider scopes in NestJS — DEFAULT vs REQUEST vs TRANSIENT? *
ScopeLifetimeWhen to use
DEFAULT (singleton)One instance for the whole app, created once at bootstrapThe default — almost everything, for performance
REQUESTA new instance per incoming request, discarded after the responseProvider needs per-request state, e.g. data read off the request itself
TRANSIENTA new instance every time the provider is injectedRare — stateful helper that must never be shared, even within one request
@Injectable({ scope: Scope.REQUEST })
export class CatsService {}

Common pitfall: reaching for REQUEST scope casually. Scope bubbles up the injection chain — any provider that depends (even indirectly) on a request-scoped provider becomes request-scoped too, so a single request-scoped dependency deep in the graph can force re-instantiation of a large chunk of the app on every request. Default to singleton unless you have a concrete need for per-request state.
