Q1. What is the difference between debouncing and throttling?

Execution frequency: debouncing postpones execution until after a period of inactivity — the function only runs once the calls have stopped coming in for a set delay. Throttling instead limits execution to a fixed number of times per interval, running immediately and then ignoring further calls until the interval elapses.

Use cases: debouncing suits tasks that shouldn't fire repeatedly in quick succession, e.g. an API call triggered by a search input. Throttling suits controlling the rate of handlers on high-frequency events like scroll or resize, where you still want periodic updates rather than silence until the user stops.

Debounce

const input1 = document.querySelector("#input1");

input1.addEventListener("input", () => {
  console.log("input..."); // runs hundreds of times!
});

function debounce(func, delay) {
  let timeout;
  return function() {
    clearTimeout(timeout);   // clear previous timer
    timeout = setTimeout(() => {
      func();                // run after delay
    }, delay);
  };
}

// Example usage:
const searchHandler = debounce(() => {
  console.log("Searching...");
}, 3000);

input1.addEventListener("input", searchHandler);

Every keystroke resets the timer, so func only fires once the user has stopped typing for the full delay — ideal for search-as-you-type API calls where you don't want a request per keystroke.

Throttle

window.addEventListener("scroll", () => {
  console.log("scrolling");
});

function throttle(func, limit) {
  let inThrottle;
  return function() {
    if (!inThrottle) {
      func();                 // run immediately
      inThrottle = true;
      setTimeout(() => (inThrottle = false), limit);
    }
  };
}

// Example usage:
const scrollHandler = throttle(() => {
  console.log("fetching...");
}, 1000);

window.addEventListener("scroll", scrollHandler);

The first call runs immediately, then a cooldown flag blocks further calls until the limit expires — so func runs at most once per interval no matter how many scroll events fire in between.

Source: GeeksforGeeks — Difference between Debouncing and Throttling

Q2. What's the difference between localStorage, sessionStorage, and cookies?

All three store data in the browser, but they differ in capacity, lifetime, scope, server interaction, and security.

Feature localStorage sessionStorage Cookies
Storage capacity Usually about 5–10 MB per origin Usually about 5 MB per origin and tab About 4 KB per cookie
Lifespan / expiry Persists until explicitly cleared by the application, browser, or user Exists for the page session and is cleared when that tab or window is closed Can be a session cookie or expire at a configured time using Expires or Max-Age
Server interaction Not automatically sent to the server Not automatically sent to the server Automatically sent with matching HTTP requests, subject to domain, path, and cookie rules
Access / scope Shared by same-origin pages and tabs Restricted to the same origin and the specific browser tab Available to matching domains and paths; JavaScript access depends on HttpOnly
Security Accessible to JavaScript, so an XSS attack can read it Accessible to JavaScript, so an XSS attack can read it Supports HttpOnly, Secure, and SameSite; still requires CSRF and XSS protection
API setItem(), getItem(), removeItem(), clear() setItem(), getItem(), removeItem(), clear() Read/write through document.cookie, response headers, or a cookie library
Best suited for Persistent client preferences such as theme or language Temporary tab-specific state such as a multi-step form Sessions, authentication, and small values the server needs

Security recommendation: avoid storing sensitive data or long-lived authentication tokens in Web Storage. For session authentication, a properly configured HttpOnly, Secure, and SameSite cookie is generally safer because JavaScript cannot read an HttpOnly cookie.

Important note: storage limits vary by browser, device, and user settings. The capacity values above are common approximations, not guaranteed limits.

Q3. What's the architectural difference between Node.js and the browser?

Both run JavaScript through an engine, but everything outside that engine — how async work actually gets done — is implemented differently.

Node.jsBrowser
Core engineV8 (Google)V8 (Chrome/Edge), SpiderMonkey (Firefox), or JavaScriptCore (Safari)
Asynchronous layerlibuv — a multi-platform C libraryBuilt-in Web APIs managed by the browser runtime
Purposelibuv manages the event loop, thread pool, file system I/O, and network socketsThe browser implements the event loop, DOM events, timers (setTimeout), and fetch requests using native C++ subsystems

Common follow-up: "so is the event loop spec-mandated?" — no, the event loop isn't part of the JavaScript language spec at all; it's a runtime concept. That's why Node (via libuv) and browsers (via their own C++ internals) are free to implement it differently, e.g. Node's distinct timers/poll/check phases vs. the browser's simpler task-queue-plus-microtask-queue model.

Q4. Why do callbacks "lose" this — and is that a closure problem?

No. A closure remembers variables from the place where a function was created. this follows separate rules.

Normal function: this comes from the call

const user = {
  name: "Rishav",
  greet() {
    console.log(this.name);
  }
};

user.greet(); // "Rishav"

Here, user.greet() means “call greet using user.” Therefore, inside greet, this is user.

But when you pass the method as a callback, it is no longer called through user:

setTimeout(user.greet, 1000); // this is lost

setTimeout receives only the function. It does not know that it originally belonged to user. Therefore this.name is usually undefined.

Arrow function: this comes from the surrounding scope

const user = {
  name: "Rishav",
  greet: () => {
    console.log(this.name);
  }
};

user.greet(); // not "Rishav"

An arrow function does not get its own this. It uses this from the place where it was created. An object literal does not provide a new this, so the arrow does not point to user.

How to fix a callback

setTimeout(user.greet.bind(user), 1000);

// or
setTimeout(() => user.greet(), 1000);

Easy rule: use a normal function for an object method that needs its object’s this. Use an arrow function when you want to keep this from the surrounding function.

Q5. Predict the output — sync code, an async function, a Promise, and setTimeout 
console.log(1);

async function test() {
  console.log(2);

  Promise.resolve().then(() => console.log(3));

  setTimeout(() => console.log(4), 0);
}

test();

console.log(5);

Output:

1
2
5
3
4

Three execution tiers are in play, and they always run in this order: all synchronous code, then every queued microtask, then one macrotask — repeating.

  • Synchronous code runs first, top to bottom — including the body of an async function. test has no await anywhere in it, so calling test() never yields control back to the caller; its entire body runs synchronously in place, exactly like a normal function call. That's why 2 logs before 5 — the whole test() call (print 2, schedule the Promise callback, schedule the timeout) finishes before the script even reaches console.log(5).
  • Microtasks (Promise callbacks) run next — but only once the call stack is completely empty, i.e. after the entire synchronous script (including that console.log(5)) has finished. That's why 3 logs after 5, not right after 2.
  • setTimeout, even with a delay of 0, is a macrotask — it always waits for the microtask queue to fully drain first. That's why 4 is last, no matter what delay was passed.

Common pitfall: assuming setTimeout(fn, 0) means "run next." It actually means "run as soon as possible, but only after the current script and every pending microtask" — a Promise callback registered even after a 0ms timeout still runs before it, because the microtask queue always fully drains before the next macrotask is picked up.

Q6. Predict the output — useState batching, stale closures, and the useEffect cleanup order 
import React, { useState, useEffect } from "react";

export default function App() {
  const [count, setCount] = useState(0);
  console.log("Render:", count);

  useEffect(() => {
    console.log("Effect Start:", count);
    return () => {
      console.log("Cleanup:", count);
    };
  }, [count]);

  console.log("After useEffect:", count);

  const handleClick = () => {
    console.log("Click Start:", count);
    setCount(count + 1);
    setCount(count + 1);
    setCount((c) => c + 1);
    console.log("Click End:", count);
  };

  return (
    <div>
      <h1>{count}</h1>
      <button onClick={handleClick}>Click</button>
    </div>
  );
}

On initial mount

Render: 0
After useEffect: 0
Effect Start: 0

The component function body runs top to bottom during the render phase — the useEffect(...) call only registers the effect at this point, it doesn't run the callback. That's why "After useEffect: 0" (an ordinary console.log sitting right after useEffect in the function body) logs before "Effect Start: 0" — the effect itself is deferred until after React commits the DOM and the browser paints.

After one click

Click Start: 0
Click End: 0
Render: 2
After useEffect: 2
Cleanup: 0
Effect Start: 2

Why count ends up 2, not 3: count inside handleClick is a plain constant captured from this render's closure — it stays 0 for the entire lifetime of that function call, no matter how many times setCount is called inside it. The first two calls, setCount(count + 1), both evaluate to setCount(0 + 1) — they're the same "replace state with 1" instruction issued twice, not two separate increments. Only the third call, the functional updater setCount((c) => c + 1), reads React's actual latest queued value instead of the stale closure — it takes the 1 left behind by the previous two calls and produces 2. This is exactly why the functional-updater form exists: it's the only one of the three that's safe to chain.

Why "Click Start"/"Click End" both log 0: React batches all three setCount calls inside the event handler and applies them in a single re-render after handleClick finishes running — so nothing inside the handler itself ever observes the updated value, only the next render does.

Why "Cleanup: 0" logs after the new render, not before it: React always fully re-runs the component function (the render phase — "Render: 2", "After useEffect: 2") before it touches effects at all. Only in the subsequent commit/effects phase does it clean up the outgoing effect — using the count = 0 that was closed over when that effect was originally created — and then run the new effect, which closes over the new count = 2. Cleanup always fires immediately before the next effect, never immediately when the state changes.

Common pitfall: expecting three setCount calls to add up to +3, and expecting the cleanup log to fire "live" the moment you click rather than one render-cycle later, right before the next effect runs.

Q7. What is TypeScript, and what does it actually give you over JavaScript?

TypeScript is a superset of JavaScript that adds static types, then compiles down to plain JavaScript before it ever runs — browsers and Node execute the compiled output, never the .ts source directly.

function add(a: number, b: number) {
  return a + b;
}

add(2, "3"); // compile error — caught before the code ever runs
// JS equivalent would silently return "23" (string concatenation)

The core value isn't a new language feature — it's shifting a whole class of bugs (wrong argument types, typos in property names, calling a method that doesn't exist on this shape) from a runtime crash in production to a red squiggle in the editor. It also unlocks much richer autocomplete and safer refactors, since the tooling knows the exact shape of every variable, not just whatever value it currently holds.

Common follow-up: "so does TypeScript add any runtime type checking?" — no. Types are fully erased at compile time (with rare exceptions like enums) — there is zero runtime cost and zero runtime safety net. If an API response doesn't actually match the type you told TypeScript to expect, nothing will catch that at runtime; TypeScript only ever checked what your own code claimed.

Q8. interface vs type — what's the actual difference?

For a plain object shape, they're close to interchangeable — the real differences show up at the edges.

interfacetype
What it can describeObject, function, and class shapes onlyAnything — object shapes, unions, tuples, primitives, mapped types
CombiningextendsIntersection (&)
Re-opening the same nameDeclaration merging — allowed, members combineError — a type alias can't be declared twice
Conflicting members when combinedextends gives a clear compile errorIntersecting conflicting primitive types silently collapses to never
interface User { name: string }
interface User { age: number }   // merges — User now has both name and age

type Id = string | number;        // type can express a union; interface can't

Common follow-up: "so which should I default to?" — most style guides land on: prefer interface for public object/class shapes that might need extending later (cleaner error messages, declaration merging can be useful for augmenting third-party types), and prefer type for unions, tuples, and anything that isn't a plain object shape, since interface can't express those at all.

Q9. any vs unknown vs never — when do you use which?
TypeWhat it meansUsable without checking first?
anyOpts the value out of type checking entirelyYes — anything goes, no compiler help at all
unknownCould be anything, but must be proven before useNo — must narrow first (typeof/instanceof/assertion)
neverA value that can never actually occurN/A — nothing is ever assignable to it except itself
function handleAny(x: any) {
  x.toUpperCase(); // compiles fine — even if x is actually a number, this blows up at runtime
}

function handleUnknown(x: unknown) {
  x.toUpperCase();               // compile error — x isn't proven to be a string yet
  if (typeof x === "string") {
    x.toUpperCase();             // fine — narrowed to string inside this branch
  }
}

function fail(): never {
  throw new Error("always throws — never returns normally");
}

never also shows up as the type TypeScript infers when a union has been narrowed down to nothing left — useful for exhaustiveness checks, where assigning a switch's default case to a never-typed variable makes the compiler flag it if a new union member is ever added and forgotten in the switch.

Common pitfall: reaching for any just to silence an error quickly. It doesn't stay contained to that one line — the "any-ness" propagates through everything that touches the value afterward, quietly turning off type checking for the rest of that call chain too. unknown is almost always the safer choice when a type genuinely isn't known yet, since it forces the check instead of skipping it.

Q10. What are generics, and why do you actually need them?

Generics let a function, type, or class work over a range of types while still preserving the relationship between what goes in and what comes out — instead of hardcoding one specific type, or throwing that relationship away with any.

function firstAny(arr: any[]): any {
  return arr[0];
}
const a = firstAny(["a", "b"]); // type: any — TypeScript has no idea it's a string

function firstOf<T>(arr: T[]): T {
  return arr[0];
}
const b = firstOf(["a", "b"]); // type: string — inferred from the actual argument
const c = firstOf([1, 2, 3]);   // type: number — same function, different T

T here is a placeholder filled in per call site, based on whatever's actually passed in — firstOf is one function definition, but the compiler checks each call as if it were written specifically for that call's type.

Common follow-up: "how is that different from just using any?" — any discards type information entirely, so the compiler can't help with anything downstream. A generic keeps the information flowing: the return type is still statically tied to whatever type was passed in, so misusing the result (e.g. calling .toUpperCase() on what firstOf returned from a number[]) is still caught at compile time.

Q11. TypeScript's structural typing ("duck typing") — why can two unrelated types be interchangeable?

TypeScript compares types by their shape — the properties and methods actually present — not by name or an explicit declared relationship. This is different from a nominal type system (Java, C#), where two classes are only compatible if one explicitly extends or implements the other, even if their members are identical.

interface Point { x: number; y: number }

class Vector {
  constructor(public x: number, public y: number) {}
}

function printPoint(p: Point) {
  console.log(p.x, p.y);
}

printPoint(new Vector(1, 2)); // fine — Vector was never declared to implement Point,
                               // but it has the same shape, so it's accepted

Vector never mentions Point anywhere, yet a Vector instance satisfies it — as far as TypeScript is concerned, "has an x: number and a y: number" is what it means to be a Point.

Common pitfall / interesting exception: structural typing normally allows extra properties too (having more than required still satisfies the shape) — except when passing an object literal directly to a typed parameter. That specific case triggers "excess property checking," a stricter, typo-catching rule that doesn't apply once the same object is assigned to a variable first and passed by reference instead.

Q12. Type narrowing — how does TypeScript know which branch you're in?

When a variable's declared type is a union (e.g. string | number), TypeScript won't let you use members specific to just one side of it until the code's control flow proves which one you're dealing with at that point — that's narrowing.

function format(value: string | number) {
  if (typeof value === "string") {
    return value.toUpperCase(); // narrowed to string here
  }
  return value.toFixed(2);      // only number left, narrowed by elimination
}

Common narrowing tools: typeof for primitives, instanceof for class instances, the in operator for checking whether a property exists on an object (useful for distinguishing between object shapes), and equality checks against literal values. For anything more involved, a custom type guard — a function that returns arg is SomeType instead of a plain boolean — lets you package up a reusable check that TypeScript will trust and apply at every call site.

interface Cat { meow(): void }
interface Dog { bark(): void }

function isCat(pet: Cat | Dog): pet is Cat {
  return (pet as Cat).meow !== undefined;
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) {
    pet.meow(); // narrowed to Cat inside this branch
  } else {
    pet.bark(); // narrowed to Dog by elimination
  }
}

Common pitfall: reaching for typeof to distinguish between two custom object shapes — it can't; every plain object reports "object" regardless of which interface it matches. That's exactly the situation the in operator or a custom type predicate is for.

Q13. Quick reference — Partial, Pick, Omit, Record, Readonly 
interface User {
  id: number;
  name: string;
  email: string;
}
Utility typeWhat it producesTypical use
Partial<User>Every property becomes optionalAn update/patch payload where only changed fields are sent
Required<User>Every property becomes mandatoryUndoing a Partial, or enforcing full objects
Pick<User, "id" | "name">Only the listed keysA trimmed-down view for a list row or a public API response
Omit<User, "email">Every key except the listed onesStripping sensitive/internal fields before sending a response
Record<string, User>An object type with arbitrary keys, all mapped to UserLookup maps/dictionaries, e.g. users indexed by id
Readonly<User>Every property becomes read-onlyPreventing reassignment after creation, e.g. Redux-style state

Common pitfall: Readonly<T> (and the readonly modifier generally) is shallow — it only blocks reassigning the top-level property itself. const u: Readonly<User> = ...; u.name = "x" is a compile error, but if User had a nested object or array property, its contents could still be mutated freely through that property.

Q14. What is the difference between REST and GraphQL, and when would you use each?

REST models an API as multiple resource-oriented endpoints, such as GET /users/42 and GET /users/42/orders. The server decides the response shape, and HTTP methods and status codes express the operation and its result.

GraphQL normally exposes a single endpoint. The client sends a typed query describing exactly which fields and related objects it needs, and resolvers obtain that data from the underlying services or databases.

AreaRESTGraphQL
Data fetchingFixed response per endpoint; may over-fetch or require several requestsClient requests exactly the fields it needs, including related data
API contractEndpoint documentation or an OpenAPI specificationStrongly typed, introspectable schema
CachingWorks naturally with standard HTTP and CDN cachingOften requires application-aware client or server caching
Error handlingPrimarily uses HTTP status codesCan return partial data together with an errors array
ComplexitySimple and familiar for resource-based CRUD APIsRequires schema design, resolvers, query limits, and protection against expensive nested queries
VersioningOften uses URL or header versionsUsually evolves by adding fields and deprecating old ones

Choose REST for straightforward CRUD services, public HTTP APIs, file operations, and cases where simple infrastructure and HTTP caching matter most. Choose GraphQL when several clients need different data shapes or a screen must combine deeply related data without many round trips.

Interview point: GraphQL is not automatically faster than REST. It can reduce over-fetching and network requests, but poorly designed resolvers can create N+1 queries or expensive requests. The best choice depends on the clients, data relationships, caching requirements, and operational complexity; the two approaches can also coexist.
