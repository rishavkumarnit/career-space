1. Core Java
  • Explain the four pillars of OOP with practical examples.
  • What is the difference between abstraction and encapsulation?
  • Interface vs abstract class?
  • Method overloading vs method overriding?
  • What is runtime polymorphism?
  • Why is String immutable in Java?
  • String vs StringBuilder vs StringBuffer?
  • What is the difference between == and equals()?
  • Why should hashCode() be overridden when equals() is overridden?
  • What are checked and unchecked exceptions?
  • throw vs throws?
  • What is the purpose of final, finally, and finalize?
  • What is an immutable class, and how would you create one?
  • What are access modifiers in Java?

Answers

  1. OOP pillars: encapsulation hides state behind methods; abstraction exposes only essential behavior; inheritance reuses or specializes behavior; polymorphism lets one interface invoke different implementations. For example, several PaymentProcessor implementations can process different payment methods.
  2. Abstraction vs encapsulation: abstraction focuses on what an object does and hides implementation complexity. Encapsulation bundles data with behavior and controls access to protect valid state.
  3. Interface vs abstract class:
    FeatureAbstract ClassInterface
    InheritanceSupports single class inheritance—a class can extend only one class.Supports multiple contracts—a class can implement multiple interfaces.
    MethodsCan contain both abstract methods without bodies and concrete methods with implementations.Originally supported abstract methods only. Java 8 added default and static methods; Java 9 added private helper methods.
    Variables / stateCan contain instance variables, including non-static and non-final fields, and therefore maintain object state.Fields are implicitly public static final, so they are constants rather than per-object state.
    ConstructorsAllowed and used to initialize the inherited state when a concrete subclass is instantiated.Not allowed because an interface is not instantiated and does not maintain instance state.
    Access modifiersMembers can use private, package-private, protected, or public, where applicable.Abstract methods are implicitly public. Interface methods may also be public default, public static, or private in modern Java.
    KeywordsDeclared with abstract class and inherited using extends.Declared with interface and adopted by a class using implements.

    When to use: use an interface to define a capability or contract that unrelated classes can implement. Use an abstract class when closely related classes need shared state, construction logic, or a common partial implementation.

  4. Overloading vs overriding: overloading uses the same method name with different parameter lists and is resolved at compile time. Overriding replaces inherited behavior with the same signature and is selected at runtime.
  5. Runtime polymorphism: a parent/interface reference calls the overridden method of the actual object, such as PaymentProcessor p = new CardProcessor(); p.pay();.
  6. String immutability: it enables safe sharing, string pooling, cached hash codes, thread safety, and security for values used in paths, class loading, and networking. Operations create a new string instead of changing the original.
  7. String classes: String is immutable. StringBuilder is mutable and fastest for single-threaded construction; StringBuffer is synchronized and usually slower.
  8. == vs equals(): for objects, == compares references while equals() compares logical equality when overridden. For primitives, == compares values.
  9. equals/hashCode contract: equal objects must return the same hash code so hash collections can locate them in the correct bucket. Override both together.
  10. Checked vs unchecked exceptions: checked exceptions must be caught or declared. Unchecked RuntimeExceptions usually indicate programming errors or invalid state and need not be declared.
  11. throw vs throws: throw raises one exception object; throws declares possible exceptions in a method signature.
  12. final, finally, finalize: final prevents reassignment, overriding, or inheritance; finally runs cleanup after try/catch. finalize() was unreliable and is deprecated—use try-with-resources or cleaners.
  13. Immutable class: make the class final, fields private and final, initialize them in the constructor, provide no setters, and defensively copy mutable inputs and outputs.
  14. Access modifiers: private is class-only, default is package-only, protected adds subclasses, and public is accessible everywhere.

Practical OOP example

interface PaymentProcessor {                 // abstraction/contract
    void pay(BigDecimal amount);
}

final class CardProcessor implements PaymentProcessor {
    private BigDecimal dailyTotal = BigDecimal.ZERO; // encapsulated state

    @Override
    public void pay(BigDecimal amount) {     // runtime polymorphism
        if (amount.signum() <= 0) throw new IllegalArgumentException();
        dailyTotal = dailyTotal.add(amount);
    }
}

An interview answer should define the concept, show how Java implements it, give a real use case, and mention a limitation—for example, prefer composition over inheritance when there is no genuine “is-a” relationship.

2. Collections
  • What is the difference between List, Set, and Map?
  • ArrayList vs LinkedList?
  • HashMap vs Hashtable?
  • How does HashMap work internally?
  • What happens when two keys have the same hash?
  • HashMap vs ConcurrentHashMap?
  • HashSet vs TreeSet?
  • Comparable vs Comparator?
  • What is the time complexity of common HashMap operations?
  • How would you remove duplicates from a List?
  • How would you sort a list of custom objects?

Answers

  1. List is ordered and allows duplicates; Set stores unique elements; Map associates unique keys with values.
  2. ArrayList offers O(1) indexed access and is usually the default. LinkedList has O(n) access and helps only for frequent insertions/removals through an existing iterator or at the ends.
  3. HashMap is unsynchronized and permits one null key; legacy Hashtable synchronizes whole operations and permits no nulls. Prefer ConcurrentHashMap for concurrency.
  4. HashMap spreads a key hash into an array bucket, then uses equals() to find the key. It resizes after its load threshold and may treeify heavily collided buckets in Java 8+.
  5. Same-bucket keys form a collision chain, initially a list and potentially a red-black tree. Both hash and equality are checked, so distinct keys remain distinct.
  6. HashMap is not thread-safe. ConcurrentHashMap supports concurrent reads and fine-grained updates and provides atomic methods such as computeIfAbsent.
  7. HashSet provides average O(1) unordered membership. TreeSet keeps elements sorted with O(log n) operations and requires comparable elements or a comparator.
  8. Comparable defines a type's natural order through compareTo; Comparator supplies reusable external ordering rules through compare.
  9. HashMap get/put/remove average O(1); a treeified collision bucket is O(log n). Resizing is O(n), and malicious or poor hashes degrade performance.
  10. Use new ArrayList<>(new LinkedHashSet<>(items)) to preserve encounter order, or stream().distinct().toList().
  11. Use list.sort(Comparator.comparing(Employee::getSalary).thenComparing(Employee::getName)), or implement Comparable for one natural ordering.

Collection selection example

List<Order> orderedResults = new ArrayList<>();       // ordered, duplicates allowed
Set<String> uniqueEmails = new HashSet<>();          // fast uniqueness checks
Map<Long, User> usersById = new HashMap<>();         // key-based lookup
Map<String, LongAdder> counters = new ConcurrentHashMap<>(); // concurrent access

Choose a collection from required behavior—ordering, uniqueness, lookup pattern, concurrency, and memory—not merely from familiarity. State expected time complexity, but note that hashing quality, resizing, and contention affect real performance.

3. Java 8+ and Streams
  • What is the Java Streams API?
  • What are the important features introduced in Java 8?
  • What is a functional interface?
  • What is a lambda expression?
  • What is the difference between map() and flatMap()?
  • What are intermediate and terminal operations?
  • filter() vs map()?
  • How does reduce() work?
  • What is Optional, and why is it used?
  • What are method references?
  • Find duplicate elements using Streams.
  • Find the second-highest number using Streams.
  • Group objects based on a particular field.
  • Find the frequency of elements using Streams.

Answers

  1. Java Streams API: a Stream is a single-use pipeline that processes data from a source such as a collection, array, file, or generated sequence. A stream does not store elements and normally does not modify its source. It describes what should happen through operations such as filtering, mapping, sorting, and aggregation.

    List<String> result = names.stream()
    .filter(name -> name.startsWith("A")) // keep matching names
    .map(String::toUpperCase)             // transform each name
    .sorted()                             // order the results
    .collect(Collectors.toList());        // terminal operation

    Intermediate operations are lazy; processing begins only when a terminal operation runs. A consumed stream cannot be reused. Parallel streams can split work across threads, but should be used only after measuring performance and confirming that operations are stateless, associative, and thread-safe.

  2. Important Java 8 features:

    • Lambda expressions and functional interfaces for passing behavior as data.
    • Streams API for declarative collection processing.
    • Method references as concise alternatives to simple lambdas.
    • Default and static interface methods for evolving interfaces without breaking implementations.
    • Optional for explicitly representing a possibly absent result.
    • java.time, an immutable and thread-safe date/time API.
    • CompletableFuture for composing asynchronous operations.
    • Collection and Map enhancements such as forEach, removeIf, computeIfAbsent, and merge, plus Base64 utilities and repeating/type annotations.

    The main shift was support for a functional, declarative programming style alongside Java's object-oriented model.

  3. Functional interface: an interface with exactly one abstract method. It can still contain any number of default, static, and inherited Object methods. Lambdas and method references provide implementations of functional interfaces. @FunctionalInterface is optional, but makes the compiler enforce the rule.

    @FunctionalInterface
interface Calculator {
    int calculate(int a, int b);

    default String description() { return "Performs a calculation"; }
}

Calculator add = (a, b) -> a + b;
System.out.println(add.calculate(4, 3)); // 7

    Common built-in types are Predicate<T>, Function<T,R>, Consumer<T>, and Supplier<T>.

  4. Lambda expression: a compact implementation of a functional interface. Its syntax is (parameters) -> expression or (parameters) -> { statements; }. The target functional-interface type supplies the parameter and return types.

    Predicate<Integer> isEven = number -> number % 2 == 0;
Comparator<String> byLength =
    (first, second) -> Integer.compare(first.length(), second.length());

    Lambdas can capture local variables only when those variables are final or effectively final. Unlike an anonymous class, a lambda does not introduce a new this; this refers to the enclosing object.

  5. map() vs flatMap(): map transforms each input into exactly one output. flatMap transforms each input into a stream and then flattens all nested streams into one stream.

    List<String> names = employees.stream()
    .map(Employee::getName)
    .collect(Collectors.toList());

List<String> skills = employees.stream()
    .flatMap(employee -> employee.getSkills().stream())
    .distinct()
    .collect(Collectors.toList());

    If every employee has a list of skills, map(Employee::getSkills) produces a Stream<List<String>>; flatMap produces a usable Stream<String>.

  6. Intermediate vs terminal operations:

    • Intermediate operations return another stream and are lazy: filter, map, flatMap, distinct, sorted, limit, and peek.
    • Terminal operations start pipeline execution and produce a result or side effect: collect, reduce, count, forEach, findFirst, anyMatch, and min/max.
    long count = names.stream()
    .filter(name -> name.length() > 5) // lazy intermediate step
    .count();                           // terminal step starts execution

    Short-circuiting terminal operations such as findFirst and anyMatch may stop without processing every element.

  7. filter() vs map(): filter decides whether an element remains in the stream, so its argument is a Predicate<T> returning boolean. map converts every retained element into another value using a Function<T,R>, and may change the stream's element type.

    List<String> adultNames = people.stream()
    .filter(person -> person.getAge() >= 18) // Person -> boolean
    .map(Person::getName)                     // Person -> String
    .collect(Collectors.toList());

  8. reduce(): reduction combines stream elements into one value using an associative accumulator. The identity is the neutral starting value—for addition it is 0; for multiplication it is 1.

    int total = numbers.stream()
    .reduce(0, Integer::sum);

Optional<Integer> maximum = numbers.stream()
    .reduce(Integer::max);

    The overload without an identity returns Optional because an empty stream has no result. For parallel execution, the accumulator/combiner must be associative and the identity must be valid; otherwise the result can be incorrect. Use collectors rather than repeated string or collection concatenation when mutable reduction is more efficient.

  9. Optional: a container that either contains one non-null value or is empty. It is most useful as a return type when absence is a valid outcome and forces the caller to handle that outcome explicitly.

    User user = userRepository.findByEmail(email)
    .orElseThrow(() -> new UserNotFoundException(email));

String city = findUser(id)
    .map(User::getAddress)
    .map(Address::getCity)
    .orElse("Unknown");

    Prefer orElseGet when creating the fallback is expensive because it is evaluated lazily. Do not call get() without checking, and generally avoid using Optional for entity fields, DTO fields, or method parameters.

  10. Method references: a shorter form of a lambda that only invokes an existing method or constructor.

    TypeExampleEquivalent lambda
    Static methodInteger::parseIntvalue -> Integer.parseInt(value)
    Bound instance methodSystem.out::printlnvalue -> System.out.println(value)
    Unbound instance methodString::trimvalue -> value.trim()
    ConstructorArrayList::new() -> new ArrayList<>()

    Use a method reference when it remains clearer than the equivalent lambda.

  11. Find duplicate elements: build a frequency map, then keep keys whose count is greater than one. This returns each duplicated value once and does not mutate external state.

    List<Integer> numbers = List.of(1, 2, 3, 2, 4, 1, 2);

Set<Integer> duplicates = numbers.stream()
    .collect(Collectors.groupingBy(
        Function.identity(),
        Collectors.counting()))
    .entrySet().stream()
    .filter(entry -> entry.getValue() > 1)
    .map(Map.Entry::getKey)
    .collect(Collectors.toSet());

// Result: [1, 2]

  12. Find the second-highest distinct number: remove duplicates, sort in descending order, skip the highest, and read the next value.

    int secondHighest = numbers.stream()
    .distinct()
    .sorted(Comparator.reverseOrder())
    .skip(1)
    .findFirst()
    .orElseThrow(() ->
        new IllegalArgumentException("At least two distinct values are required"));

    This solution is easy to explain but sorting costs O(n log n). A one-pass solution is preferable for a very large collection when performance is critical.

  13. Group objects by a field: Collectors.groupingBy uses a classifier function to create a map from each group key to its matching objects.

    Map<String, List<Employee>> byDepartment = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

Map<String, Double> averageSalaryByDepartment = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.averagingDouble(Employee::getSalary)));

    A downstream collector can count, sum, average, map, or otherwise aggregate each group instead of returning lists.

  14. Find the frequency of elements: group equal elements using identity as the key and count the elements in every group.

    List<String> words = List.of("java", "sql", "java", "spring");

Map<String, Long> frequency = words.stream()
    .collect(Collectors.groupingBy(
        Function.identity(),
        LinkedHashMap::new, // preserve first-encounter order
        Collectors.counting()));

// {java=2, sql=1, spring=1}

    If order is irrelevant, omit LinkedHashMap::new and use the two-argument groupingBy overload.

4. Multithreading and Concurrency
  • Process vs thread?
  • How do you create a thread in Java?
  • Runnable vs Callable?
  • What is ExecutorService?
  • What is synchronization?
  • What is a race condition?
  • What is deadlock, and how can you prevent it?
  • synchronized vs volatile?
  • What is ConcurrentHashMap?
  • How would you execute multiple tasks concurrently?
  • What happens if multiple threads modify the same resource?

Answers

  1. Process vs thread: a process is an independently running program with its own virtual address space, resources, and isolation boundary. A thread is an execution path inside a process; threads share the heap and open resources but each has its own stack, program counter, and local variables.

    Creating or switching processes is generally heavier than working with threads. Threads communicate cheaply through shared memory, but that shared memory creates visibility, race-condition, and synchronization problems. A failure in one process is better isolated, whereas an unhandled fatal error in one thread can terminate the process.

  2. Creating work in Java: implement Runnable, supply a lambda, or use Callable, then submit it to an executor. Extending Thread and calling start() also creates a thread, but couples the task to its execution mechanism.

    Runnable task = () -> System.out.println(Thread.currentThread().getName());
Thread thread = new Thread(task);
thread.start(); // start() creates a new call stack; calling run() directly does not

ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(task);
executor.shutdown();

    Application code normally prefers an executor because it reuses bounded resources and provides task queuing, results, cancellation, and lifecycle management.

  3. Runnable vs Callable: Runnable.run() returns void and cannot declare checked exceptions. Callable<T>.call() returns a value of type T and may throw an exception.

    Callable<BigDecimal> totalTask = () -> orderService.calculateTotal();
Future<BigDecimal> future = executor.submit(totalTask);
BigDecimal total = future.get(2, TimeUnit.SECONDS);

    Future.get() blocks and wraps a task failure in ExecutionException. Use a timeout, handle cancellation and interruption, or use CompletableFuture when results must be composed without immediately blocking.

  4. ExecutorService: it separates task submission from thread creation. A pool owns worker threads, a queue holds pending work, and submitted tasks return Future objects. This prevents the expensive and unsafe pattern of creating an unlimited thread per request.

    Choose the pool from the workload: CPU-bound work usually starts near the available processor count; blocking I/O may use more threads, but must still be bounded according to downstream capacity. In production, configure core/max threads, queue capacity, thread names, rejection policy, metrics, and graceful shutdown. shutdown() stops new submissions and finishes accepted work; shutdownNow() requests interruption but cannot guarantee immediate termination.

  5. Synchronization: synchronization protects a critical section so only one thread at a time can execute it for the same monitor. It also establishes a Java Memory Model happens-before relationship: changes made before one thread releases the monitor become visible after another acquires it.

    public synchronized void transfer(Account target, BigDecimal amount) {
    balance = balance.subtract(amount);
    target.credit(amount);
}

    A synchronized instance method locks this; a static synchronized method locks the Class object. Protect every access participating in the same invariant with the same lock, keep the critical section small, and avoid slow remote calls while holding it.

  6. Race condition: the result depends on the unpredictable ordering of two or more threads. For example, count++ performs read, add, and write operations; two threads can read the same old value and one increment is lost.

    private final AtomicInteger count = new AtomicInteger();
public void increment() { count.incrementAndGet(); }

    Prevent races using immutability, thread confinement, synchronized blocks, locks, atomic classes, concurrent collections, or database constraints. An atomic variable protects its own operation, but multiple related variables may still require one lock or an immutable state transition.

  7. Deadlock: two or more threads wait forever in a cycle—for example, thread A owns lock 1 and requests lock 2 while thread B owns lock 2 and requests lock 1. The classic necessary conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait.

    Prevent it by acquiring locks in one global order, reducing nested locks and lock duration, using tryLock(timeout), and never calling unknown or remote code while locked. Diagnose it using thread dumps such as jstack, Java Flight Recorder, or monitoring that shows blocked threads and lock owners. If using ReentrantLock, always unlock in finally.

  8. synchronized vs volatile: synchronized provides mutual exclusion and visibility for a block of operations. volatile guarantees that reads observe the latest write to one variable and prevents certain reorderings, but provides no exclusive access.

    private volatile boolean running = true; // suitable visibility flag
public void stop() { running = false; }

private int count;
public synchronized void increment() { count++; } // compound action protected

    volatile int count; count++; is still unsafe because increment is a read-modify-write sequence. Use volatile for independent state flags or safely published immutable references; use a lock or atomic type for compound state changes.

  9. ConcurrentHashMap: a thread-safe map designed for high concurrency. Reads are generally non-blocking, and updates coordinate at a fine-grained bucket/node level rather than locking the entire map. It does not allow null keys or values, removing ambiguity between “absent” and “mapped to null.”

    ConcurrentHashMap<String, LongAdder> counts = new ConcurrentHashMap<>();
counts.computeIfAbsent(key, ignored -> new LongAdder()).increment();

    Use atomic methods such as putIfAbsent, compute, merge, and replace. A sequence like if (!map.containsKey(k)) map.put(k, v) is still a race because the two calls are not one atomic operation. Iterators are weakly consistent and do not represent a locked snapshot.

  10. Executing multiple tasks concurrently: submit independent tasks to a bounded executor and combine their results with Future, invokeAll, or CompletableFuture. Define an overall timeout and decide whether partial results are acceptable.

    CompletableFuture<Stock> stock = CompletableFuture.supplyAsync(
    () -> inventoryClient.get(productId), executor);
CompletableFuture<Price> price = CompletableFuture.supplyAsync(
    () -> pricingClient.get(productId), executor);

ProductView view = stock.thenCombine(price, ProductView::new)
    .orTimeout(2, TimeUnit.SECONDS)
    .join();

    Do not automatically use the common pool for blocking production I/O. Supply a dedicated, measured executor; handle exceptions with exceptionally/handle; propagate cancellation and tracing context; and avoid blocking join() inside the same saturated pool.

  11. Multiple threads modifying one resource: without coordination, updates can be lost, stale values can be observed, and multi-field invariants can become invalid. Collection internals can also be corrupted when a non-thread-safe implementation is mutated concurrently.

    First try to eliminate shared mutable state through immutable objects, per-request state, message passing, or ownership by one thread. Otherwise select the narrowest correct mechanism: an atomic class for one variable, a concurrent collection for atomic map operations, a lock for a multi-step in-memory invariant, or an optimistic/pessimistic database lock and unique constraint for shared persistent data. Thread safety must cover the complete business operation—not only individual getter and setter calls.

Executor example

ExecutorService pool = Executors.newFixedThreadPool(4);
try {
    List<Callable<String>> tasks = List.of(
        () -> inventoryClient.check(),
        () -> paymentClient.check());

    for (Future<String> future : pool.invokeAll(tasks, 2, TimeUnit.SECONDS)) {
        if (!future.isCancelled()) System.out.println(future.get());
    }
} finally {
    pool.shutdown();
}

In production, use bounded queues and explicit rejection policies. Avoid holding a lock during network or database calls, propagate timeouts, preserve interruption, and monitor active threads, queue depth, task latency, and rejected work.

  • What does @RestController do?
  • How does Spring Boot auto-configuration work?
  • What is a Spring Bean?
  • Singleton vs prototype bean scope?
  • What is @Configuration?
  • What is @Bean?
  • What is Spring Boot Actuator?
  • How do you manage application configuration across environments?

Answers

  1. IoC: Inversion of Control means application code does not construct and coordinate its complete object graph. Spring's IoC container reads configuration and component metadata, creates objects, resolves dependencies, applies lifecycle callbacks/proxies, and manages their scopes. The application's classes therefore focus on business behavior instead of object wiring.

  2. Dependency Injection: DI is the mechanism by which the container supplies an object's collaborators from outside rather than the object creating them with new. This reduces coupling to implementations and makes replacement and unit testing easier. Spring supports constructor, setter, and field injection; constructor injection is the default choice for required dependencies.

  3. Constructor vs field injection: constructor injection makes dependencies explicit, permits final fields, guarantees a completely initialized object, and allows plain unit tests without Spring or reflection. Field injection is shorter but hides requirements, prevents immutability, and makes manual construction difficult. Setter injection is appropriate for genuinely optional or reconfigurable dependencies.

  4. Stereotype annotations: @Component is the generic component-scan stereotype. @Service expresses that a class owns business/application logic. @Repository marks persistence code and participates in translating provider exceptions into Spring's DataAccessException hierarchy. They all create beans, but the specific annotation communicates architectural intent and may enable specialized behavior.

  5. @RestController: it combines @Controller with @ResponseBody. Request-mapping methods return response data rather than a view name, and an HttpMessageConverter—commonly Jackson—serializes the value to JSON according to content negotiation. Use DTOs and ResponseEntity when status or headers must be controlled; do not expose persistence entities directly.

  6. Auto-configuration: @EnableAutoConfiguration imports configuration selected from Spring Boot metadata. Conditions such as @ConditionalOnClass, @ConditionalOnProperty, and @ConditionalOnMissingBean inspect the classpath, settings, and existing beans. Boot supplies a sensible default only when conditions match and normally backs off when the application provides its own bean. The condition evaluation report explains why a configuration matched or did not match.

  7. Spring Bean: a bean is an object whose creation, dependencies, scope, lifecycle, and optional proxying are managed by the Spring container. Beans may come from component scanning, @Bean methods, or infrastructure auto-configuration. The default lifecycle includes instantiation, dependency population, awareness callbacks, bean post-processors, initialization callbacks, normal use, and destruction callbacks when the context closes.

  8. Singleton vs prototype: Spring singleton means one instance per bean definition per application context—not one instance for the entire JVM. Prototype creates a new instance whenever the container is asked for it. Singleton beans are shared across requests and must not hold unsafe user-specific mutable state. Spring creates prototype beans but does not automatically manage their complete destruction lifecycle.

  9. @Configuration: it identifies a source of bean definitions. In full configuration mode, Spring can proxy the class so one @Bean method calling another still obtains the managed singleton rather than constructing an untracked object. Set proxyBeanMethods = false when inter-bean method calls are unnecessary and lightweight configuration is preferred.

  10. @Bean: it registers the method's return value in the application context. It is especially useful for third-party classes that cannot be annotated, conditional construction, or explicit configuration. By default the bean name is the method name; dependencies can be declared as method parameters, and lifecycle methods can be configured when required.

  11. Spring Boot Actuator: Actuator adds operational endpoints and Micrometer instrumentation for health, readiness/liveness, metrics, loggers, mappings, thread dumps, and more. Expose only required endpoints, place management traffic behind appropriate network and authentication controls, and never publicly reveal environment or configuration values. Custom HealthIndicators should reflect whether the application can actually serve traffic without making health checks fragile.

  12. Environment configuration: keep defaults in versioned configuration, override them through profile files, environment variables, command-line values, or a configuration service. Store secrets in a secret manager rather than Git or container images, bind related settings with validated @ConfigurationProperties, and fail fast when required values are absent. Promote the same immutable artifact between environments and change configuration externally.

Dependency-injection example

@Service
public class OrderService {
    private final PaymentClient paymentClient;

    public OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}

@Configuration
class ClientConfiguration {
    @Bean
    PaymentClient paymentClient(WebClient.Builder builder) {
        return new PaymentClient(builder.build());
    }
}

@SpringBootApplication combines @Configuration, @EnableAutoConfiguration, and @ComponentScan. Auto-configuration is conditional and backs off when the application supplies its own bean; inspect the condition evaluation report when expected configuration is missing.

6. REST API Development
  • What is REST?
  • GET vs POST vs PUT vs PATCH?
  • PUT vs PATCH?
  • What HTTP status codes do you commonly use?
  • How would you design a REST API for a payment or order system?
  • What makes an API idempotent?
  • How would you implement pagination?
  • How would you handle API validation?
  • How would you handle global exceptions?
  • What is the difference between authentication and authorization?
  • How would you secure a REST API?
  • How would you handle API versioning?
  • How would you handle third-party API failures?

Answers

  1. REST: Representational State Transfer is an architectural style in which resources have stable URIs and clients manipulate their representations with standard HTTP semantics. A REST request is stateless: it carries everything needed to process it, enabling independent scaling. Good APIs use nouns such as /orders/42, HTTP methods/status codes, cache headers, and links or metadata where useful rather than encoding every action into custom verbs.

  2. HTTP methods: GET retrieves without changing intended state and is safe/idempotent. POST creates under a collection or invokes an action and is not inherently idempotent. PUT creates or completely replaces the resource at a known URI and is idempotent. PATCH applies a partial change; DELETE removes a resource and is idempotent even if repeated responses differ.

  3. PUT vs PATCH: PUT supplies the complete replacement representation, so omitted fields may be reset. PATCH sends only changes, commonly as JSON Merge Patch or JSON Patch. PUT should produce the same state when repeated. PATCH is idempotent only when the patch operation itself is designed that way—for example, “set status” is idempotent while “increment balance” is not.

  4. Status codes: use 200 for a successful response, 201 plus Location for creation, and 204 when no body is returned. Client errors include 400 malformed input, 401 invalid/missing authentication, 403 insufficient permission, 404 missing resource, 409 state conflict, 422 semantic validation, and 429 rate limiting. Use 500 for an unexpected server failure and 502/503/504 for dependency or availability failures.

  5. Order/payment API design: expose resources such as POST /orders, GET /orders/{id}, POST /payments, and explicit refund/cancel transitions. Validate amounts, currency and allowed state changes; authenticate the caller and check ownership; use idempotency keys and unique constraints; return stable error contracts; and expose an immutable transaction ID. Treat slow or uncertain provider operations as workflows with pending states, verified webhooks, and reconciliation rather than one long HTTP transaction.

  6. Idempotency: repeated execution has the same intended effect as one execution. HTTP defines GET, PUT, and DELETE as idempotent, but retries still need safe implementation. For a payment POST, persist the client idempotency key, request fingerprint, processing state, and final response under a unique constraint. A matching retry returns the saved response; reuse with a different payload is rejected.

  7. Pagination: offset pagination (?page=2&size=20) is simple and supports jumping to pages, but large offsets become expensive and concurrent inserts can shift results. Cursor/keyset pagination uses the last ordered value, such as ?after=2026-10-08T10:00:00Z&id=42, and is stable and efficient for feeds. Always cap page size, use deterministic indexed ordering with a unique tie-breaker, and return next-cursor metadata.

  8. Validation: use Bean Validation annotations such as @NotBlank, @Positive, and @Valid for transport-level constraints. Enforce cross-field and state-dependent business rules in the service/domain layer, because they may require current database state. Return a consistent error document with field, rejected rule, human-safe message, code, timestamp, path, and correlation ID; never return a stack trace.

  9. Global exceptions: centralize mapping with @RestControllerAdvice and targeted @ExceptionHandler methods. Map domain exceptions to stable HTTP errors, validation failures to field-level details, and unexpected exceptions to a generic 500 response while logging the internal cause with a correlation ID. Do not catch every exception in each controller or expose database/provider messages to clients.

  10. Authentication vs authorization: authentication answers “who are you?” by validating credentials or a token. Authorization answers “may this identity perform this operation on this resource?” using roles, scopes, ownership, and policies. Authentication normally precedes authorization, but a valid token alone must never grant access to every record.

  11. REST API security: require TLS; validate token signature, issuer, audience, expiry, and scopes; authorize at both route and resource-ownership levels; validate input and use parameterized persistence APIs; rate-limit abuse; restrict CORS; apply safe headers; rotate secrets; and redact sensitive logs. Use least privilege for service accounts and databases, audit high-risk actions, and test broken-object-level authorization explicitly.

  12. Versioning: first evolve compatibly by adding optional fields and tolerating unknown response fields. For a breaking contract, use a clear strategy such as /api/v2 or versioned media types, maintain separate documentation and contract tests, announce a deprecation/sunset policy, monitor client usage, and provide a migration period. Avoid versioning merely because the internal implementation changed.

  13. Third-party failures: set connection and response timeouts, propagate a correlation ID, and classify failures as transient, permanent, or unknown. Retry only transient and idempotent operations with exponential backoff, jitter, and a cap; use circuit breakers and bulkheads to prevent cascading failure. For an unknown payment outcome, do not blindly retry—query by provider reference or reconcile asynchronously, and surface an explicit pending status.

7. Spring Security and JWT
  • Authentication vs authorization?
  • What is JWT?
  • Explain the JWT authentication flow.
  • Access token vs refresh token?
  • Where should a JWT be validated?
  • How would you implement role-based authorization?
  • What happens when a JWT expires?
  • How would you secure sensitive APIs?
  • What are common security vulnerabilities in REST APIs?

Answers

  1. Authentication vs authorization: Authentication answers “Who are you?” by validating credentials or a token and creating an authenticated Authentication object. Authorization answers “May you perform this action?” by checking authorities, scopes, ownership, tenant, or another business rule. They are separate: a correctly authenticated customer should still receive 403 Forbidden when trying to access another customer's order.
  2. JWT: A JSON Web Token is a compact string with Base64URL-encoded header and payload plus a cryptographic signature. Common claims include sub, iss, aud, exp, roles, and scopes. The signature protects integrity and authenticity; it does not encrypt the payload, so passwords, secrets, and sensitive personal data must not be placed in it.
  3. Authentication flow: The user authenticates with an authorization server such as Keycloak. It issues an access token signed with its private key. The client sends Authorization: Bearer <token>; Spring Security's resource-server filter verifies the signature using the issuer's public key, checks issuer, audience, and expiry, maps claims to authorities, and only then runs authorization rules. The API does not trust claims until all validation succeeds.
  4. Access vs refresh token: An access token is deliberately short-lived and is presented to resource APIs. A refresh token lasts longer and is presented only to the authorization server to obtain a new access token. Refresh tokens should be protected more strongly, rotated on use, and revoked when reuse is detected. Browser applications commonly keep them in secure, HttpOnly, SameSite cookies rather than JavaScript-readable storage.
  5. Validation location: The gateway should reject invalid traffic early, but each sensitive resource service should also validate JWTs because internal routes can be exposed accidentally or called through another path. Validation includes signature, allowed algorithm, issuer, intended audience, time claims, and required scope—not merely decoding the token. Central identity configuration plus service-level enforcement provides defense in depth.
  6. Role-based authorization: Convert trusted token claims into Spring GrantedAuthority values, define coarse endpoint rules in SecurityFilterChain, and enable method security for business-level checks. For example, @PreAuthorize("hasAuthority('SCOPE_orders.write') and #userId == authentication.name") combines permission and ownership. Deny by default and test allowed and forbidden cases.
  7. Expiry: A resource server rejects an expired access token with 401 Unauthorized; it must not silently extend it. The client can use a still-valid refresh token with the authorization server and retry once with the newly issued access token. If refresh fails or has expired, require login again. Short access-token lifetime limits damage from theft, while revocation or token introspection may be needed for immediate logout requirements.
  8. Securing sensitive APIs: Use TLS, least-privilege scopes, object-level ownership checks, validation, rate limits, safe error messages, audit trails, secret rotation, and private networking for internal services. Protect high-risk actions with step-up authentication or approval and avoid logging credentials or tokens. CORS is a browser control, not API authentication, and CSRF protection is still relevant when credentials are cookie-based.
  9. Common API vulnerabilities: Broken object-level authorization occurs when changing an ID exposes another user's record; mass assignment lets clients set fields such as role; injection passes untrusted input into interpreters; SSRF makes the server call attacker-controlled destinations. Prevent these with per-object authorization, request DTO allow-lists, parameterized queries, outbound URL allow-lists, bounded payloads, dependency/configuration scanning, rate limiting, and explicit negative security tests.

8. JPA and Hibernate
  • What is ORM?
  • JPA vs Hibernate?
  • What is an Entity?
  • Explain one-to-one, one-to-many, and many-to-many relationships.
  • Lazy vs eager loading?
  • What is the N+1 query problem?
  • How can N+1 queries be avoided?
  • What is cascading?
  • What is the difference between save() and saveAndFlush()?
  • What is the first-level cache?
  • JPQL vs native query?
  • What is a database transaction?

Answers

  1. ORM: Object-relational mapping connects Java classes, fields, and object relationships to tables, columns, and foreign keys. It removes repetitive row-mapping and generates SQL, dirty checking, and relationship handling, but it does not eliminate the need to understand joins, indexes, locking, and transaction boundaries. A useful interview point is that ORM improves productivity while poorly chosen fetch plans can still generate expensive SQL.
  2. JPA vs Hibernate: Jakarta Persistence (JPA) is a standard contract containing annotations and APIs such as @Entity, JPQL, and EntityManager. Hibernate is an ORM provider that implements that contract and adds features such as filters, advanced batching, and provider-specific annotations. In Spring Data JPA, repositories usually program against JPA while Hibernate is the default engine doing the work.
  3. Entity: An entity is a domain object whose state is persisted and managed by a persistence context. It requires an identity using @Id, a no-argument constructor at least accessible to the provider, and should have stable equality semantics. Avoid placing API serialization concerns or expensive relationship traversal inside entity methods; use DTOs at service boundaries.
  4. Relationships: A one-to-one uses a unique foreign key; a many-to-one normally places the foreign key on the child; a one-to-many is usually the inverse collection; and many-to-many uses a join table. In real systems, model many-to-many as a join entity such as Enrollment(student_id, course_id, enrolled_at, status) when the relationship has data. The side with @JoinColumn owns the relation, and helper methods should update both sides in memory.
  5. Lazy vs eager: Lazy fetching returns a proxy or collection and loads it when accessed inside an active persistence context. Eager declares that data must be available, but it may still cause secondary selects and N+1 queries rather than one join. Prefer lazy associations and select an explicit fetch plan for each use case using a fetch join, entity graph, or projection. Accessing an uninitialized lazy relation after the session closes causes LazyInitializationException.
  6. N+1: The application first loads N orders with one query and then accesses each order's customer, causing up to N additional queries. The code looks harmless but network round trips and database work grow with result size. Detect it through SQL logs, Hibernate statistics, APM traces, or query-count assertions—not just by reviewing repository method names.
  7. Avoiding N+1: Use JOIN FETCH for a known object graph, @EntityGraph for reusable repository fetch plans, DTO projections when only selected columns are required, or batch fetching for controlled secondary queries. Do not set all associations to eager: that creates oversized graphs and moves the problem. Collection fetch joins plus pagination can duplicate rows, so page IDs first and fetch the graph in a second query.
  8. Cascading: Cascade controls whether an entity operation propagates from a parent to associated objects—for example, persisting an order can persist its newly created order items. It does not mean database ON DELETE CASCADE. Use only the operations required by aggregate ownership, avoid CascadeType.ALL by habit, and never cascade remove into shared reference entities such as products or roles.
  9. save() vs saveAndFlush(): Spring Data save() calls persist for new entities or merge for detached ones; generated SQL may wait until flush or commit. saveAndFlush() additionally forces pending SQL to the database, useful when a later operation needs a constraint checked immediately. Flush is not commit—the surrounding transaction can still roll back—and excessive flushing reduces batching and performance.
  10. First-level cache: Every persistence context has a mandatory identity map. Loading the same entity ID twice in one transaction generally returns the same managed Java object and avoids a second ID query. It is not a cross-request cache and can consume large memory during bulk work, so batch jobs often call flush() and clear() periodically.
  11. JPQL vs native SQL: JPQL addresses entities and mapped fields, supports polymorphism, and is portable across databases. Native SQL addresses physical tables and exposes vendor features such as PostgreSQL CTEs, JSON operators, or specialized window expressions. Prefer JPQL/projections for ordinary domain queries; use native SQL when it provides measurable value and test mappings and portability explicitly.
  12. Transaction: A transaction is an atomic unit of database work with ACID guarantees. In a service method it should contain all related state changes—for example, save the order and its outbox event together—so either both commit or neither does. Keep it short, avoid slow remote calls while locks are held, and choose isolation and locking based on the concurrency invariant.

Targeted fetching example

@EntityGraph(attributePaths = "items")
Optional<Order> findWithItemsById(Long id);

@Query("select o from Order o join fetch o.customer where o.id = :id")
Optional<Order> findWithCustomer(Long id);

Keep associations lazy by default and choose the fetch plan per use case. Verify generated SQL and query counts in tests. Fetch-joining multiple collections or combining collection fetch joins with pagination can multiply rows, so DTO projections, batch fetching, or two-step queries may be safer.

9. Transactions
  • What is a transaction?
  • Explain ACID properties.
  • What does @Transactional do?
  • What are transaction isolation levels?
  • What is a dirty read?
  • What is a non-repeatable read?
  • What is a phantom read?
  • What happens when an exception occurs inside a transactional method?
  • What is transaction rollback?
  • How would you maintain consistency when multiple database operations are involved?

Answers

  1. Transaction: A transaction groups related reads and writes into one logical unit. For a bank transfer, debit and credit must commit together or both roll back; exposing a half-finished transfer violates the business invariant. Transactions should be as short as possible because open transactions retain connections, locks, and database resources.
  2. ACID: Atomicity means all-or-nothing; consistency means committed work preserves declared constraints and business invariants; isolation controls what concurrent transactions can observe; durability means committed data survives failure according to the database's guarantees. Consistency is not automatic for every business rule—the application and schema must define constraints correctly.
  3. @Transactional: Spring normally wraps the bean in a proxy. On entry, the interceptor obtains or joins a transaction according to propagation settings, binds persistence resources to the thread, and commits or rolls back on exit. Because proxy interception is involved, self-invocation and private methods commonly bypass the annotation. Put transaction boundaries in public service methods rather than controllers or repositories alone.
  4. Isolation levels: READ_UNCOMMITTED allows the weakest visibility; READ_COMMITTED prevents dirty reads; REPEATABLE_READ keeps previously read rows stable in typical engines; and SERIALIZABLE aims to make concurrent work behave sequentially. Exact behavior is database-specific. Stronger isolation can increase blocking or serialization failures, so combine the lowest adequate level with optimistic/pessimistic locking and safe retry.
  5. Dirty read: Transaction A reads a value written by B before B commits. If B rolls back, A acted on data that never officially existed. READ_COMMITTED and stronger levels prevent this; major production databases often default to at least that level.
  6. Non-repeatable read: A transaction reads one row twice and sees different committed values because another transaction updated it between reads. If stable state is required for a calculation, use appropriate isolation, a version check, or a row lock rather than assuming repeated queries remain identical.
  7. Phantom read: A transaction repeats a predicate query—such as all available seats—and a concurrent insert or delete changes the set of matching rows. This differs from a non-repeatable read, which changes an existing row. Serializable isolation, predicate/range locking, or a better domain constraint can protect invariants affected by phantoms.
  8. Exceptions and rollback: By default Spring rolls back for RuntimeException and Error, not checked exceptions. Use rollbackFor when a checked exception represents failure. If code catches and suppresses the exception, the interceptor may commit; either rethrow it or mark the transaction rollback-only. Also remember that an exception after flush can leave the transaction unusable even if caught.
  9. Rollback: The database discards uncommitted changes and releases locks. It cannot unsend an email, revoke an already completed HTTP call, or erase a published message. Coordinate such side effects with a transactional outbox, idempotency key, after-commit handler, or a compensating operation instead of assuming database rollback covers them.
  10. Multiple operations: Keep changes within one database in one local transaction and enforce invariants with constraints and locking. Across separately owned service databases, use a Saga: each service commits locally, publishes an event through an outbox, and defines a compensating action for failure. Consumers must be idempotent because delivery is normally at least once; reconciliation handles rare uncertain outcomes.

Important Spring transaction caveat

@Transactional(rollbackFor = PaymentException.class)
public void placeOrder(CreateOrder command) throws PaymentException {
    orderRepository.save(map(command));
    outboxRepository.save(OrderCreated.from(command));
}

Spring normally applies transactions through a proxy. A call from one method to another method on the same object bypasses that proxy, so the inner @Transactional may not take effect. Keep transactional methods public, call them through another injected bean, and avoid slow remote calls while holding database locks.

10. SQL and Database
  • Primary key vs foreign key?
  • INNER JOIN vs LEFT JOIN?
  • WHERE vs HAVING?
  • GROUP BY vs ORDER BY?
  • What is normalization?
  • What is denormalization?
  • What is an index?
  • How does an index improve query performance?
  • Clustered vs non-clustered index?
  • What is a composite index?
  • What is a database transaction?
  • What is a database deadlock?
  • How would you identify a slow query?
  • What is EXPLAIN used for?
  • Write a query to find duplicate records.
  • Write a query to find the second-highest salary.
  • Write a query using a window function.

Answers

  1. Primary vs foreign key: A primary key uniquely and permanently identifies a row and is implicitly unique and non-null. A foreign key references a candidate key in another or the same table and prevents orphaned relationships. For example, orders.customer_id references customers.id; choose deliberate delete behavior such as restrict, set null, or cascade rather than leaving it ambiguous.
  2. INNER JOIN vs LEFT JOIN: An inner join returns only rows having a match on both sides. A left join retains every left-side row and fills right-side columns with null when no match exists. Put a filter on the right table in the WHERE clause carefully because it can accidentally turn a left join into inner-join behavior; place match-specific conditions in ON when unmatched left rows must remain.
  3. WHERE vs HAVING: WHERE removes individual rows before grouping and should handle ordinary predicates so less data reaches aggregation. HAVING filters completed groups, commonly using aggregate expressions: GROUP BY department HAVING COUNT(*) > 10. Using HAVING for a nonaggregate predicate can be less clear and sometimes less efficient.
  4. GROUP BY vs ORDER BY: GROUP BY combines rows sharing key values so aggregate functions can return one result per group. ORDER BY sorts the final rows and does not aggregate them. SQL does not promise result order without an explicit ORDER BY, even if a grouping or index appears to return sorted output.
  5. Normalization: Normalization separates facts to reduce duplication and update anomalies. 1NF uses atomic values, 2NF removes partial dependency on a composite key, and 3NF removes transitive dependency on non-key attributes. For example, store customer contact data once in customer rather than repeating it in every order, while preserving historical order snapshots deliberately where required.
  6. Denormalization: Denormalization intentionally duplicates or precomputes data for a measured read requirement—for example, a materialized sales summary or customer name snapshot on an invoice. It improves some reads but adds write amplification and consistency rules. State which copy is authoritative and update derived copies through a transaction, event, refresh process, or reconciliation.
  7. Index: An index is a separate search structure, commonly a B-tree, containing indexed keys and row locators or included data. It can enforce uniqueness and support selective predicates, joins, ranges, and ordering. It is not free: indexes consume memory/storage and every insert, update, and delete may need to maintain them.
  8. How indexes help: Rather than scanning every table row, the engine can navigate the index to a small key range and fetch only qualifying rows. A covering index may satisfy the query without visiting the table. Benefits depend on selectivity, column order, statistics, and expressions; wrapping an indexed column in a function or using a leading wildcard may prevent an efficient lookup.
  9. Clustered vs non-clustered: In engines with clustered storage, the clustered key determines the physical/primary row organization, so only one such order exists. A non-clustered/secondary index stores its own ordered keys and a locator to the base row. PostgreSQL, MySQL/InnoDB, and SQL Server use different terminology and implementation details, so explain the concept and identify the database in an interview.
  10. Composite index: A multi-column index such as (customer_id, created_at DESC) is useful for recent orders of one customer. Its leftmost prefix usually supports customer_id alone but not an arbitrary query filtering only created_at. Choose equality columns first, then range/order columns based on real query patterns, and verify with the execution plan.
  11. Database transaction: It provides an all-or-nothing boundary and isolation from concurrent work. A transfer should update both account rows and append ledger entries in the same transaction, with constraints preventing invalid balances. Commit makes changes durable; rollback removes uncommitted work, but neither automatically coordinates an already completed external API call.
  12. Deadlock: A deadlock forms when transactions wait in a cycle—for example, A locks account 1 then requests 2 while B locks 2 then requests 1. The database detects the cycle and aborts a victim. Prevent it by locking resources in a consistent order, keeping transactions short, indexing updates correctly, and safely retrying the full idempotent transaction.
  13. Finding a slow query: Start with APM and slow-query logs to identify the exact SQL, parameters, call count, p95/p99 time, rows returned, and lock or I/O waits. Reproduce against production-like volume, inspect the actual plan, and check missing/stale statistics, N+1 calls, blocking, pool saturation, and result size. Optimize the measured bottleneck and compare the same metrics afterward.
  14. EXPLAIN: It displays the optimizer's estimated scan, join, sort, and aggregation plan. EXPLAIN ANALYZE actually runs the statement and reports actual rows and timings, so use it cautiously for writes or expensive production queries. Large gaps between estimated and actual row counts suggest statistics or data-distribution problems; repeated loops often reveal N+1-like nested work.
  15. Duplicates: SELECT email, COUNT(*) AS occurrences FROM users GROUP BY email HAVING COUNT(*) > 1;. To retrieve full duplicate rows, place the grouped keys in a CTE and join back to users. After cleanup, add a unique constraint if duplicates are invalid so application races cannot recreate them.
  16. Second-highest salary: SELECT MAX(salary) FROM employee WHERE salary < (SELECT MAX(salary) FROM employee); returns the second distinct value. A scalable alternative is DENSE_RANK() OVER (ORDER BY salary DESC) and filter rank 2; DENSE_RANK handles ties, whereas ROW_NUMBER ranks individual rows.
  17. Window function: SELECT id, department, salary, DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank FROM employee; ranks salaries independently inside each department without collapsing rows. Unlike GROUP BY, window functions retain each detail row and add analytics such as ranks, running totals, or previous-row comparisons.

Slow-query investigation flow

  1. Capture the exact SQL, bind values, frequency, p95/p99 latency, and wait time.
  2. Run EXPLAIN (ANALYZE, BUFFERS) with production-like data and inspect actual versus estimated rows.
  3. Check sequential scans, join algorithms, sorts spilling to disk, lock waits, N+1 calls, and connection-pool saturation.
  4. Add or adjust an index only when it matches the filter/join/order pattern; then rerun the plan and load test.

For a composite B-tree index such as (customer_id, created_at), queries beginning with customer_id generally benefit from the leftmost-prefix rule. Every index consumes storage and makes writes more expensive.

11. Redis and Caching
  • What is Redis?
  • Why would you use Redis in a backend application?
  • Redis vs database?
  • What is caching?
  • Explain the cache-aside strategy.
  • What is TTL?
  • What happens when cached data becomes stale?
  • Where would you use Redis in a payment or backend system?

Answers

  1. Redis: Redis is a low-latency, in-memory data-structure server. Beyond strings it supports hashes, lists, sets, sorted sets, bitmaps, streams, atomic operations, expiry, replication, and optional persistence. Because commands on the primary execution path are atomic, it is useful for counters and conditional updates, but multi-step workflows still require careful Lua/transactions and failure design.
  2. Backend uses: Common uses are cache entries, sessions, rate-limit counters, one-time tokens, leaderboards, distributed coordination, and short-lived idempotency state. Choose the data structure deliberately: a sorted set fits rankings, INCR plus expiry fits simple limits, and hashes fit small grouped fields. Define behavior when Redis is slow or unavailable.
  3. Redis vs database: A relational database typically remains the durable system of record and provides constraints, joins, and robust transactions. Redis prioritizes speed and specialized structures; persistence and failover do not automatically make it a suitable financial ledger. Decide whether Redis data is disposable, rebuildable, or authoritative, then configure durability and recovery accordingly.
  4. Caching: A cache stores reusable data closer to the caller to reduce latency and protect downstream systems. It helps read-heavy, repeatedly requested, moderately stable data. It can hurt when hit rate is low, objects are huge, invalidation is unreliable, or strong read-after-write consistency is mandatory. Measure hit rate, miss latency, evictions, memory, and fallback load.
  5. Cache-aside: The service reads Redis first; on a miss it reads the database and populates Redis. On mutation, commit the database first and invalidate the cache key. This tolerates cache loss because the database remains authoritative, but concurrent misses can stampede and an unlucky read/write race can briefly cache stale data. Use TTL, request coalescing, versioned keys, or event invalidation according to risk.
  6. TTL: Time to live automatically expires a key and bounds staleness and memory use. Choose it from business tolerance, not an arbitrary round number. Add random jitter so thousands of keys do not expire together, and distinguish cache expiry from session/security expiry, where policy may require an exact deadline.
  7. Stale data: Staleness occurs when the source changes while an old cached representation remains. Mitigate it through write invalidation, domain-event invalidation, short TTLs, versioned keys, or a write-through strategy. Since database commit and cache deletion are not normally atomic, consumers must accept a defined staleness window or use patterns such as outbox-driven invalidation and reconciliation.
  8. Payment/backend use: Redis is suitable for rate limits, short-lived checkout state, session data, merchant configuration cache, and idempotency locks/records with a durable fallback. It must not be the only record of money movement. For a distributed lock use a unique owner token, bounded lease, and compare-and-delete release; also enforce the business invariant in the database because a lock can expire during a pause.

Spring cache-aside example

public Product findProduct(long id) {
    String key = "product:" + id;
    Product cached = redis.get(key, Product.class);
    if (cached != null) return cached;

    Product product = repository.findById(id).orElseThrow();
    redis.set(key, product, Duration.ofMinutes(10));
    return product;
}

On update, commit the database change first and invalidate the key. Protect hot misses with request coalescing or a short distributed lock, add TTL jitter to reduce synchronized expiry, and monitor hit rate, memory, evictions, latency, and database fallback load. Never assume a cache and database update are one atomic operation.

12. Kafka and RabbitMQ
  • Why do we need message queues?
  • Synchronous vs asynchronous communication?
  • Kafka vs RabbitMQ?
  • What is a Kafka producer?
  • What is a consumer?
  • What is a topic?
  • What is a partition?
  • What is a consumer group?
  • How would you handle message failure?
  • What are retries and a dead-letter queue?
  • When would you prefer asynchronous processing?

Answers

  1. Why messaging: A broker decouples producer availability and speed from consumers, buffers traffic spikes, and moves slow work outside the request path. It also enables fan-out, retries, and independent scaling. The trade-off is eventual consistency, duplicates, ordering constraints, schema evolution, and additional operational monitoring; a queue is not automatically the right solution for a simple immediate query.
  2. Synchronous vs asynchronous: HTTP/gRPC request-response is appropriate when the caller needs an immediate answer and can tolerate dependency coupling. Messaging lets the producer acknowledge accepted work without waiting for every downstream service. Use deadlines and circuit breakers for sync calls; use durable events, idempotency, status tracking, and reconciliation for async flows. Many systems combine both—for example, sync order creation followed by async fulfilment.
  3. Kafka vs RabbitMQ: Kafka is a distributed append-only log: events remain for a retention period, consumers track offsets, and old data can be replayed. It excels at high-throughput event streams, integration events, and stream processing. RabbitMQ is a broker centered on exchanges, queues, routing keys, acknowledgements, and per-message delivery, making it strong for work queues and commands. Choose from replay, ordering, routing, throughput, and operational needs—not popularity.
  4. Producer: A Kafka producer serializes a key and value, selects a partition, batches records, and waits according to its acknowledgement setting. A stable key such as orderId sends related events to the same partition and preserves their order. Reliability also depends on retries, idempotent-producer configuration, delivery timeout, schema versioning, and handling send failures rather than ignoring the returned future.
  5. Consumer: A consumer polls records assigned to it, deserializes and processes them, then advances offsets. Offset commit means “work before this position is complete,” so committing before the database transaction can lose work. Committing afterward gives at-least-once delivery and possible duplicates; make effects idempotent and monitor lag, processing time, rebalance frequency, and failures.
  6. Topic: A topic is a named durable stream, normally split into partitions and configured with retention or compaction. Topic names and events form an integration contract, so use clear ownership, schemas, compatibility rules, and versioning such as orders.created.v1. Avoid placing unrelated event types in one loosely governed topic.
  7. Partition: A partition is an ordered append-only shard and Kafka's main unit of parallelism. Order is guaranteed only within one partition, not across the entire topic. More partitions can increase throughput and consumer concurrency but also add broker metadata, open files, rebalancing cost, and make later repartitioning/key choice consequential.
  8. Consumer group: Within one group, each partition is assigned to at most one active consumer, so members share the work. A group cannot usefully process one topic with more active consumers than partitions. Separate groups maintain independent offsets and each receive the full stream—for example, Inventory and Analytics can consume the same order events without competing.
  9. Failure handling: First classify transient failures, poison data, and permanent business rejection. Retry transient errors with bounded exponential backoff and jitter; do not block a partition indefinitely. Preserve event ID, key, payload, error, attempts, and trace context in a dead-letter topic, alert on it, and provide a controlled replay path after correction. Business rejection is often a normal outcome event, not a technical retry.
  10. Retry and DLQ: Retry topics or delayed queues prevent hot-looping the same failure. A dead-letter destination quarantines messages that exceed policy so healthy traffic can proceed, but it is not a garbage bin: assign ownership, dashboards, alerts, retention, inspection, correction, and replay procedures. Consumers must remain idempotent because both retry and replay can deliver the event again.
  11. When async fits: Prefer it for notifications, audit/analytics, media processing, inventory/payment workflows, and integrations where immediate completion is unnecessary and temporary downstream outage should be absorbed. Avoid it when the user requires an immediate strongly consistent decision or when added operational complexity has no benefit. Expose 202 Accepted plus a status resource for genuinely asynchronous APIs.

Reliable Kafka consumer flow

  1. Read the event and validate its version and required fields.
  2. Check a processed_events table using the event ID.
  3. In one local database transaction, apply the business change and store the processed event ID.
  4. Acknowledge/commit the Kafka offset only after the database transaction succeeds.

If the process crashes before committing the offset, Kafka redelivers the record and the idempotency record prevents duplicate effects. Preserve ordering by using a stable business key such as orderId; scale a consumer group only up to the useful partition count.

Answers

  1. Microservices architecture: The system is split around business capabilities such as Orders, Inventory, and Payments. Each service owns its logic and normally its data, exposes an explicit API/event contract, and can be built and deployed independently. The goal is autonomous change, not merely many small projects; tightly coupled services sharing one schema produce a distributed monolith.
  2. Core components:
    • Individual services: Small, self-contained units that implement one business capability and can be developed, deployed, and scaled independently.
    • API Gateway: The client-facing entry point that routes requests and can handle concerns such as authentication, rate limiting, TLS, and protocol translation.
    • Service registry and discovery: Tracks available service instances and lets callers locate healthy endpoints dynamically. Examples include Eureka and Consul; Kubernetes commonly provides discovery through Services and DNS.
    • Load balancer: Distributes traffic among healthy instances to improve throughput, availability, and resource utilization.
    • Database per service: Each service owns its data and exposes it through contracts instead of allowing other services to query its tables directly. This reduces coupling, although cross-service operations require eventual-consistency patterns.
    • Message broker or event bus: Kafka or RabbitMQ enables asynchronous, loosely coupled communication and supports event-driven workflows.
    • Centralized configuration and identity: Configuration services manage environment-specific settings, while OAuth 2.0/OpenID Connect providers such as Keycloak handle identity and token issuance. Secrets should use a dedicated secret manager.
    • Observability: Centralized logs, metrics, traces, health checks, correlation IDs, dashboards, and alerts reveal system health and help trace a request across service boundaries.

    Interview summary: Microservices are not only a collection of small APIs. They require routing, discovery, load balancing, isolated data ownership, reliable messaging, security, configuration, and observability so independently deployed services can operate as one reliable system.

  3. Monolith vs microservices: A modular monolith has one deployment and process, making local transactions, testing, debugging, and operations simpler. Microservices provide independent deployment and scaling when team and domain boundaries justify them, but every call can fail and cross-service work becomes eventually consistent. Start with the simplest architecture that meets scale and organizational needs, then extract measured boundaries.
  4. Advantages and costs: Benefits include team ownership, technology/deployment autonomy, targeted scaling, and some fault isolation. Costs include network latency, contract compatibility, duplicated platform concerns, distributed tracing, eventual consistency, complex testing, and more infrastructure. Mentioning both sides shows architectural maturity; “microservices are always scalable” is not sufficient.
  5. Communication: Use HTTP or gRPC for an immediate query/command response and Kafka/RabbitMQ for decoupled events or long workflows. Every remote call needs a deadline, correlation ID, authentication, versioned contract, and an explicit failure policy. Events should represent completed facts, be backward compatible, and carry stable identifiers so consumers can be idempotent.
  6. API Gateway: It is the controlled public entry point that routes requests and can centralize TLS termination, JWT validation, CORS, rate limiting, request IDs, and coarse policy. It should not accumulate domain orchestration or become a new monolith. Services still enforce their own business authorization, and internal services should be private where possible.
  7. Service discovery: Because instances scale and addresses change, discovery resolves a logical name to healthy endpoints. Eureka/Consul use a registry and heartbeats; Kubernetes commonly uses Services, EndpointSlices, and DNS. Discovery must work with health checks and load balancing, and stale instances or DNS caching must be considered.
  8. Circuit breaker: It counts qualifying failures or slow calls and opens after a threshold, causing new requests to fail fast instead of exhausting threads/connections. After a wait it becomes half-open and permits test calls; success closes it. Combine it with timeouts and bulkheads, tune it from SLOs, and do not use a fallback that silently returns incorrect business data.
  9. Handling service failure: Bound every call with connect/read deadlines, retry only transient and idempotent operations with backoff and jitter, and use circuit breakers plus separate pools to prevent cascading failure. Return a clear degraded response or queue recoverable work. Add metrics, logs, traces, alerts, and a correlation ID; resilience without observability only hides failures.
  10. Consistency: Each service commits its own database transaction. A transactional outbox atomically saves state and an event, while idempotent consumers safely handle redelivery. A Saga coordinates local steps and compensations such as releasing inventory after payment failure. Explicit states, timeouts, reconciliation, and manual recovery are required because compensation itself can fail.
  11. Distributed transaction: It spans independently managed resources. Two-phase commit asks participants to prepare and then commit, providing strong atomicity but increasing coupling, blocking risk, and coordinator dependency. Sagas trade immediate atomicity for availability and eventual consistency. Use 2PC only when resources support it and its operational cost matches the invariant; otherwise redesign around local transactions and compensations.
  12. Saga vs Two-Phase Commit (2PC):
    AreaSagaTwo-Phase Commit (2PC)
    ApproachA sequence of independent local transactionsOne coordinated transaction across multiple participants
    ConsistencyEventual consistencyStrong atomic consistency
    Failure recoveryRuns compensating business actions for previously completed stepsCoordinator instructs every participant to commit or roll back

    Saga example: placing an order

    1. Order Service creates an order in its local database.
    2. Inventory Service reserves stock in its own local transaction.
    3. Payment Service charges the customer in another local transaction.
    4. If payment fails, the Saga triggers compensations: release the inventory and mark the order as failed or cancelled.

    A Saga may use choreography, where services react to each other's events, or orchestration, where a Saga coordinator sends commands and tracks the workflow. Choreography is simple for a few steps but can become difficult to understand; orchestration makes a complex flow explicit but introduces a coordinator component.

    How 2PC works

    1. Prepare phase: the coordinator asks all participants whether they can commit. Each participant performs its work, holds required resources, and votes yes or no.
    2. Commit phase: if every participant votes yes, the coordinator tells all of them to commit; otherwise it tells them to roll back.

    Important: a compensation is not always a technical rollback. Refunding a captured payment, for example, is a new auditable business transaction and could also fail. A production Saga therefore needs idempotency keys, durable state, retries with backoff, timeouts, dead-letter handling, monitoring, and reconciliation for stuck workflows.

    Interview answer: “2PC provides strong atomicity by coordinating prepare and commit across all participants, but it increases coupling and may hold locks or block during failures. A Saga uses local transactions and compensating actions, so it scales and fits autonomous microservices better, but it provides eventual consistency and requires careful failure handling. I generally prefer a Saga for cross-service business workflows and reserve 2PC for short transactions where all resources support it and the business truly requires immediate atomicity.”

  13. Scalable backend: Begin with workload shape and measurable SLOs. Remove the actual bottleneck using stateless horizontal scaling, suitable database indexes/replicas/partitioning, bounded pools, caching, asynchronous queues, and backpressure. Distribute across failure zones, eliminate single points of failure, capacity-test production-like data, monitor saturation and tail latency, and keep a safe degradation and rollback strategy.

Circuit Breaker interview questions

Basic level

  1. What is a Circuit Breaker, and why is it needed?

    A Circuit Breaker wraps a remote call, measures failures or slow responses, and temporarily rejects new calls when the dependency is unhealthy. It prevents repeated calls from consuming threads, connections, and timeouts, thereby limiting cascading failure and giving the dependency time to recover.

  2. What are its three states?
    • Closed: calls flow normally and outcomes are recorded. For example, User Service calls Order Service successfully.
    • Open: the failure threshold has been reached, so calls fail fast without contacting Order Service.
    • Half-open: after a waiting period, a limited number of trial calls are allowed. Successful trials close the circuit; sufficient failures open it again.
  3. What happens in the open state?

    The protected dependency is not called. Requests immediately receive an exception or approved fallback until the open-state wait duration expires, after which the breaker moves to half-open for probe calls.

  4. Retry vs Circuit Breaker:

    A retry repeats a failed call because a transient problem may disappear. A Circuit Breaker stops calls when failure is persistent. Use a small retry count with exponential backoff and jitter only for idempotent operations; place retry inside the breaker so one user request is normally recorded as one final outcome. Incorrect ordering or aggressive retries can amplify an outage.

  5. Caller or callee?

    Place it in the caller, around the outbound call, because the caller must protect its own threads and define how it degrades when that dependency fails. Each caller may have different latency limits and fallback behavior. The callee still needs rate limiting, load shedding, timeouts, and health checks.

  6. What is a fallback?

    A fallback is an intentional alternative executed when the call is rejected or fails—for example, returning cached catalogue data. It must be safe and truthful; returning an empty order list when the service is unavailable could mislead a user. Critical writes are usually queued durably or rejected clearly rather than faked.

Spring Boot and Resilience4j

  1. Which library is commonly used?

    Resilience4j is a lightweight, modular fault-tolerance library commonly used with modern Spring Boot. Its modules include CircuitBreaker, Retry, RateLimiter, Bulkhead, and TimeLimiter.

  2. How is it implemented, and which annotations are used?

    Add the Resilience4j Spring Boot starter and Spring AOP dependency, configure a named instance, and wrap an outbound method with @CircuitBreaker(name = "orderService", fallbackMethod = "orderFallback"). Related annotations include @Retry, @Bulkhead, @RateLimiter, and @TimeLimiter.

  3. How is it configured in application.yml?
    resilience4j:
  circuitbreaker:
    instances:
      orderService:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 10

        failure-rate-threshold: 50
        slow-call-duration-threshold: 2s
        slow-call-rate-threshold: 50

    Property names may vary slightly by Resilience4j/Spring Boot version, so validate them against the version used by the project.

  4. What does @CircuitBreaker do?

    Spring AOP intercepts the proxied method and uses the breaker identified by name. fallbackMethod optionally identifies the recovery method. Because it is proxy-based, self-invocation within the same bean normally bypasses the annotation.

  5. What are slidingWindowSize and failureRateThreshold?

    The sliding window is the recent sample used to calculate health: the last N calls for a count-based window or recent N seconds for a time-based window. The failure-rate threshold is the percentage of recorded failures that opens the circuit after minimumNumberOfCalls has been reached.

  6. What does waitDurationInOpenState do?

    It defines how long the breaker remains open before it may enter half-open and test recovery. A very short value can hammer an unhealthy dependency; a very long value delays recovery, so tune it using service behavior and SLOs.

  7. How is a fallback method defined?

    It belongs to the same Spring bean, must return a compatible type, and normally accepts the original method arguments followed optionally by the handled exception.

    public OrderResponse getOrders(Long userId) { ... }

private OrderResponse orderFallback(Long userId, Throwable error) {
    return OrderResponse.temporarilyUnavailable(userId);
}

    For CompletableFuture, Reactor, or other asynchronous return types, the fallback must return the corresponding compatible type.

Design and scenario questions

  1. UserService calls OrderService. Where does the breaker go?

    Put it in UserService around its OrderService client. Use a separate named breaker for OrderService so failures in another dependency do not affect it, and combine it with a strict connect/read timeout.

  2. Which failures does it protect against?

    Connection refusal, DNS/network failure, repeated HTTP 5xx responses, timeouts, excessive latency, exhausted downstream pools, and deployment outages. Do not normally record expected business responses such as a valid 404 or validation error as infrastructure failure.

  3. Real-life analogy:

    An electrical breaker cuts power when excessive current could damage the circuit. A software breaker similarly stops traffic to an unhealthy dependency and later sends controlled probes before restoring normal traffic.

  4. What if it opens frequently?

    Inspect breaker events, traces, downstream error rate and latency, saturation, recent deployments, network/DNS, pool sizes, and timeout alignment. Confirm that recorded and ignored exceptions are correct, fix the root cause, capacity-test it, then tune thresholds only from observed SLOs—do not hide an outage by simply increasing the threshold.

  5. How do you test it?

    Use a stub such as WireMock to return controlled failures or delays. Send enough calls to cross the configured minimum and threshold, assert the transition from closed to open and that later requests never reach the stub, advance/wait for half-open, then return success and assert closure. Also unit-test fallback semantics and run integration/chaos tests for timeouts and recovery.

  6. Circuit Breaker vs Bulkhead:

    A breaker stops calls based on dependency health; a bulkhead limits concurrent work so one slow dependency cannot consume every thread or connection. They solve different problems and should often be combined with timeouts: the bulkhead contains resource usage while the breaker fails fast during an outage.

Advanced questions

  1. Can it cause loss of critical functionality?

    It intentionally rejects calls, so a careless fallback can lose work or return incorrect data. For critical commands, use an idempotency key and a durable queue/outbox, expose a pending state, or return an explicit retryable error. Never claim success unless the operation was durably accepted.

  2. What about a fast but unreliable service?

    A failure-rate rule still opens the breaker even when failures arrive quickly. This protects correctness and avoids retry storms, but first classify exceptions carefully so expected client/business errors do not trip it.

  3. Can breakers be chained across service layers?

    Yes, but independently tuned breakers, retries, and fallbacks at every hop can create long latency and confusing behavior. Use an end-to-end deadline, limited retry budget, correlation IDs, clear ownership, and avoid fallback chains that call more unhealthy services. Prefer flatter call graphs and asynchronous workflows for long chains.

  4. Performance implications:

    State checks and metric recording add small CPU/memory overhead, usually far less than a network call. The larger risks are poorly chosen sliding windows, high-cardinality breaker names, blocking fallbacks, excessive event logging, and half-open probe storms.

  5. How is it monitored?

    Expose Resilience4j metrics through Spring Boot Actuator and Micrometer to Prometheus/Grafana. Track state, call count by outcome, rejected calls, failure and slow-call rates, state transitions, fallback rate, dependency latency, and business impact. Alert on sustained open state or abnormal fallback use, not every isolated transition.

  6. Resilience4j vs Netflix Hystrix:

    Hystrix is in maintenance mode and is based around its own command/thread-pool model. Resilience4j is actively used for modern applications, modular, lightweight, Java 8 functional-style, and integrates with Spring Boot, Reactor, and Micrometer. For new Spring Boot systems, Resilience4j is generally the appropriate choice.

This provides eventual consistency, not one global ACID transaction. Every step needs an idempotency key, explicit state transitions, retry policy, timeout handling, trace/correlation ID, and a reconciliation process for workflows stuck in an intermediate state.

Answers — Docker

  1. Docker: Docker builds and runs an application with its user-space runtime and libraries as an isolated process. Containers share the host kernel, so they are lighter than virtual machines but are not miniature VMs. A container should run one main concern, write durable state to external storage, receive configuration at runtime, and be replaceable rather than manually patched.
  2. Image vs container: An image is an immutable, content-addressed stack of read-only layers describing the filesystem and startup metadata. A container is a running instance with a thin writable layer, network namespace, resource controls, and runtime settings. Many containers can start from the same image; deleting a container loses its writable layer unless data is stored in a volume or external service.
  3. Dockerfile: It is the repeatable build recipe. FROM selects the base, WORKDIR sets context, COPY adds artifacts, RUN creates layers during build, USER drops privilege, and ENTRYPOINT/CMD define startup. Pin trusted base versions, use .dockerignore, order layers for caching, avoid secrets in build layers, and scan the final image.
  4. Spring Boot containerization: Build and test the JAR in CI or a multi-stage build, then copy only the artifact into a small supported JRE image. Run as non-root, expose the application port as documentation, configure a JVM/container-aware entrypoint, and supply profiles, URLs, and secrets through environment/configuration at deployment. Add Actuator readiness/liveness endpoints and handle SIGTERM for graceful shutdown.
  5. Benefits: The same versioned artifact moves through development, test, and production, reducing “works on my machine” drift. Containers start quickly, isolate dependencies, integrate well with CI/CD and orchestration, and make rollback predictable. They do not remove the need for OS/image patching, secret management, observability, backups, or capacity planning.

Answers — Kubernetes

  1. Kubernetes: Kubernetes is a control plane for declaring and continuously reconciling desired state for container workloads. It schedules Pods, restarts failed instances, manages service discovery, configuration, secrets, rollouts, and scaling. It solves orchestration, not application correctness; poor probes, resource limits, or state handling can still cause outages.
  2. Pod: A Pod is the smallest schedulable unit and may contain one main container plus tightly coupled sidecars. Containers in it share an IP/port namespace and mounted volumes and are created and destroyed together. Pods are ephemeral, so clients use a Service instead of a Pod IP and persistent state uses managed stores or persistent volumes.
  3. Deployment: A Deployment declares the desired replica count and Pod template for a stateless workload. It manages ReplicaSets, rolling updates, rollout history, pause/resume, and rollback. Configure maxUnavailable/maxSurge, readiness probes, and graceful termination so new versions receive traffic only when ready and old requests can finish.
  4. Service: A Kubernetes Service selects Pods by label and provides a stable DNS name and virtual address while endpoints change. ClusterIP is internal, NodePort exposes node ports, and LoadBalancer integrates with a cloud load balancer. An Ingress or Gateway commonly handles external HTTP routing and TLS above Services.
  5. Scaling: A Deployment can scale replicas manually; the Horizontal Pod Autoscaler reacts to CPU, memory, or custom metrics; the Cluster Autoscaler adds/removes nodes. Effective scaling also requires stateless application nodes, enough database/broker capacity, partitioning, connection limits, readiness, and backpressure. Autoscaling reacts after load appears, so minimum capacity and realistic load testing still matter.

Answers — AWS

  1. AWS experience: Name only services you actually used and explain responsibility rather than reciting a catalog: “I deployed Spring Boot images to ECS, stored data in RDS PostgreSQL, used S3 for documents, CloudWatch for logs/alarms, and IAM roles plus Secrets Manager for access.” Add one concrete design or incident and clarify what platform work was handled by another team.
  2. EC2: Elastic Compute Cloud provides configurable virtual machines. You choose the AMI, instance type, network, storage, and scaling model and remain responsible for guest OS patches, runtime, deployment, and much of availability. Use security groups, IAM instance roles instead of static keys, private subnets where appropriate, Auto Scaling Groups, health checks, and immutable replacement.
  3. S3: Simple Storage Service is highly durable object storage accessed by bucket/key APIs. It fits uploads, backups, logs, static assets, and data lakes, but is not a relational database or conventional block filesystem. Use least-privilege bucket policies, block public access by default, encryption, versioning/lifecycle rules, and presigned URLs when clients need temporary direct access.
  4. RDS: It manages relational engines such as PostgreSQL and MySQL, automating backups, monitoring integration, maintenance, and optional Multi-AZ failover. The team still owns schema design, indexes, slow-query tuning, connection pooling, capacity, parameter choices, and tested recovery. Read replicas scale eligible reads but do not replace backups or solve write bottlenecks.
  5. AWS deployment: CI tests and scans an immutable image, publishes it to ECR, and deploys it to ECS/EKS (or EC2) behind an Application Load Balancer. Run tasks in private subnets, restrict security groups, use IAM roles and Secrets Manager, connect to Multi-AZ RDS, and send logs/metrics/traces to an observable platform. Add health checks, autoscaling, migrations, blue/green or rolling deployment, alarms, backups, and an exercised rollback/recovery plan.

Answers

  1. Unit vs integration: A unit test constructs one class with controlled collaborators, runs in milliseconds, and pinpoints business-rule failures. An integration test verifies real boundaries such as Spring wiring, HTTP serialization, JPA mappings, database constraints, or broker configuration. Use many focused unit tests and fewer high-value integration/contract/end-to-end tests; the distinction is the boundary being exercised, not the annotation name alone.
  2. Mocking: A mock replaces a collaborator with programmable behavior and records interactions. It is useful for failure paths or expensive/nondeterministic dependencies, but mocking every internal class couples tests to implementation. Prefer real value objects and pure logic, mock true boundaries, and assert the observable result; verify calls only when the interaction itself is the behavior.
  3. Mockito: @Mock creates collaborators, @InjectMocks constructs the subject, when(...).thenReturn(...) stubs results, thenThrow models errors, and verify/ArgumentCaptor inspect interactions. Use @ExtendWith(MockitoExtension.class) in JUnit 5. Avoid broad any() matchers when important arguments should be asserted, and do not mock DTOs/entities unnecessarily.
  4. REST API tests: Cover valid responses, request validation, malformed input, authentication, object-level authorization, media types, serialization, pagination/sorting, concurrency/idempotency, stable error contracts, and persistence side effects. Add controller slice tests, database-backed integration tests, consumer/provider contract tests, and a small number of end-to-end flows. Explicitly test 401 vs 403 and information leakage.
  5. JUnit: JUnit 5 supplies the Jupiter programming model and Platform: @Test, lifecycle hooks, assertions, nested and parameterized tests, tags, extensions, and executable discovery. Use descriptive test names and Arrange–Act–Assert. A good test is deterministic, independent, fast enough for its layer, and explains the rule it protects.
  6. RSpec: RSpec is Ruby's behavior-driven testing framework and is common in Rails for model, request, service, and system specs. describe, context, and it express behavior, while expectations assert outcomes. In a Java interview, distinguish it from JUnit/Mockito and mention it only when discussing a Rails service or polyglot project.
  7. External API testing: Unit-test your adapter with a mocked HTTP client for business branches, then integration-test against WireMock/MockWebServer for URL, headers, JSON, error mapping, timeouts, retries, and malformed responses. Use provider contract tests or a sandbox for compatibility. Inject the client and clock, keep retries bounded, and assert that non-idempotent requests are not duplicated.
  8. Mock vs real dependency: A mock is fast and deterministic but proves only your assumption about the collaborator. A real PostgreSQL/Kafka/Redis container verifies protocol, SQL, mapping, and configuration but takes longer and can require lifecycle management. Use Testcontainers for important infrastructure compatibility and mocks for narrow unit behavior; neither alone gives complete confidence.

  • How would you design a reconciliation process?
  • How would you secure sensitive financial data?
  • How would you handle concurrent requests for the same transaction?

Answers

  1. Payment API design: Create a payment intent containing immutable amount, currency, merchant/order reference, payer, and idempotency key; return a server-generated payment ID and explicit state such as PENDING. Keep provider interaction behind an adapter, verify signed callbacks, and expose status, capture/cancel, and refund operations with authorization and audit history. Treat the provider response and webhook as inputs to a state machine, not direct permission to overwrite any state.
  2. Prevent duplicate charges: Require an idempotency key scoped to the merchant/operation and enforce it with a database unique constraint. Store a canonical request hash so reuse with different amount or beneficiary is rejected. Use conditional state changes or locking so only one worker performs the provider call, reuse the same provider reference during safe retries, and make webhook/message consumers idempotent as well.
  3. Idempotency: Repeating the same logical operation one or many times produces the same externally visible result without repeating the side effect. It does not mean every HTTP method is automatically safe: the server must identify the operation and persist its outcome. This is essential because clients, gateways, brokers, and operators can retry after timeouts even when the first attempt succeeded.
  4. Idempotency-key implementation: In one transaction insert (merchant_id, key, request_hash, status) under a unique constraint. The winner processes the operation and stores status code plus response; an identical concurrent/repeated request waits or returns the stored result. A different hash receives a conflict. Define retention and protect against a worker stuck in PROCESSING through leases/status recovery and reconciliation.
  5. Success with lost response: The outcome is unknown to the client, not necessarily failed. It retries with the same key and receives the stored response; the server must not generate a new charge. If local state is uncertain, query the provider by the original stable reference or consume its verified webhook, then reconcile. Never blindly retry with a new provider reference after a timeout.
  6. Failed banking API: Use strict connect/read timeouts, a circuit breaker, and bounded concurrency. Distinguish a definitive decline from a technical failure and from an unknown result after submission. Retry only if the provider supports idempotency; otherwise query status/reconcile before another attempt. Queue recoverable work, surface a truthful pending state, alert on error rates, and preserve provider correlation IDs.
  7. Safe retries: Retry transient conditions such as connection reset, throttling, or a documented 5xx, not validation errors or declines. Apply exponential backoff with jitter, a maximum attempt/time budget, the same idempotency identifier, and a circuit breaker. Persist retry state for durable workflows and route exhausted cases to controlled investigation rather than an endless loop.
  8. Transaction consistency: Commit payment state, ledger entries, and an outbox event atomically in the local database. Publish from the outbox and let idempotent consumers update their own stores. Across provider and services, use explicit Saga states and compensation/refund where valid, plus reconciliation for ambiguous outcomes. A remote provider call cannot participate reliably in the same local ACID transaction.
  9. Audit trail: Keep append-only records with transaction/event ID, actor, timestamp, correlation ID, source, reason, prior/new state, provider reference, and monetary debit/credit entries. Restrict and monitor access, encrypt sensitive fields, synchronize time, and make tampering detectable through immutable storage or controlled ledger rules. Corrections should append reversal/adjustment entries rather than rewriting history.
  10. Reconciliation: On a schedule ingest provider settlement/status reports, normalize them, and match by stable provider and internal references, amount, currency, and date. Classify exact matches, missing local/provider records, duplicates, and amount/status mismatches. Auto-repair only safe known cases, retain evidence, alert owners, and route unresolved breaks to an auditable operations queue.
  11. Financial-data security: Minimize collected data, tokenize card details through a compliant provider, use TLS and encryption at rest, isolate networks, rotate secrets/keys, and grant least-privilege access through short-lived identities. Mask logs and UI, audit reads and mutations, apply retention/deletion policy, and follow applicable PCI/regulatory controls. Never store CVV or log full PAN, credentials, tokens, or webhook secrets.
  12. Concurrent requests: Enforce the invariant at the database with unique constraints and an atomic conditional update such as UPDATE ... SET status='PROCESSING' WHERE status='PENDING'. Use optimistic @Version checks when conflicts are rare or a short pessimistic lock when contention is expected. Idempotency records ensure only one logical request wins even across multiple application instances.

Idempotent payment flow

BEGIN;
INSERT INTO idempotency_request(merchant_id, request_key, request_hash, status)
VALUES (:merchant, :key, :hash, 'PROCESSING'); -- unique(merchant_id, request_key)

INSERT INTO payment(id, amount, currency, status)
VALUES (:id, :amount, :currency, 'PENDING');
COMMIT;

A repeated request with the same key and payload receives the stored result; the same key with a different payload is rejected. If the provider times out, mark the outcome UNKNOWN rather than failed, query the provider using its stable reference, and reconcile before retrying a charge. Store money as an integer minor unit or exact decimal—never binary floating point.

Questions

  1. What is Hibernate, and how is it different from JPA?
  2. Explain the transient, persistent/managed, detached, and removed entity states.
  3. What are SessionFactory, Session, EntityManagerFactory, and EntityManager?
  4. What is dirty checking, and when does Hibernate execute SQL?
  5. What is the difference between persist(), merge(), save(), and update()?
  6. Explain lazy and eager fetching. What is LazyInitializationException?
  7. What is the N+1 query problem, and how can it be resolved?
  8. What are Hibernate's first-level and second-level caches?
  9. What is the difference between cascade types and orphanRemoval?
  10. How do optimistic and pessimistic locking prevent concurrent-update problems?
  11. What are the owning and inverse sides of a bidirectional relationship?
  12. How would you diagnose and improve Hibernate performance?

Answers

  1. Hibernate vs JPA: Hibernate is an ORM framework that maps Java objects and relationships to relational tables and generates SQL for persistence operations. Jakarta Persistence (formerly JPA) is a specification defining APIs and annotations such as EntityManager, @Entity, and JPQL. Hibernate is a common implementation of that specification and also provides vendor-specific features. Code written only against standard JPA APIs is generally easier to move to another provider.
  2. Entity states: A transient object was created with new but is not associated with a persistence context. A managed entity is tracked by the current persistence context, so changes can be synchronized automatically. A detached entity was previously managed but is no longer tracked because the context was cleared or closed. A removed entity is managed and scheduled for deletion when the context flushes.
  3. Persistence objects: SessionFactory is Hibernate's heavyweight, thread-safe factory and should usually be created once per database. A Session is a lightweight, non-thread-safe unit of work holding the persistence context. JPA's equivalents are EntityManagerFactory and EntityManager. In Spring, these are normally configured and scoped for you; application code should not share one entity manager/session across threads.
  4. Dirty checking and flushing: Hibernate keeps snapshots of managed entities. At flush time it compares their current state with the tracked state and generates UPDATE statements for detected changes, so calling a repository save() after every setter is not required for an already managed entity. A flush commonly occurs before transaction commit and sometimes before a query whose result could depend on pending changes. flush() synchronizes SQL with the database but does not commit the transaction.
  5. Persistence methods: JPA persist() makes a new instance managed and has no returned entity. merge() copies state into a managed instance and returns that managed instance; the supplied object remains detached. Hibernate save() is a provider-specific insert-oriented operation that returns an identifier. Hibernate update() reattaches a detached instance and can fail if the session already contains another object with the same identity. In Spring Data JPA, save() delegates to persist for new entities and merge otherwise.
  6. Fetching: Lazy fetching loads an association only when it is accessed; eager fetching requests it as part of the original load contract, although it does not guarantee one SQL join. LazyInitializationException occurs when an uninitialized lazy proxy or collection is accessed after its session/persistence context has closed. Fix the use case by fetching required data inside the transaction with a fetch join, entity graph, or DTO projection—not by making every association eager or keeping the session open across arbitrary layers.
  7. N+1 problem: N+1 means one query loads N parent rows and accessing an association triggers as many as N more queries. Resolve it per use case with JPQL JOIN FETCH, @EntityGraph, DTO projections, or batch fetching. Do not combine collection fetch joins carelessly with pagination because row multiplication can produce incorrect or inefficient paging; use a two-step ID query or batch loading when needed.
  8. Caches: The first-level cache is the mandatory persistence-context identity map. It ensures one managed object per entity identity and avoids repeating an ID lookup within that context. The optional second-level cache is shared across sessions/entity managers and stores entity or collection data through a configured cache provider. The query cache stores query result identifiers, not complete object graphs, and must be used selectively. Cache mostly-read data, define invalidation and expiry behavior, and measure hit rates.
  9. Cascade vs orphan removal: Cascade types propagate operations such as PERSIST, MERGE, or REMOVE from a parent to associated entities. orphanRemoval = true deletes a child when it is removed from the parent's relationship and no longer belongs to that aggregate. They are related but not identical: cascade remove applies when the parent itself is deleted, while orphan removal applies when the child is disconnected. Avoid CascadeType.REMOVE on shared entities or many-to-many relationships.
  10. Locking: Optimistic locking uses a @Version column. An update includes the previous version in its WHERE clause; if another transaction already changed the row, Hibernate raises an optimistic-lock exception so the operation can be retried or rejected. Pessimistic locking requests a database lock, such as PESSIMISTIC_WRITE, and can block competing transactions. Prefer optimistic locking when conflicts are rare; use pessimistic locking for short, highly contested critical sections after considering deadlocks and timeouts.
  11. Relationship ownership: In a bidirectional association, the owning side controls the foreign-key update. The inverse side uses mappedBy. For a typical one-to-many/many-to-one mapping, the child with @ManyToOne and @JoinColumn is the owner. Update both sides in helper methods so the in-memory object graph remains consistent, even though only the owning side determines the SQL relationship change.
  12. Performance diagnosis: Start with measured request and SQL timings. Enable controlled SQL/statistics logging outside sensitive production paths, inspect query counts, use application tracing, and analyze slow statements with the database execution plan. Look for N+1 queries, unnecessary eager relationships, missing indexes, oversized entity graphs, unbounded result sets, excessive flushing, lock waits, and connection-pool exhaustion. Apply targeted projections/fetch plans, pagination, batching with periodic flush()/clear(), read-only transactions where useful, and properly sized pools; then verify improvements with production-like load.
19. Java and Spring Deep Dives

1. Type casting in Java: internal working and why data is lost

Type casting converts a value or reference from one type to another. Java has two distinct forms: primitive conversion changes the value's representation, while reference casting changes the type through which an existing object reference is viewed.

Primitive widening

A widening conversion moves a value to a type with a wider supported range and is usually automatic:

int count = 42;
long largeCount = count;   // int -> long: exact
double result = count;     // int -> double: exact for this value

The JVM does not copy the original variable's raw bytes and add empty bytes blindly. It converts the numeric value into the target type's representation. Signed integers are sign-extended when widened, so negative values remain negative.

Widening does not always mean perfect precision. A float and double have a much larger range than integer types but store only a fixed number of significant binary digits. For example, a long has 64 bits of integer precision, while a double has 53 bits of integer precision:

long id = 9_007_199_254_740_993L; // 2^53 + 1
double approximate = id;
long restored = (long) approximate;

System.out.println(approximate); // 9.007199254740992E15
System.out.println(restored);    // 9007199254740992: one was lost

Primitive narrowing and data loss

A narrowing conversion moves to a type with a smaller range or less precision and requires an explicit cast because information may be discarded:

int value = 130;
byte small = (byte) value;
System.out.println(small); // -126

double price = 99.99;
int whole = (int) price;
System.out.println(whole); // 99

A Java byte is an 8-bit signed two's-complement value with range -128 to 127. The binary representation of 130 ends with 10000010. Narrowing to byte keeps only those low 8 bits and discards the higher bits. Because the retained sign bit is 1, the same bit pattern represents -126. Java does not clamp the result to 127 and does not raise an overflow exception.

Floating-point to integer conversion first removes the fractional part by truncating toward zero. NaN becomes zero; values outside the target integer range become the nearest endpoint before any further narrowing. This is why money should use BigDecimal with an explicit rounding rule rather than casts from double.

Numeric promotion inside expressions

Java promotes byte, short, and char operands to int before arithmetic. The calculation may therefore produce an int even when both inputs are bytes:

byte a = 10;
byte b = 20;
// byte sum = a + b;       // compile error: a + b is int
byte sum = (byte) (a + b); // explicit narrowing back to byte

Reference casting

Animal animal = new Dog(); // upcasting: automatic and safe
Dog dog = (Dog) animal;    // downcasting: checked at runtime

Animal cat = new Cat();
// Dog invalid = (Dog) cat; // ClassCastException

Upcasting does not modify the object; it only exposes the members defined by the parent type. Downcasting also does not transform a Cat into a Dog. The JVM checks the object's real runtime class, and an incompatible cast throws ClassCastException. Prefer pattern matching when the type is genuinely variable:

if (animal instanceof Dog dog) {
    dog.fetch();
}

Interview summary: primitive narrowing can lose high-order bits, fractional data, or floating-point precision because the target representation cannot hold all source information. Reference casting preserves the object but may fail when its runtime type is incompatible.

2. Do Java threads share memory?

Threads in the same JVM process share the heap, which contains objects and arrays, and shared class data such as static fields. They also use the same loaded classes and native process resources. Each thread has its own Java stack, program counter, and native stack. Method parameters and local variables live in that thread's stack frame, but a local variable can hold a reference to an object on the shared heap.

Memory/resourceShared?Meaning
Heap objects and arraysYesTwo threads can read or modify the same object when both can reach it
static fieldsYesOne class-level value is visible across threads, subject to memory-visibility rules
Thread stack and stack framesNoEach thread has its own method calls, primitive locals, and reference variables
Object referenced by a local variablePossiblyThe reference is local; the referenced heap object can still be shared
Program counter and registersNoEach thread tracks its own current instruction and execution state

Sharing memory creates two separate correctness problems:

  1. Atomicity: counter++ is a read, calculation, and write. Two threads can read the same old value and overwrite one another's increments.
  2. Visibility and ordering: without a happens-before relationship, one thread is not guaranteed to observe another thread's latest writes in the expected order because values may be cached and operations may be reordered.
class UnsafeCounter {
    private int value;
    void increment() { value++; } // race condition
}

class SafeCounter {
    private final AtomicInteger value = new AtomicInteger();
    void increment() { value.incrementAndGet(); }
    int get() { return value.get(); }
}

Use immutable objects, confinement, synchronized, locks, atomic classes, concurrent collections, or message passing according to the operation. volatile provides visibility and ordering for reads/writes of that field, but it does not make a compound action such as counter++ atomic.

A lock release happens-before a later successful acquisition of the same lock. A write to a volatile field happens-before a later read of that field. Thread start/join and concurrent utilities provide additional happens-before guarantees defined by the Java Memory Model.

3. DTO and view layer in Spring Boot

A DTO (Data Transfer Object) is the explicit data contract crossing an application boundary. Request DTOs define accepted input; response DTOs define returned output. A DTO should contain the fields required by the use case, without persistence behavior.

The view layer is the presentation boundary. In a REST Spring Boot application, the controller and JSON response form the view layer. In server-rendered Spring MVC, a controller supplies a model and returns a template name for Thymeleaf or another view engine.

// API contracts: no JPA annotations
public record CreateUserRequest(
    @NotBlank String name,
    @Email String email
) {}

public record UserResponse(
    long id,
    String name,
    String email
) {}

@RestController
@RequestMapping("/api/users")
class UserController {
    private final UserService userService;

    UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    ResponseEntity<UserResponse> create(
            @Valid @RequestBody CreateUserRequest request) {
        UserResponse response = userService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }
}

@Service
class UserService {
    private final UserRepository repository;

    @Transactional
    public UserResponse create(CreateUserRequest request) {
        User user = new User(request.name(), request.email());
        User saved = repository.save(user);
        return new UserResponse(saved.getId(), saved.getName(), saved.getEmail());
    }
}

This flow is HTTP request → controller/view boundary → request DTO → service/domain → entity/repository → response DTO → JSON. The controller handles HTTP concerns; the service owns the use case and transaction; the repository owns persistence.

Returning JPA entities directly can expose internal or sensitive fields, create recursive JSON through bidirectional relationships, trigger lazy-loading queries during serialization, and accidentally break the API when the schema changes. DTOs provide an allow-list of fields, stable versionable contracts, validation at the boundary, and use-case-specific shapes.

A DTO is not automatically a security boundary: still enforce authorization in the service and never trust client-supplied ownership, role, price, or audit fields. For large read-only lists, use a JPA DTO projection so the database selects only required columns instead of loading full entities and mapping them afterward.

@Query("""
    select new com.example.UserSummary(u.id, u.name)
    from User u
    where u.active = true
    """)
Page<UserSummary> findActiveSummaries(Pageable pageable);

For server-rendered MVC, the view model follows the same boundary principle:

@Controller
class UserPageController {
    @GetMapping("/users/{id}")
    String show(@PathVariable long id, Model model) {
        model.addAttribute("user", userService.getView(id));
        return "users/details"; // resolves templates/users/details.html
    }
}

4. REST statelessness in depth

REST's stateless constraint means every request contains all information the server needs to understand and authorize that request. The server does not rely on hidden conversational state from earlier requests. Any application state required between requests is held by the client and sent again, or is stored as a resource in a shared durable system.

Statelessness does not mean the server or database stores no data. Orders, users, carts, and idempotency records are server-side resource state. The constraint concerns per-client session context required to process the next request.

Stateful design that breaks horizontal scaling

// Instance A stores hidden conversation state in local memory.
POST /checkout/start       -> session step = ADDRESS
POST /checkout/next        -> expects the previous request to be on the same instance

If the load balancer sends the second request to instance B, or instance A restarts, B does not know the current step. Sticky sessions reduce this symptom but create uneven load, complicate failover, and keep correctness tied to one instance.

Stateless resource-oriented design

POST /checkouts
Authorization: Bearer <token>
Idempotency-Key: 8f1f...
{ "cartId": "c-42" }

201 Created
Location: /checkouts/ch-901
{ "id": "ch-901", "status": "ADDRESS_REQUIRED" }

PUT /checkouts/ch-901/address
Authorization: Bearer <token>
If-Match: "version-1"
{ "line1": "...", "city": "...", "postalCode": "..." }

POST /checkouts/ch-901/confirm
Authorization: Bearer <token>
Idempotency-Key: d941...

Every request identifies the resource, carries credentials, declares the intended operation and representation, and includes concurrency/idempotency metadata when needed. Any API instance can handle it by reading shared resource state. This enables horizontal scaling, retries, failover, observability, and caching because requests do not depend on one server's memory.

A bearer JWT is one way to send authentication context, but REST does not require JWT. An opaque session token can still support stateless application servers when the session record is in a shared store accessible to every instance. From the REST viewpoint, the request remains self-contained because it carries the token; operationally, the server performs a shared lookup.

Consequences and design rules

  • Authentication: send credentials or a token on every protected request. Do not assume a prior login request established local server memory.
  • Pagination: send the cursor, limit, filters, and sort order each time rather than storing the user's current page in process memory.
  • Retries: use idempotent HTTP methods where possible and idempotency keys for operations such as payments.
  • Concurrency: use ETags/If-Match, entity versions, or database constraints instead of a server-local flag.
  • Caching: explicit methods, resource URLs, and cache headers let intermediaries understand when a response can be reused.
  • Workflow state: model a long workflow as a resource with an ID and explicit state, rather than an invisible sequence tied to a connection or instance.

Tradeoff: self-contained requests may repeat headers and require token validation or state lookups. That overhead buys loose coupling between requests and instances. WebSockets can maintain a stateful connection for real-time transport while the underlying business commands still carry user and resource identity explicitly.
