SOLID Principles in Java

SOLID is a set of five object-oriented design principles used to write code that is maintainable, extensible, testable, and loosely coupled. These principles are especially useful when building Java and Spring Boot applications.

PrincipleFull formMain idea
SSingle Responsibility PrincipleOne class, one responsibility
OOpen/Closed PrincipleExtend behavior without modifying existing code
LLiskov Substitution PrincipleSubclasses must behave correctly in place of their parent
IInterface Segregation PrincipleDon't force classes to implement unused methods
DDependency Inversion PrincipleDepend on abstractions, not concrete implementations

S

Single Responsibility Principle (SRP)

Definition: A class should have only one reason to change.

Suppose we are developing an e-commerce application.

Bad Violates SRP

public class OrderService {
    public void createOrder(Order order) {
        System.out.println("Order saved");
    }

    public void sendEmail(Order order) {
        System.out.println("Email sent");
    }

    public void generateInvoice(Order order) {
        System.out.println("Invoice generated");
    }
}

Problem: OrderService has three responsibilities: order persistence, email notifications, and invoice generation. A change to any one of these concerns requires changing the same class.

Good Follows SRP

public class OrderRepository {
    public void save(Order order) {
        System.out.println("Order saved");
    }
}

public class EmailService {
    public void sendEmail(Order order) {
        System.out.println("Email sent");
    }
}

public class InvoiceService {
    public void generateInvoice(Order order) {
        System.out.println("Invoice generated");
    }
}

Each class now handles one responsibility. An orchestrator can coordinate them:

public class OrderService {
    private final OrderRepository repository;
    private final EmailService emailService;
    private final InvoiceService invoiceService;

    public OrderService(OrderRepository repository,
                        EmailService emailService,
                        InvoiceService invoiceService) {
        this.repository = repository;
        this.emailService = emailService;
        this.invoiceService = invoiceService;
    }

    public void placeOrder(Order order) {
        repository.save(order);
        emailService.sendEmail(order);
        invoiceService.generateInvoice(order);
    }
}
Important: SRP doesn't mean a class can have only one method. Its methods should serve one cohesive responsibility.

O

Open/Closed Principle (OCP)

Definition: Software entities should be open for extension but closed for modification.

Imagine a payment system supporting UPI, credit cards, and PayPal.

Bad Violates OCP

public class PaymentService {
    public void pay(String paymentType, double amount) {
        if (paymentType.equals("UPI")) {
            System.out.println("UPI payment");
        } else if (paymentType.equals("CARD")) {
            System.out.println("Card payment");
        } else if (paymentType.equals("PAYPAL")) {
            System.out.println("PayPal payment");
        }
    }
}

Problem: Every new payment method requires modifying the existing PaymentService.

Good Follows OCP

public interface PaymentMethod {
    void pay(double amount);
}

public class UpiPayment implements PaymentMethod {
    @Override
    public void pay(double amount) {
        System.out.println("Paid using UPI");
    }
}

public class CardPayment implements PaymentMethod {
    @Override
    public void pay(double amount) {
        System.out.println("Paid using Card");
    }
}

public class PaymentService {
    public void processPayment(PaymentMethod method, double amount) {
        method.pay(amount);
    }
}

Usage:

PaymentService service = new PaymentService();
service.processPayment(new UpiPayment(), 1000);
service.processPayment(new CardPayment(), 2000);

A cryptocurrency implementation can now be added without changing PaymentService:

public class CryptoPayment implements PaymentMethod {
    @Override
    public void pay(double amount) {
        System.out.println("Paid using Crypto");
    }
}
Key idea: Use interfaces and polymorphism to extend behavior without repeatedly changing stable business logic.

L

Liskov Substitution Principle (LSP)

Definition: Objects of a subclass should be replaceable with objects of their parent class without breaking expected behavior.

Bad Violates LSP

public class Bird {
    public void fly() {
        System.out.println("Flying...");
    }
}

public class Sparrow extends Bird {}

public class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins cannot fly");
    }
}

public void makeBirdFly(Bird bird) {
    bird.fly();
}

makeBirdFly(new Sparrow()); // Works
makeBirdFly(new Penguin()); // Runtime exception

Problem: Penguin cannot fulfill the flying behavior promised by its parent class.

Good Follows LSP

public abstract class Bird {
    public abstract void eat();
}

public interface Flyable {
    void fly();
}

public class Sparrow extends Bird implements Flyable {
    @Override
    public void eat() { System.out.println("Sparrow eating"); }

    @Override
    public void fly() { System.out.println("Sparrow flying"); }
}

public class Penguin extends Bird {
    @Override
    public void eat() { System.out.println("Penguin eating"); }
}

public void makeBirdFly(Flyable bird) {
    bird.fly();
}

A penguin cannot be passed to makeBirdFly() because it doesn't implement Flyable.

Key idea: Inheritance should preserve behavioral contracts, not merely represent an is-a relationship. LSP also applies to return values, exceptions, preconditions, and postconditions.

I

Interface Segregation Principle (ISP)

Definition: Clients should not be forced to depend on methods they do not use.

Bad Violates ISP

public interface Employee {
    void work();
    void attendMeeting();
    void writeCode();
}

public class SecurityGuard implements Employee {
    public void work() { System.out.println("Guarding"); }
    public void attendMeeting() { throw new UnsupportedOperationException(); }
    public void writeCode() { throw new UnsupportedOperationException(); }
}

Problem: SecurityGuard is forced to implement methods irrelevant to its responsibility.

Good Follows ISP

public interface Workable {
    void work();
}

public interface MeetingAttendee {
    void attendMeeting();
}

public interface Programmer {
    void writeCode();
}

public class Developer implements Workable, MeetingAttendee, Programmer {
    public void work() { System.out.println("Working"); }
    public void attendMeeting() { System.out.println("Attending meeting"); }
    public void writeCode() { System.out.println("Writing code"); }
}

public class SecurityGuard implements Workable {
    public void work() { System.out.println("Guarding"); }
}
Key idea: Prefer small, focused interfaces instead of large interfaces containing unrelated methods.

D

Dependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions.

This is particularly important in Spring Boot applications.

Bad Violates DIP

public class MySQLDatabase {
    public void save(String data) {
        System.out.println("Saved to MySQL");
    }
}

public class UserService {
    private MySQLDatabase database = new MySQLDatabase();

    public void createUser(String name) {
        database.save(name);
    }
}

Problem: UserService depends directly on MySQLDatabase. Switching to PostgreSQL requires changing the service.

Good Follows DIP

public interface Database {
    void save(String data);
}

public class MySQLDatabase implements Database {
    @Override
    public void save(String data) { System.out.println("Saved to MySQL"); }
}

public class PostgreSQLDatabase implements Database {
    @Override
    public void save(String data) { System.out.println("Saved to PostgreSQL"); }
}

public class UserService {
    private final Database database;

    public UserService(Database database) {
        this.database = database;
    }

    public void createUser(String name) {
        database.save(name);
    }
}

Usage:

Database db = new PostgreSQLDatabase();
UserService service = new UserService(db);
service.createUser("Rahul");

How DIP works in Spring Boot

public interface NotificationService {
    void send(String message);
}

@Service
public class EmailNotificationService implements NotificationService {
    @Override
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

@Service
public class OrderService {
    private final NotificationService notificationService;

    public OrderService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void placeOrder() {
        notificationService.send("Order placed");
    }
}

Spring injects EmailNotificationService into OrderService. With multiple implementations, use @Qualifier or @Primary to choose one.

Important distinction: Dependency Injection is a technique; Dependency Inversion is a design principle. You can use DI without fully following DIP.

Common interview questions

What is the difference between SRP and ISP?

SRP focuses on the responsibilities of a class or module. ISP prevents clients from depending on interface methods they don't need.

What is the difference between OCP and DIP?

OCP says behavior should be extendable without modifying existing code. DIP helps achieve that by making high-level logic depend on abstractions.

Does using an interface automatically satisfy SOLID?

No. Interfaces are tools. Poorly designed interfaces can still violate SRP, LSP, or ISP.

Which SOLID principles are most commonly used in Spring Boot?

All five are relevant, but SRP, OCP, and DIP are especially visible in service-layer architecture, strategy implementations, and dependency injection.

Is inheritance required for LSP?

LSP applies to behavioral subtyping, including both class inheritance and interface implementations in Java.

A useful way to remember SOLID

  • SGive each class a focused responsibility.
  • OAdd new behavior without changing stable existing logic.
  • LA subtype must honor its parent's contract.
  • IDon't make clients depend on capabilities they don't need.
  • DDepend on interfaces or abstractions rather than concrete implementations.
